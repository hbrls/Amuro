# OpenHarmony LENS

> updated_by: Codex - GPT-5
> updated_at: 2026-06-13 11:40:42

## 目标

OpenHarmony LENS 用于从 OpenHarmony / HarmonyOS 技术体系、系统架构、版本血统、应用模型、权限模型和兼容层边界出发，判断 Android App 或 Android 标准接口在鸿蒙环境中的行为来源。

## 适用场景

- 需要判断某个鸿蒙版本是否具备 Android / AOSP 兼容基础。
- 需要分析 HarmonyOS NEXT / 纯血鸿蒙路径下 Android APK、兼容容器或迁移工具的角色。
- 需要设计覆盖鸿蒙大版本、设备形态和运行方式的验证矩阵。
- 需要区分宿主系统能力、兼容层代理能力和容器虚拟能力。

## 分析范围

- 系统应用模型与 Android 应用模型差异
- 权限声明与授权流程
- 应用列表、包管理、应用发现能力
- 兼容层或容器层接口真实性
- 原生能力、桥接能力、SDK 能力边界
- 设备系统版本、API version、厂商定制差异

## 分析维度

1. 系统血统：AOSP 兼容、过渡形态、NEXT / 纯血鸿蒙。
2. 应用模型：原生鸿蒙应用、Android APK、兼容容器内应用。
3. 能力边界：位置、通知、剪贴板、存储、传感器、网络、电池等是否由宿主代理。
4. 版本矩阵：鸿蒙 4 / 5 / 6 / 7 的发布时间、升级路径、可安装性和兼容策略。
5. 设备矩阵：手机、平板、折叠屏等设备形态对版本和兼容能力的影响。
6. API version：系统版本、API version、应用模型和调用路径的对应关系。
7. 能力来源：原生系统能力、兼容层能力、SDK 封装能力和业务层模拟能力。
8. 证据来源：官方资料、开发者文档、云设备、真机实测、客户侧反馈。

## 输出要求

使用本 LENS 时，至少输出：

- 鸿蒙版本血统判定表。
- 目标能力在该系统体系下是否存在原生接口的判断。
- Android APK 与兼容容器可用性判断。
- 宿主能力、兼容层能力、容器视图之间的边界图。
- 最小覆盖矩阵：版本、设备形态、运行方式、接口族、证据等级。
- 最小诊断入口要求。
- 缺口标记：无法实测的矩阵格必须标注风险和待补证方式。

## 判断原则

- 不得把所有鸿蒙版本视为同一种系统架构。
- 不得把 NEXT / 纯血鸿蒙上的兼容行为外推到 AOSP 兼容版本，反之亦然。
- 不得在缺少证据时断言 APK 可安装性或接口真实性。
- 不得以样本穷举替代系统血统和架构边界分析。
- 不得把 Android API 行为直接套用到 OpenHarmony / HarmonyOS。
- 不得把兼容层表现直接等同于原生系统能力。
- 不得把 SDK 返回值直接等同于系统能力。
- 必须区分设备系统版本、API version、应用模型和调用路径。
