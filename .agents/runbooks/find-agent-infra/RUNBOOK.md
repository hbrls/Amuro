# 技术产品调研 RUNBOOK

> updated_by: Codex - GPT-5
> updated_at: 2026-07-31 14:44:38

本 RUNBOOK 指导 Agent 自上而下地完成一次性技术产品调研。调研由产品问题和架构问题驱动，目标是建立对产品及系统的整体理解，而不是盘点仓库实现细节。

## 核心调研焦点：工作 PC 与完整运行形态

本 RUNBOOK 的核心调研焦点是产品在工作 PC 上的安装、运行与完整系统形态。Local 优先是产品选型标准，不是裁剪调研范围的条件；即使产品不满足选型标准，也必须完成证据充分的调研并报告缺陷。

### 焦点：Windows 与 macOS

- 本文中的 PC 同时包括 Windows 和 macOS 工作机，不能把 PC 等同于 Windows。
- Windows 和 macOS 都是必查平台，必须分别说明安装方式、运行形态、依赖、权限、网络要求和卸载方式。
- Linux 可以作为系统其他组件的运行环境被记录，但不能替代 Windows 或 macOS 工作机的调研。
- 若产品仅支持 Linux，或缺失 Windows、macOS 任一平台支持，应记录事实、影响和选型缺陷；不得仅因平台不符合要求而停止其余产品与架构调研。

### 焦点：Local 优先是选型标准

- 必须判断产品属于本地运行、云端 SaaS 或本地与云端混合形态，并说明核心能力实际运行在哪里。
- 产品要求是 Local 优先：若主体能力依赖云端、桌面客户端只是壳，或本地形态存在明显能力缺失，应明确报告为选型缺陷。
- 选型缺陷不等于停止调研。不得把不符合 Local 优先要求的产品直接排除后省略其真实运行形态。

### 焦点：存在云端时必须完整调研

- 只要产品存在云端组件，就必须把云端纳入系统全貌、组件关系和核心链路，不能只因其被描述为网关或辅助服务而略过。
- 云端调研至少应覆盖其职责边界、核心组件、主要依赖、接口、持久化、通信、部署或托管形态，以及数据、权限和网络边界。
- 若云端只是认证、转发、路由或代理网关，也应说明其作用、接口、数据经过方式、鉴权和故障影响；与核心问题无关的扩缩容、高可用或内部实现不必无边界展开。
- 报告必须同时给出云端形态的调研结果和 Local 优先适配判断，不能用选型结论替代事实调研。

## 适用范围

本 RUNBOOK 只包含以下两类调研：

### 产品调研

- 产品定位
- 目标用户
- 核心流程
- 功能边界
- 维护状态
- 版本演进
- 生态与反馈

### 技术架构调研

- 运行形态
- 主要依赖
- 接口形态
- 持久化方式
- 通信方式
- 部署形态

## 明确排除

### 不是源码审计

调研不得演变为逐文件、逐目录或逐实现细节的源码审计。以下行为不属于本 RUNBOOK 的默认步骤：

- 批量扫描 schema、路由、锁、队列、心跳、重试或进程内数据结构
- 统计源码文件、路由模块、端点、配置键或代码行数
- 穷举数据库表、接口、环境变量或第三方依赖
- 为了证明“未发现”而进行无边界的全仓库搜索
- 在缺少上层问题时直接追踪函数调用和实现细节

源码只可用于验证已经提出的关键技术问题。每次阅读源码前，必须能够说明“需要验证什么结论”；问题得到足够回答后立即停止下钻。

### 不做竞品比较

每次调研都是针对唯一产品的独立调研。本 RUNBOOK 不包含竞品调研、横向比较、选型矩阵或优劣排名。不得主动扩大到其他产品，也不得以竞品作为解释当前产品的默认参照。

产品对比由另一个 Agent 在多个独立调研结果之上，使用单独的对比流程完成；不得让当前产品调研 Agent 在本 RUNBOOK 内追加横向对比。

### 不调研遥测（Telemetry）

本 RUNBOOK 不包含遥测、监控、指标采集、链路追踪、错误上报或运营数据采集的调研。不得主动扫描埋点、上报通道、指标定义、Dashboard 或告警规则，也不得将这些内容作为架构或运行形态的默认组成部分。产品中存在埋点或上报通道不等同于其属于核心架构，不得据此展开调查。

如用户明确提出遥测相关需求，应使用单独的调研流程，不得在本 RUNBOOK 内追加。

## 核心原则

### 自上而下

先理解产品为何存在、服务谁、如何工作，再建立系统边界、组件关系和核心链路，最后验证关键技术结论。不得从数据库、路由、锁或队列等底层细节反向拼装产品全貌。

### 问题驱动

每项证据都必须服务于一个调研问题。没有对应问题的资料收集不进入调研范围；没有影响核心结论的实现差异不继续下钻。

### 先全貌，后细节

技术架构调研应先回答：

1. 系统以什么形态运行？
2. 系统由哪些主要部分组成？
3. 各部分的职责和边界是什么？
4. 一条核心业务链路如何穿过这些部分？
5. 哪些技术约束会影响部署、使用或扩展？

只有在这些问题形成初步模型后，才按需核验接口、持久化、通信和依赖。

### 证据与结论匹配

| 证据类型 | 适合回答的问题 | 使用边界 |
| --- | --- | --- |
| 官方产品资料 | 定位、用户、功能、核心流程、支持范围 | 宣传性表述需与实际文档、版本记录或用户反馈交叉确认 |
| 官方文档与版本记录 | 使用方式、部署方式、维护状态、功能演进 | 文档可能滞后，需记录证据时间和版本 |
| 仓库元数据与配置 | 许可证、发布状态、运行入口、构建及部署形态 | 只能证明当前快照，不外推历史或运行时表现 |
| 定点源码证据 | 官方资料无法回答的关键架构问题 | 只验证具体问题，不扩展为源码审计 |
| Issue、Discussion 与社区资料 | 真实使用反馈、常见限制、生态活跃度 | 个案不代表整体，必须说明样本和时间边界 |
| 架构推导 | 组件关系、运行边界和核心链路的解释 | 必须标注为推导，不等同于运行验证 |
| 未决 | 缺少运行验证、官方说明或足够反馈 | 不得包装为已确认结论 |

### 单一交付物

- 调研结束时只保留一份整合文档。
- 临时记录应在最终交付前整合或删除。
- 关键结论应附官方文档、版本记录、仓库文件或公开讨论等证据锚点。
- 明确区分“已确认”“合理推导”“未发现”和“未决”。

## 调研流程

### 步骤 1：锁定目标、问题与边界

**目标**：明确本次调研需要回答什么，而不是先决定扫描什么。

**执行步骤**：

1. 从用户请求、Vision 或上游文档中提取调研目的。
2. 将目的改写为可回答的产品问题和技术架构问题。
3. 锁定唯一调研主体及其官方资料入口。
4. 明确不包含源码审计、竞品比较、集成实施和性能 benchmark。
5. 确认证据窗口，包括调研日期、目标版本、分支或 Release。
6. 根据实际问题裁剪后续步骤；不得为了填满模板而扩大范围。

**交付内容**：

- 调研目标
- 核心问题
- 覆盖范围
- 排除边界
- 证据窗口

### 步骤 2：建立产品全貌

**目标**：先回答产品是什么、为谁解决什么问题、如何被使用。

**执行步骤**：

1. 读取官方首页、README、产品文档和入门流程。
2. 提炼产品定位和目标用户，不直接复述宣传文案。
3. 用用户视角描述一条端到端核心流程。
4. 识别主要功能域及其边界。
5. 区分当前可用能力、实验性能力、规划能力和已废弃能力。

**交付内容**：

- 一句话产品定位
- 目标用户与使用场景
- 核心流程
- 功能地图与边界

### 步骤 3：判断维护状态、版本演进、生态与反馈

**目标**：判断产品当前是否活跃、如何演进，以及公开使用反馈反映了什么。

**执行步骤**：

1. 检查最新 Release、Changelog、提交或官方公告的时间。
2. 识别最近几个关键版本带来的方向性变化，不穷举所有版本。
3. 查看官方集成、插件、SDK、扩展点和社区入口。
4. 抽样查看近期 Issue、Discussion 和公开反馈，归纳重复出现的主题。
5. 区分官方承诺、已发布能力和用户期望。

**边界**：

- Star、Fork、Issue 数只能描述公开快照，不直接等同产品质量或采用率。
- 单个 Issue 或评论不能代表普遍反馈。
- 不将其他产品引入本步骤进行比较。

**交付内容**：

- 维护状态判断
- 关键版本演进
- 生态入口
- 反馈主题及其证据边界

### 步骤 4：建立技术架构全貌

**目标**：先形成系统级架构模型，再决定哪些技术问题需要深入验证。

**执行步骤**：

1. 从官方架构文档、部署文档、仓库顶层结构和运行入口识别系统形态。
2. 列出少量主要组件，说明各自职责、运行位置和边界。
3. 区分桌面端、客户端、本地服务、中心服务、外部服务和数据存储等角色。
4. 画出或文字描述组件之间的主要调用与数据流。
5. 记录当前模型中的假设和未决点。

**禁止事项**：

- 不从 schema、路由目录或锁实现开始分析。
- 不按文件树顺序逐项介绍模块。
- 不因仓库中存在某个目录就推断其运行时地位。

**交付内容**：

- 运行形态
- 系统边界
- 主要组件与职责
- 组件关系或部署拓扑
- 初步假设与未决点

### 步骤 5：梳理核心技术链路

**目标**：通过一至三条关键链路解释系统实际上如何协作。

**执行步骤**：

1. 从产品核心流程中选择最能解释系统的关键场景。
2. 描述触发入口、主要组件、状态变化、数据去向和结果反馈。
3. 标出跨进程、跨网络或外部服务边界。
4. 识别影响可靠性、安全性或部署的关键约束。
5. 只记录与核心链路直接相关的技术细节。

**交付内容**：

- 核心链路说明
- 状态和数据流向
- 关键边界与约束

### 步骤 6：按问题核验技术架构

**目标**：在已有系统模型和核心链路基础上，回答六类技术架构问题。

#### 运行形态

- 产品以桌面应用、CLI、本地服务、中心服务、容器或组合形态运行。
- 各进程或服务分别部署在哪里，彼此是否可独立运行。

#### 主要依赖

- 只记录影响安装、运行、部署或关键能力的依赖。
- 不输出完整依赖树，不把开发依赖与运行时硬依赖混为一谈。

#### 接口形态

- 说明系统边界上存在的接口类型及用途，如 CLI、HTTP、WebSocket、SDK 或进程间调用。
- 不穷举端点、handler 或命令注册项。

#### 持久化方式

- 说明主要状态存放在哪里、由谁拥有，以及本地、外置或云端形态。
- 不默认扫描全部 schema 或枚举所有数据表。

#### 通信方式

- 说明主要组件如何交换命令、事件和状态，以及同步、异步、轮询或长连接等总体模式。
- 不默认检查每一种心跳、锁、重试、退避或幂等实现。

#### 部署形态

- 说明官方支持的部署方式、平台、必要依赖、权限和网络边界。
- 区分开发运行、源码构建、正式部署和终端用户安装。
- 桌面应用存在不等同于完全离线或不依赖后端，应依据官方运行模型判断。
- **双平台（核心调研焦点）**：必须分别详细说明 Windows 和 macOS 工作机上的安装方式、运行入口、依赖、权限、网络要求和卸载方式；Linux 不能替代任一工作机平台。
- **主体位置**：必须明确主体功能运行在 PC 本地、云端还是混合环境；若主体功能依赖云端，应完成云端调研并将其标记为 Local 优先选型缺陷。
- **云端形态**：存在云端组件时，必须说明其职责、组件、依赖、接口、持久化、通信、部署或托管方式，以及数据、权限和网络边界。

**交付内容**：

- 六类技术架构结论
- 每项结论的证据来源与置信边界
- 仍需运行验证的事项

### 步骤 7：定点验证关键结论

**目标**：只补齐会影响核心结论的证据缺口。

**执行步骤**：

1. 列出尚未被官方资料充分回答的关键问题。
2. 优先补充官方文档、Release、配置样例和部署清单。
3. 仍无法回答时，才定位与问题直接相关的入口文件或关键实现。
4. 为每次源码读取记录待验证问题和得到的答案。
5. 达到停止条件后立即停止，不展开相邻实现。

**停止条件**：

- 已有两个相互一致的直接证据；或
- 已有一个权威直接证据，且不存在明显冲突；或
- 继续下钻不会改变产品或架构层结论；或
- 只能通过运行验证才能继续，应转为未决。

**禁止事项**：

- 不进行“顺便看看”的仓库扫描。
- 不为确认一个接口而枚举整个路由层。
- 不为确认持久化形态而盘点全部 schema。
- 不为确认通信模式而审计所有锁、队列、心跳和重试代码。

### 步骤 8：整合交付

**目标**：形成一份可独立阅读、结论优先的调研报告。

**执行步骤**：

1. 先写核心结论，再补充支撑内容。
2. 检查产品结论和技术架构结论是否回答了步骤 1 的问题。
3. 删除没有服务于核心问题的细节和数量盘点。
4. 标注事实、推导、反馈样本和未决项。
5. 检查全文未包含竞品比较或源码审计内容。
6. 整合或删除临时过程记录。

**交付内容**：

- 单一整合文档
- 未决项与后续验证建议

## 常见陷阱

### 1. 从细节开始

- **错误**：先扫描数据库、路由、锁和队列，再尝试归纳系统架构。
- **正确**：先建立产品全貌、系统边界和核心链路，只针对关键问题下钻。

### 2. 把资料收集当成结论

- **错误**：用文件数、端点数、配置键数或依赖数量替代架构解释。
- **正确**：说明这些元素在系统中的职责、关系以及对用户或部署的影响。

### 3. 把技术架构调研做成源码审计

- **错误**：逐文件检查实现完整性、代码质量、并发安全或异常分支。
- **正确**：源码只用于确认会影响整体架构结论的具体问题。

### 4. 概念混淆

- **错误**：把开发模式当作生产部署，把容器镜像当作原生应用，把桌面壳当作完全离线应用。
- **正确**：分别说明开发、构建、部署、运行和连接依赖。

### 5. 证据扩大

- **错误**：从“未发现”推导“已证明不存在”，从单个 Issue 推导普遍反馈，从样例版本推导最低支持版本。
- **正确**：使用“当前证据未发现”“样本中出现”“官方未说明”等有边界的表述。

### 6. 擅自加入竞品

- **错误**：为了说明优劣而主动引入相似产品或选型矩阵。
- **正确**：只解释当前调研主体；竞品比较必须采用独立任务和流程。

## 检查清单

### 开始调研前

- [ ] 已明确产品问题和技术架构问题
- [ ] 已锁定唯一调研主体
- [ ] 已声明不做源码审计、竞品比较和遥测调研
- [ ] 已确认证据窗口
- [ ] 已确认 PC 同时指 Windows 和 macOS，且两个平台均须独立调研
- [ ] 已确认 Local 优先是选型标准，不是停止云端调研的条件

### 建立全貌后

- [ ] 已说明产品定位、目标用户、核心流程和功能边界
- [ ] 已形成系统边界、主要组件和运行形态
- [ ] 已选择一至三条核心链路
- [ ] 尚未进行无问题驱动的底层扫描

### 技术核验时

- [ ] 每次下钻都有明确待验证问题
- [ ] 只记录影响架构结论的主要依赖、接口、持久化、通信和部署信息
- [ ] 达到停止条件后已停止继续展开
- [ ] 已区分直接事实、架构推导、社区反馈和未决项

### 整合交付前

- [ ] 报告直接回答了最初的核心问题
- [ ] 已删除文件、端点、表、配置和依赖的无关盘点
- [ ] 未包含源码审计内容
- [ ] 未包含竞品比较或选型矩阵
- [ ] 未包含遥测、监控或运营数据采集内容
- [ ] 已分别详细说明 Windows 和 macOS 工作机安装方式
- [ ] 已明确主体功能位于本地、云端还是混合环境，并给出 Local 优先适配判断
- [ ] 存在云端组件时，已完成云端职责、架构、依赖、接口、数据和部署形态调研
- [ ] 云端承担主体能力或本地能力不完整时，已明确报告选型缺陷
- [ ] 已明确维护状态、版本演进和反馈样本边界
- [ ] 已整合或清理临时过程记录

## 接手指南

### 新 Agent 接手时

1. 阅读现有调研目标、核心问题和排除边界。
2. 确认证据窗口是否仍然有效。
3. 先检查产品全貌和系统模型是否已经形成。
4. 从未决问题继续，不重复进行底层扫描。

### 人工接手时

1. 查看交付结论和未决项。
2. 检查架构推导是否需要运行验证。
3. 记录裁决结果、验证方式和责任 owner。
