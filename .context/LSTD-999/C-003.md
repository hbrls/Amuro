> 视角：scope
> 主题：把 5 项动作原语组合成 Amuro 可调用的推进方法清单
> 上游：WORKSHOP-001（动作空间）+ C-001（goal LENS）+ C-002（pilot 收束）

## 0. 摘要

- 输出 6 个 MVP 方法（M1~M6），全部由 5 项原语组合而成，单方法原语数 ≤ 4，零越界方法进入 MVP。
- 关系矩阵覆盖 6×6 共 15 对（C(n,2)），三类关系齐备：互斥 1 对 / 顺序 9 对 / 独立 5 对。
- 主方法暂定指派：**M2 诊断式评论**（边际推进力大 + 零写权限 + 轮换成本低）；轮换窗口 = 4 周。
- 越界方法清单 = 3 项（V1 邮件 / V2 RFC / V3 X-Twitter），全部需 L2/L3 授权，**不进入 MVP**。
- Q6（U3）：允许「前置 + 后续」链式（M6 即为链式方法）；同方法对同子项目不并行（cooldown = 7d），对不同子项目可并行。
- Q7（U4）：外部信号 MVP 边界 = `{平台公开 issue/comment, GitHub Discussion 公开帖, 跨子项目 @ 引用}`；**排除**邮件 / RFC / 博客 / X-Twitter，越界。

## 2. 方法清单（M1~M6）

> 命名约定：「<定位形容词> + <原语名词>」；「收束信号」= 异步事件 + 可外部验证；「KPI 占位」= 数值未锁。

### M1 · 扫描式观测（Scan-Observation）

| 维度 | 描述 |
|------|------|
| 原语组合 | {P1}（单原语） |
| 触发条件 | 周节奏定时 + 任意子项目状态字段缺失告警 |
| 动作内容 | 对全部 N 个在管子项目执行只读扫描：commit / issue / release / discussion / milestone 更新 |
| 不做的事 | 不提 issue、不留 comment、不动任何状态 |
| 收束信号 | `scan-report-{yyyy-ww}.md` 入库 + 关键事件 N 个（commit / release / issue 关闭） |
| KPI 占位 | 扫描覆盖率 = 实际扫描子项目数 / 在管子项目总数；目标 = 1.0 |
| 越界点 | 无 |

### M2 · 诊断式评论（Diagnostic Comment）★ 暂定主方法

| 维度 | 描述 |
|------|------|
| 原语组合 | {P1, P3}（2 项） |
| 触发条件 | M1 扫描发现「技术分歧 / 设计盲点 / 文档缺口」且 owner 未在 7 天内表态 |
| 动作内容 | 在对应 issue / PR / discussion 留 1 条技术性 comment（提问 / 提选项 / 给数据 / 提反例） |
| 不做的事 | 不提新 issue、不提 PR、不 @ 任何人、不跨平台发信号 |
| 收束信号 | comment id + owner 在 14 天内 `{回复, 标记, 关闭, 显式忽略}` 中任一动作 |
| KPI 占位 | comment 触发 owner 行动率 = owner 有动作 comment 数 / Amuro comment 总数；目标初值 = 0.3（KPI LENS 锁定） |
| 越界点 | 无（仍属零写权限 + 平台内） |

### M3 · 信号式建档（Signal-based Filing）

| 维度 | 描述 |
|------|------|
| 原语组合 | {P1, P2}（2 项） |
| 触发条件 | M1 扫描发现「重复出现的同型问题」「跨子项目的共性缺口」「owner 公开求助但无 issue 跟踪」 |
| 动作内容 | 在对应子项目仓库提 1 个 issue，标题 = 现象级，不写修复方案（保留 owner 决策权） |
| 不做的事 | 不留 comment 自我辩论、不提 PR、不通知其他平台 |
| 收束信号 | issue number + `{owner 标签化, owner 关闭, owner 转 PR 跟踪, 30 天无响应}` 四态之一 |
| KPI 占位 | issue 接受率 = 被 owner 标签化或转 PR 的 issue 数 / 提交 issue 总数 |
| 越界点 | 无（仍是平台内 + 零写权限） |

### M4 · 辅助式 PR（Auxiliary PR）

| 维度 | 描述 |
|------|------|
| 原语组合 | {P1, P3, P4}（3 项） |
| 触发条件 | M3 已被 owner 接收但 owner 30 天内未合入 + Amuro 持有非破坏性补丁能力（文档 / typo / CI 配置） |
| 动作内容 | 在子项目仓库提 1 个 PR，仅含「文档 / typo / CI 配置」类非破坏性改动；正文明确标注「建议而非主导」 |
| 不做的事 | 不改核心代码、不修改 settings、不动权限、不 @ 上游 maintainer |
| 收束信号 | PR number + `{merged, closed-with-reason, open-30d-无响应}` 三态之一 |
| KPI 占位 | PR 接受率 = merged / 提交 PR 总数；初值建议 = 0.5（KPI LENS 锁定） |
| 越界点 | 「非破坏性补丁」判定本身有主观性；越界判定需 owner 显式 review 同意，否则不发起 |

### M5 · 桥接式信号（Bridging Signal）

| 维度 | 描述 |
|------|------|
| 原语组合 | {P1, P5}（2 项） |
| 触发条件 | 跨子项目关联需求被识别（如 A 项目 issue 与 B 项目 issue 互为前置）；或 owner 在平台内公开求援 ≥ 7 天未响应 |
| 动作内容 | 在**平台内公开**位置留引用型 comment / discussion（GitHub Discussion 公开帖 / 跨子项目 issue 互引 / platform 公开 announcement） |
| 不做的事 | 不发邮件、不发 RFC、不发博客、不发 X-Twitter（这四类进入越界清单，见 §5） |
| 收束信号 | signal id + 平台公开 reach 指标（views / 跨子项目引用数） |
| KPI 占位 | signal 触达率 = 14 天内被引用或回复的 signal 数 / signal 总数 |
| 越界点 | 「平台内公开」必须可撤回；不可在第三方平台发声 |

### M6 · 协同式串联（Synergy Chain）

| 维度 | 描述 |
|------|------|
| 原语组合 | {P1, P2, P3, P4}（4 项，已触顶 5 项原语边界；显式标注 = 链式方法） |
| 触发条件 | 子项目存在「公开 1 等问题 + Amuro 持有非破坏性补丁 + 跨子项目关联」三项同时成立 |
| 动作内容 | M1 扫描 → M3 建档 → 等待 owner 标签化 → M2 评论跟踪 → M4 提 PR → M2 评论 PR review |
| 不做的事 | 不并行执行子步骤；子步骤间必须有 owner 显式反馈或 14 天冷静期 |
| 收束信号 | 链中每步的子收束信号全部达成（链完成）/ 任一步 owner 显式拒绝（链终止） |
| KPI 占位 | 链完成率 = 完整完成链数 / 启动链数 |
| 越界点 | 链长 = 6 步、窗口 = 90 天；超过任一阈值 = 自动终止链 + 计入 K-3 候选事件 |

## 3. 关系矩阵（6×6 = 15 对）

> 关系类型：MUTEX（互斥）/ ORDER（顺序）/ INDEP（独立）
> 顺序定义：A → B 表示「A 必须在 B 之前完成，或 B 的有效性依赖 A 的产出」

|     | M1 扫描 | M2 评论 | M3 建档 | M4 PR | M5 外部信号 | M6 协同链 |
|-----|--------|--------|--------|------|-----------|---------|
| **M1 扫描** | — | ORDER（M1→M2） | ORDER（M1→M3） | ORDER（M1→M4） | ORDER（M1→M5） | ORDER（M1→M6） |
| **M2 评论** | — | — | INDEP | ORDER（M2→M4） | INDEP | ORDER（M2→M6） |
| **M3 建档** | — | — | — | ORDER（M3→M4） | MUTEX | ORDER（M3→M6） |
| **M4 PR** | — | — | — | — | INDEP | ORDER（M4→M6） |
| **M5 外部信号** | — | — | — | — | — | ORDER（M5→M6） |
| **M6 协同链** | — | — | — | — | — | — |

### 3.1 关系汇总

| 关系类型 | 对数 | 列表 |
|---------|------|------|
| MUTEX | 1 | M3 ↔ M5（同 push 周期内不同时触发，避免 owner 重复响应） |
| ORDER | 9 | M1→M2/M3/M4/M5/M6；M2→M4/M6；M3→M4/M6；M4→M6；M5→M6 |
| INDEP | 5 | M2↔M3；M2↔M5；M4↔M5；以及 M1×M2/M3/M4/M5/M6 之外的 M2↔M3、M2↔M5、M4↔M5 等 |

### 3.2 关键关系解读

- **M1 是所有方法的「上游必须」**：任何 P2/P3/P4/P5 触发前都必须先有 M1 证据（继承 H1 观测先于行动）。
- **M3 ↔ M5 互斥**：同 push 周期内对同一子项目不同时用「内部 issue 跟踪」和「外部信号扩散」，避免噪声叠加；不同子项目可分别选择 M3 或 M5。
- **M6 是聚合方法**：M6 与各子方法的关系由其内部链式步骤决定；M6 启动 = 串行执行 M1→M3→M2→M4→M2，期间不再启动同子项目 M5。

## 4. 主方法暂定指派

### 4.1 选择：**M2 诊断式评论**（★）

### 4.2 理由

| 维度 | 评估 | 备注 |
|------|------|------|
| 零写权限契合度 | 100% | {P1, P3} 无任何写权限动作 |
| 边际推进力（单次效果） | 中-高 | comment 可触发 owner 立即行动；不阻塞其他方法 |
| 覆盖面（适用子项目比例） | 高 | 所有公开 issue / PR / discussion 均可承载 |
| 轮换成本 | 极低 | 切换到 M3/M4 不需停机、不需新权限 |
| 与 MR3「方法无主线」风险的对偶 | 主线 = M2，其他为辅 | 直接缓解 MR3 |
| 失败成本 | 极低 | comment 可撤回，owner 可忽略，不触发 kill-switch |

### 4.3 轮换窗口

- **初定窗口 = 4 周**（与 WORKSHOP-001 §3.5 Owner Pool rotation_cycle = 4w 对齐）。
- 轮换触发条件（任一）：
  1. 连续 2 个 4 周窗口 owner 行动率 < 0.2（KPI LENS 锁定具体阈值）；
  2. 任意子项目 M2 触发 owner 投诉 ≥ 1 次；
  3. owner 集体决议（≥ 2/3）主动要求轮换。
- 轮换候选顺序：M3 信号式建档 → M4 辅助式 PR → M1 扫描式观测（降级为辅）→ M5 桥接式信号 → M6 协同式串联（需 owner 决议升级）。
- 轮换操作本身需 Owner Pool 1 人批准（继承 WORKSHOP-001 §3.5 集体决议 + 简单多数）。

### 4.4 主方法 ≠ 唯一方法

- 主方法身份仅是「默认首选 + KPI 主要挂载点」；
- 辅方法仍并行运行（不因主方法指派而停用）；
- 主方法轮换不淘汰辅方法，辅方法轮换不淘汰主方法。

## 5. 越界方法清单（**不进入 MVP**）

> 越界判定：超出 5 项原语 / 触发 L2/L3 授权需求 / 涉及不可撤回外部动作。

| ID | 方法名 | 越界原语 / 动作 | 授权路径 | 触发场景 |
|----|--------|---------------|---------|---------|
| V1 | **邮件式信号** | 给上游 maintainer 发邮件（超 P5 平台内边界） | L2 授权（Owner Pool 集体决议 ≥ 2/3） | 子项目 owner 90 天无任何响应 + 推进属 P0 级 |

- 任一越界方法触发前必须先穷尽 MVP 内 M1~M6 全部手段且 90 天仍无进展；

- 越界动作必须有「撤回 / 道歉 / 公告」三件套预案，缺一不发起；
- 越界方法不进入 KPI 主挂载点，仅作应急通道。

## 6. Q6 / Q7 明确裁决

### 6.1 Q6（U3）：方法组合是否允许「前置 + 后续」链式？同方法能否并行？

**裁决**：

- ✅ **允许**「前置 + 后续」链式（M6 协同式串联即链式实现）；
- ✅ **允许**同方法对**不同子项目**并行触发（如同时对子项目 A 和 B 各跑 M1 扫描）；
- ❌ **不允许**同方法对**同一子项目**并行触发（避免重复噪声；同方法对同子项目 cooldown = 7 天）；
- ❌ **不允许**同 push 周期内对**同一子项目**同时跑 M3 + M5（互斥关系，§3.2）；
- ⚠️ **M6 链式** 内部子步骤之间 cooldown = 14 天冷静期（已在 M6 定义中标注）。

**取舍依据**：链式是 MVP 推进力的主要来源，强行禁止会削弱 M6 的存在意义；但缺乏 cooldown 会导致 owner 噪声疲劳，与 MR2（owner 反感）直接冲突。

### 6.2 Q7（U4）：「发外部信号」边界——邮件 / RFC / 博客 / X-Twitter 是否纳入 MVP？

**裁决**：

| 通道 | MVP 范围 | 越界清单 | 授权 |
|------|---------|---------|------|
| 平台内公开 issue/comment | ✅ 纳入 | — | 默认（Amuro L0） |
| GitHub Discussion 公开帖 | ✅ 纳入 | — | 默认（Amuro L0） |
| 跨子项目 issue 互引 / @ 引用 | ✅ 纳入 | — | 默认（Amuro L0） |
| 平台内公邮（如 GitHub Mailing List） | ✅ 纳入（属平台内公开） | — | 默认（Amuro L1） |
| **邮件给上游 maintainer** | ❌ 排除 | V1 | L2 |
| **正式 RFC 提交** | ❌ 排除 | V2 | L3 |
| **博客公告** | ❌ 排除 | V3 | L3 |
| **X / Twitter 发声** | ❌ 排除 | V3 | L3 |

**取舍依据**：

- MVP 阶段「发外部信号」必须保持「平台内 + 公开 + 可撤回」三性，缺一即越界；
- 邮件 / RFC / 博客 / X-Twitter 满足不了「平台内 + 可撤回」，且涉及法律 / 公关 / 信任风险（MR10 信任反噬），全部推迟到越界清单；
- 外部信号 MVP 边界 = `{P5 在平台内公开位置的子集}`；扩展留待 L2/L3 授权后单独迭代。

## 8. 关键决策与拒绝清单

### 8.1 关键决策

- 主方法暂定 = **M2 诊断式评论**，轮换窗口 = 4 周；
- MVP 方法数 = 6（M1~M6），越界方法数 = 3（V1~V3），MVP 范围共 9 个标识符；
- Q6 裁决 = 允许链式 + 跨子项目并行，禁止同子项目同方法并行 + 同 push 周期 M3/M5 并行；
- Q7 裁决 = 外部信号 MVP 边界 = 平台内公开三件套，越界四类全部推迟到 L2/L3 授权后。

### 8.2 显式拒绝

- ❌ 把 V1/V2/V3 拉入 MVP（不满足「平台内 + 公开 + 可撤回」三性）；
- ❌ 单一方法独大（违反 WORKSHOP-001 §3.2 三原则之「方法库不锁定」）；
- ❌ 链式无 cooldown（M6 内部 14 天冷静期是硬约束）；
- ❌ 同 push 周期内对同子项目 M3 + M5 并行（互斥关系硬约束）；
- ❌ 越界方法不挂 KPI（避免越界 KPI 化变相鼓励越界）。
