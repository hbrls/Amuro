## 1. 本轮目标（继承 `.context/LSTD-1234/Index.md`）

### 1.1 总项目目标（不变）

> Amuro 是一组并行的真实子项目（LLM wiki、设备指纹算法、flowable→cf workflow 迁移等）。本仓库作为**总项目**：
>
> > **管理所有子项目的进展，并主动推动它们继续前进。用尽一切方法去推进项目，推进所有项目。**

## 3. 方法库清单（MVP = 6 个方法）

> 命名约定：「<定位形容词> + <原语名词>」；收束信号 = 异步事件 + 可外部验证；KPI 占位 = 数值未锁。

### 3.1 M1 · 扫描式观测（Scan-Observation）

| 维度 | 描述 |
|------|------|
| 原语组合 | {P1}（单原语） |
| 触发条件 | 周节奏定时 + 任意子项目状态字段缺失告警 |
| 动作内容 | 对全部 N 个在管子项目执行只读扫描：commit / issue / release / discussion / milestone 更新 |
| 不做的事 | 不提 issue、不留 comment、不动任何状态 |
| 收束信号 | `scan-report-{yyyy-ww}.md` 入库 + 关键事件 N 个 |
| KPI 占位 | 扫描覆盖率 = 实际扫描子项目数 / 在管子项目总数；目标 = 1.0 |
| 越界点 | 无 |

### 3.2 M2 · 诊断式评论（Diagnostic Comment）★ 暂定主方法

| 维度 | 描述 |
|------|------|
| 原语组合 | {P1, P3}（2 项） |
| 触发条件 | M1 扫描发现"技术分歧 / 设计盲点 / 文档缺口"且 owner 未在 7 天内表态 |
| 动作内容 | 在对应 issue / PR / discussion 留 1 条技术性 comment（提问 / 提选项 / 给数据 / 提反例） |
| 不做的事 | 不提新 issue、不提 PR、不 @ 任何人、不跨平台发信号 |
| 收束信号 | comment id + owner 在 14 天内 `{回复, 标记, 关闭, 显式忽略}` 中任一动作 |
| KPI 占位 | comment 触发 owner 行动率 = owner 有动作 comment 数 / Amuro comment 总数；目标初值 = 0.3 |
| 越界点 | 无（仍属零写权限 + 平台内） |

### 3.3 M3 · 信号式建档（Signal-based Filing）

| 维度 | 描述 |
|------|------|
| 原语组合 | {P1, P2}（2 项） |
| 触发条件 | M1 扫描发现"重复出现的同型问题" / "跨子项目的共性缺口" / "owner 公开求助但无 issue 跟踪" |
| 动作内容 | 在对应子项目仓库提 1 个 issue，标题 = 现象级，不写修复方案（保留 owner 决策权） |
| 不做的事 | 不留 comment 自我辩论、不提 PR、不通知其他平台 |
| 收束信号 | issue number + `{owner 标签化, owner 关闭, owner 转 PR 跟踪, 30 天无响应}` 四态之一 |
| KPI 占位 | issue 接受率 = 被 owner 标签化或转 PR 的 issue 数 / 提交 issue 总数 |
| 越界点 | 无（仍是平台内 + 零写权限） |

### 3.4 M4 · 辅助式 PR（Auxiliary PR）

| 维度 | 描述 |
|------|------|
| 原语组合 | {P1, P3, P4}（3 项） |
| 触发条件 | M3 已被 owner 接收但 owner 30 天内未合入 + Amuro 持有非破坏性补丁能力（文档 / typo / CI 配置） |
| 动作内容 | 在子项目仓库提 1 个 PR，仅含"文档 / typo / CI 配置"类非破坏性改动；正文明确标注"建议而非主导" |
| 不做的事 | 不改核心代码、不修改 settings、不动权限、不 @ 上游 maintainer |
| 收束信号 | PR number + `{merged, closed-with-reason, open-30d-无响应}` 三态之一 |
| KPI 占位 | PR 接受率 = merged / 提交 PR 总数；初值建议 = 0.5 |
| 越界点 | "非破坏性补丁"判定本身有主观性；越界判定需 owner 显式 review 同意，否则不发起 |

### 3.5 M5 · 桥接式信号（Bridging Signal）

| 维度 | 描述 |
|------|------|
| 原语组合 | {P1, P5}（2 项） |
| 触发条件 | 跨子项目关联需求被识别（如 A 项目 issue 与 B 项目 issue 互为前置）；或 owner 在平台内公开求援 ≥ 7 天未响应 |
| 动作内容 | 在**平台内公开**位置留引用型 comment / discussion（GitHub Discussion 公开帖 / 跨子项目 issue 互引 / platform 公开 announcement） |
| 不做的事 | 不发邮件、不发 RFC、不发博客、不发 X-Twitter（这四类进入越界清单，见 §5） |
| 收束信号 | signal id + 平台公开 reach 指标（views / 跨子项目引用数） |
| KPI 占位 | signal 触达率 = 14 天内被引用或回复的 signal 数 / signal 总数 |
| 越界点 | "平台内公开"必须可撤回；不可在第三方平台发声 |

### 3.6 M6 · 协同式串联（Synergy Chain）

| 维度 | 描述 |
|------|------|
| 原语组合 | {P1, P2, P3, P4}（4 项，已触顶 5 项原语边界；显式标注 = 链式方法） |
| 触发条件 | 子项目存在"公开 1 等问题 + Amuro 持有非破坏性补丁 + 跨子项目关联"三项同时成立 |
| 动作内容 | M1 扫描 → M3 建档 → 等待 owner 标签化 → M2 评论跟踪 → M4 提 PR → M2 评论 PR review |
| 不做的事 | 不并行执行子步骤；子步骤间必须有 owner 显式反馈或 14 天冷静期 |
| 收束信号 | 链中每步的子收束信号全部达成（链完成）/ 任一步 owner 显式拒绝（链终止） |
| KPI 占位 | 链完成率 = 完整完成链数 / 启动链数 |
| 越界点 | 链长 = 6 步、窗口 = 90 天；超过任一阈值 = 自动终止链 + 计入 K-3 候选事件 |

### 4.1 关系汇总

| 关系类型 | 对数 | 列表 |
|---------|------|------|
| MUTEX | 1 | M3 ↔ M5（同 push 周期内不同时触发，避免 owner 重复响应） |
| ORDER | 9 | M1→M2/M3/M4/M5/M6；M2→M4/M6；M3→M4/M6；M4→M6；M5→M6 |
| INDEP | 5 | M2↔M3；M2↔M5；M4↔M5；以及其他成对独立标注 |

### 4.2 关键关系解读

- **M1 是所有方法的"上游必须"**：任何 P2/P3/P4/P5 触发前都必须先有 M1 证据（继承 H1 观测先于行动）。
- **M3 ↔ M5 互斥**：同 push 周期内对同一子项目不同时用"内部 issue 跟踪"和"外部信号扩散"，避免噪声叠加；不同子项目可分别选择 M3 或 M5。
- **M6 是聚合方法**：M6 启动 = 串行执行 M1→M3→M2→M4→M2，期间不再启动同子项目 M5。

## 6. 主方法暂定指派

### 6.1 选择：**M2 诊断式评论**（★）

### 6.2 理由

| 维度 | 评估 | 备注 |
|------|------|------|
| 零写权限契合度 | 100% | {P1, P3} 无任何写权限动作 |
| 边际推进力（单次效果） | 中-高 | comment 可触发 owner 立即行动；不阻塞其他方法 |
| 覆盖面（适用子项目比例） | 高 | 所有公开 issue / PR / discussion 均可承载 |
| 轮换成本 | 极低 | 切换到 M3/M4 不需停机、不需新权限 |
| 与 MR3「方法无主线」风险的对偶 | 主线 = M2，其他为辅 | 直接缓解 MR3 |
| 失败成本 | 极低 | comment 可撤回，owner 可忽略，不触发 kill-switch |

### 6.3 轮换窗口

- **初定窗口 = 4 周**（与 WORKSHOP-001 §3.5 Owner Pool rotation_cycle = 4w 对齐）。
- 轮换触发条件（任一）：
  1. 连续 2 个 4 周窗口 owner 行动率 < 0.2（KPI LENS 锁定具体阈值）；
  2. 任意子项目 M2 触发 owner 投诉 ≥ 1 次；
  3. owner 集体决议（≥ 2/3）主动要求轮换。
- 轮换候选顺序：M3 → M4 → M1 → M5 → M6（需 owner 决议升级）。
- 轮换操作本身需 Owner Pool 1 人批准（继承 WORKSHOP-001 §3.5 集体决议 + 简单多数）。

### 6.4 主方法 ≠ 唯一方法

- 主方法身份仅是"默认首选 + KPI 主要挂载点"；
- 辅方法仍并行运行（不因主方法指派而停用）；
- 主方法轮换不淘汰辅方法，辅方法轮换不淘汰主方法。

## 7. 关键裁决

### 7.1 Q6（U3）：方法组合是否允许"前置 + 后续"链式？同方法能否并行？

| 裁决 | 内容 |
|------|------|
| ✅ 允许 | "前置 + 后续"链式（M6 协同式串联即链式实现） |
| ✅ 允许 | 同方法对**不同子项目**并行触发 |
| ❌ 不允许 | 同方法对**同一子项目**并行触发（同方法对同子项目 cooldown = 7 天） |
| ❌ 不允许 | 同 push 周期内对**同一子项目**同时跑 M3 + M5（互斥关系） |
| ⚠️ M6 链式 | 内部子步骤之间 cooldown = 14 天冷静期 |

### 7.2 Q7（U4）：「发外部信号」边界——邮件 / RFC / 博客 / X-Twitter 是否纳入 MVP？

| 通道 | MVP 范围 | 越界清单 | 授权 |
|------|---------|---------|------|
| 平台内公开 issue/comment | ✅ 纳入 | — | 默认（Amuro L0） |
| GitHub Discussion 公开帖 | ✅ 纳入 | — | 默认（Amuro L0） |
| 跨子项目 issue 互引 / @ 引用 | ✅ 纳入 | — | 默认（Amuro L0） |
| 平台内公邮（如 GitHub Mailing List） | ✅ 纳入（属平台内公开） | — | 默认（Amuro L1） |
