# C-001 · Goal Lens 分析：LLM 知识库机制

> 视角：goal lens (CEO/founder-mode plan review)
> 主题：设计 LLM 知识库机制
> 注：`.context/current-task.md` 和 `.context/current-task-metadata.yaml` 均不存在，本轮分析基于"设计 LLM 知识库机制"这一主题从第一性原理出发。

---

## 一、这个目标真正要解决什么问题

从 goal lens 的"前提挑战"（Premise Challenge）视角审视：

**表面问题**：LLM / Agent 需要一套"知识库"来存储和检索信息。

**更深处的问题（逐层剥离）**：

1. **LLM 的上下文窗口是唯一可用的"记忆"，但它有三个结构性问题**：
   - **容量上限**：即使是 200K token 的窗口，对中等规模项目也迅速不够用。
   - **无持久性**：会话结束，所有已推理的内容全部丢弃。下次从头开始。
   - **检索效率**：把所有可能相关的信息都塞进 prompt 是最简单的解法，也是损耗最快的——token 成本、延迟、注意力稀释三者一起恶化。

2. **当前 Amuro 项目中，Agent 的知识沉淀方式是什么？**
   - `.context/` 文件化任务状态（TASK-*.md、C-*.md）
   - `.agents/` 下的 skills、lens、workflows
   - 但这些是**静态定义**，不是在运行时被"学到"的知识。
   - 也就是说，Agent 每次执行都像第一次见到这个项目。

3. **如果什么都不做会怎样？**
   - Agent 在长周期项目中会越来越"健忘"。
   - 每次任务都需要重复加载大量上下文，成本线性增长。
   - 高级使用模式（像 gstack 的 learning 系统那样跨会话积累经验）不可实现。

**因此，真正要解决的问题是：**

> 如何让 Amuro Agent 在跨会话、跨任务的生命周期中，积累、组织和检索对执行任务有实际价值的结构化知识，而不是每次都从零开始把世界塞进 prompt。

这不是一个"要不要做 RAG"的问题，而是一个**Agent 如何拥有"工作记忆+长期记忆"双层架构**的问题。

---

## 二、当前最关键、最先需要拆清的问题

从 goal lens 的焦点原则（Focus as Subtraction）出发：在动手设计之前，有且仅有一个问题必须先回答清楚——

### **这个知识库里存的是什么"知识"？谁来写、谁在用？**

这个问题如果不拆清，后面所有的技术选型（向量数据库 / 全文检索 / graph RAG / 动态摘要……）都是在为空壳做设计。

具体需要拆清的三个子维度：

| 维度 | 需要明确的边界 |
|---|---|
| **知识类型** | 是代码库静态知识（架构、模块关系、接口约定）？是 Agent 运行经验（上次这个模式失败了、那个模式可用）？是项目元知识（团队偏好、工程规范）？还是以上全部？ |
| **写入者** | 知识是由 human 手动编排（curated knowledge）？由 Agent 在执行后自动沉淀（learned knowledge）？还是两者都有？如果是自动沉淀，什么触发写入——任务成功？错误？用户反馈？ |
| **消费者和时机** | 知识在什么环节被检索——任务开始时（planning 阶段）、任务执行中（on-demand query）、还是事后分析时？消费者是 Agent 自身还是 human？ |

**为什么不先问"技术方案"？**

因为 goal lens 的核心本能之一是**反演（Inversion）**：不是先问"怎么做 Vector RAG"，而是先问"如果我们做出来一个很漂亮的 RAG 系统，但它存的内容实际没人用、或者写进去的东西 Agent 自己搜不到、或者每次只检索到一大堆不相关的噪音——那我们在解决哪个问题？"

**当前阶段判定**：这是一个 **peacetime（和平期）** 设计决策——面向长期积累能力做的一次基础设施投入。不是 wartime 紧急需求。因此值得花时间把"知识"的定义拆清楚再动手。

## 三、下一步讨论应该聚焦在哪里

要让本轮讨论形成"可执行、可交付"的结论，建议聚焦以下三个连续步骤：

### 第一步：给"知识"下操作性定义

不要停留在"知识库"这个抽象名词。接下来需要产出一个**有边界、可验证**的定义，例如：

```
知识类型 A：代码库结构知识
  - 来源：project 文件结构 + git log + 架构文档
  - 写入时机：项目首次索引 / 文件变更触发增量更新
  - 消费者：Agent 规划阶段（"这个改动应该改哪些文件"）
  - 检索模式：基于文件名/路径/模块名的结构查询

知识类型 B：任务经验知识
  - 来源：Agent 执行后自动复盘
  - 写入时机：任务完成后（成功 or 失败都记录）
  - 消费者：Agent 下一次同类任务时参考
  - 检索模式：语义相似度匹配 + 过滤
```

**输出物**：一份 `.context/knowledge-schema.md`，列出每种知识类型的完整五要素（类型、来源、写入时机、消费者、检索模式）。

### 第二步：最小可交付版本（MVP）的边界

从中挑出**一种知识类型 + 一个消费者场景**作为 MVP。例如：
- MVP = "代码库结构知识 → Agent 接到新任务时自动加载相关文件路径"
- 非 MVP = 所有其他类型、自动学习、混合检索

明确写出 MVP 定义的 yes/no 边界，确保后续可以做出来、可以验证"有没有用"。

### 第三步：定义"有用"的判断标准

做基础设施最容易出现的陷阱：花大量时间做出来一个机制，但没人能说清它到底有没有提升 Agent 执行质量。在 MVP 出来之前就需要定义：
- **对照基线**：不使用知识库时的任务执行效果（成功率？耗时？token 消耗？）
- **验证指标**：引入知识库后，哪个指标应该改善？改善到什么程度算"有用"？
- **退化警戒**：什么信号表示这套机制在变成噪音而非帮助？

---

## 小结

| 结论 | 内容 |
|---|---|
| 真实问题 | LLM 缺乏跨会话的持久记忆导致每次任务都从零开始，需要"工作记忆+长期记忆"双层架构 |
| 最先拆清的问题 | 知识库里的"知识"到底是什么——类型、来源、写入时机、消费者、检索模式 |
| 下一步聚焦 | 1) 对知识做操作性分类 2) 切出 MVP 边界 3) 定义"有用"的判断标准 |

**不是"要不要做 RAG"，而是"Agent 到底需要记住什么才能在下一次做得更好"。**
