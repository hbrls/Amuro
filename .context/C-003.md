## 一、LLM 产出回写协议

### 1.1 追单循环产出清单

根据 VISION.md 定义的追单循环：

```
捕获新信号 → 蒸馏客户上下文 → 更新机会假设 → 识别缺失信息
→ 生成下一步动作 → 起草客户特定消息 → 模拟可能反应 → 更新信心和阶段 → 重复
```

LLM 每次循环产出以下五类内容：

| # | 产出类型 | 性质 | 持久化判断 |
|---|---------|------|-----------|
| A | **蒸馏结论** (client distillation) | 对客户上下文、痛点、动机的结构化理解增量 | **必须持久化**。这是整个知识库的核心积累，不持久化等于每次从零蒸馏 |
| B | **信心评估** (confidence assessment) | 对当前 deal 推进概率的估值 + 方向判断 | **必须持久化**。需要追踪趋势（上行/下行/横盘），单点值无意义 |
| C | **异议地图更新** (objection map delta) | 新发现的异议、已有异议状态变更 | **必须持久化**。异议是 deal 推进的核心 blocker map |
| D | **下一步动作** (next action) | FUP 提议：目标对象、目的、消息草稿 | **持久化但需人确认**。消息不能自动发出 |
| E | **阶段变化** (stage transition) | 当前 lead 状态是否应变更及其理由 | **持久化但需人确认**。阶段是人的决策，LLM 提供 reasoning |

### 1.2 各产出的持久化位置与格式

| 产出 | 目标文件 | 位置 | 格式 | 写入方式 |
|------|---------|------|------|---------|
| A 蒸馏结论 | `analysis.md` | `# Client Distillation` | 自由文本为主，标签辅助 | 追加增量（delta），不覆盖历史 |
| B 信心评估 | `Index.md` | `## Confidence` + `## Confidence History` | 结构化数值 + 趋势标记 + 自然语言理由 | 覆盖当前值 + 追加历史行 |
| C 异议地图 | `analysis.md` | `# Objection Map` | 结构化列表（每条：异议、状态、最后更新） | 增量更新（upsert by objection key） |
| D 下一步动作 | `followups.md` | 新增 FUP-XXX 条目 | 现有 FUP 结构化格式 | 追加新条目，status = `proposed` |
| E 阶段变化 | `Index.md` + `analysis.md` | `## Current State` + `# Stage History` | 结构化字段 + 日志条目 | 提议 Index.md 变更 + 自动记入 analysis.md |

### 1.3 文件结构增量设计

基于现有 lead 文件结构，在不推翻重来的前提下做最小增量：


## 二、人机分工边界

### 2.1 分工原则

Amuro 是 KA 工作台——Agent 辅助人推进，而非替代人决策。分工边界基于一个核心判断：

> **LLM 可以自主写入"它自己推理的结果"（分析、评估、记录），但不能自主执行"触发外部动作的决策"（发消息、改变阶段、关闭 lead）。**

### 2.2 字段归属矩阵

| 字段/区域 | 人维护 | LLM 维护 | LLM 提议 + 人确认 | 理由 |
|-----------|:------:|:--------:|:----------------:|------|
| **Index.md** | | | | |
| Goal | ● | | | 机会的本质方向是人定义的 |
| Account | ● | | | 客户归属不可变更 |
| Current Objective | ● | ○ | ● | 阶段性目标应有人参与判断 |
| Exit Conditions | ● | | | **绝对不允 LLM 修改**——这是人的退出标准，LLM 改 = 失控 |
| Waiting On | ○ | | ● | LLM 可发现新的依赖项，人确认 |
| Required Context | ○ | | ● | LLM 可发现缺失信息，人确认 |
| Confidence Score | | ● | | LLM 推理结果，透明展示即可 |
| Confidence History | | ● | | 日志性数据，自动记录 |
| Stage History | | ● | | 日志性数据，自动记录 |
| **analysis.md** | | | | |
| Client Distillation | | ● | | LLM 的理解输出，人可随时纠正 |
| Stakeholder Map | ○ | ● | | LLM 构建为主，人修正为辅 |
| Opportunity Hypotheses | | ● | | LLM 推理，人可标记 inactive |
| Objection Map | | ● | | LLM 识别和维护异议 |
| Cycle Log | | ● | | 自动日志 |
| **followups.md** | | | | |
| FUP status (scheduled/ready_to_send) | ● | | | 决定消息是否发出，只能是人 |
| FUP status (proposed) | | ● | | LLM 提案的初始状态 |
| FUP status (sent/archived) | ● | | | 动作执行后的标记 |
| FUP.message (body) | | ● | | LLM 起草草稿 |
| FUP.purpose / target | | ● | | LLM 判断跟进方向和对象 |
| FUP.trigger (if no reply) | | ● | | LLM 建议自动跟进条件 |
| **Current State** (阶段字段) | | | ● | LLM 检测条件满足，人确认变更 |

- ● = 主要维护者（允许另一方只读或建议）
- ○ = 次要贡献者（可提议但不可直接写）

### 2.3 边界设计原则

1. **Exit conditions 是最终原语**。如果 LLM 能改 exit conditions，就会在没有人类意图的情况下改变一个 lead 的终止定义。这是失控的起点。Exit conditions 在 Amuro 中应实现为"LLM 不可写区"。

2. **消息发送权 = 人的特权**。Amuro 产出消息草稿（LLM 强项），但把 `proposed → ready_to_send` 的状态转换留给人的手。这不需要复杂的技术方案——只需要在 followups.md 中约定 LLM 永远只写 `status: proposed`，不写其他状态。

3. **分析区是 LLM 的"工作笔记"**。analysis.md 是 LLM 对自己推理过程的外化记录，人可以随时阅改但不是主要维护者。这个区设计为"允许出错但透明"——错误的蒸馏不会造成外部影响，被纠正后下次循环会基于修正后的内容。

## 三、写入触发时机

### 3.1 时机决策框架

写入触发时机取决于产出物对时效性和完整性的要求差异：

| 触发时机 | 适用产出 | 不适用产出 |
|---------|---------|-----------|
| **每次交互结束** (immediate) | 蒸馏增量、信心更新、异议更新、cycle log | FUP（消息未确认前不应设为 ready） |
| **用户确认后** (gated) | FUP status 变更、消息草稿激活、阶段转换 | 纯分析性产出（滞后写入造成信息丢失） |
| **阶段变化时** (event-driven) | 阶段历史追加、重大假设更新 | 细粒度蒸馏（应落在每次交互） |

### 3.2 各产出具体触发时机

```
产出 A（蒸馏结论）    → 每次交互结束，自动追加增量到 analysis.md
                       理由：蒸馏是推论链的中间状态，推迟写入 = 丢失推理上下文

产出 B（信心评估）    → 每次交互结束，自动覆盖 Index.md 当前值 + 追加历史行
                       理由：信心趋势需要逐次记录，单点值无法做 timeline 分析

产出 C（异议地图）    → 每次交互结束，增量 upsert 到 analysis.md
                       理由：异议的新增/消解/升级是实时信号，延迟写入会导致
                             下一次循环基于过时的异议地图做推理

产出 D（FUP + 消息草稿）→ 每次交互结束，LLM 追加 proposed FUP
                          → 用户确认后，人将 status 改为 ready_to_send
                       理由：消息必须人审之后才能发

产出 E（阶段变化）    → LLM 检测到 exit condition 满足时，提议变更
                      → 用户确认后，人修改 Current State
                      → LLM 自动追加 Stage History 日志
                       理由：阶段是人的决策，但检测条件的是 LLM
```

### 3.3 写入冲突处理

当 LLM 写入 `analysis.md` 时，可能与人在同一区域的手动编辑产生冲突。方案：

- **analysis.md** 设计为 LLM 主导区。人在此区域只做修正（correction）而非同时编辑。实践中人在 Amuro 中使用 followups.md 和 Index.md 作为交互界面，analysis.md 作为"只读 + 偶尔修正"的知识沉淀区——冲突概率低。
- **Index.md** 的 LLM 写入区（Confidence / Confidence History / Stage History）与人的写入区（Goal / Exit Conditions / Account）无重叠，无冲突。
- **followups.md** 的状态字段由不同角色写入不同的值：LLM 写 `proposed`，人写所有其他状态。约定清晰则无冲突。

## 五、与现有 lead 文件结构的兼容方案

### 5.1 兼容原则

- **不修改现有字段的语义**。Index.md 的现存字段保持不变。
- **新增字段全部放在现有字段之后**。Index.md 中新增的 `Confidence`、`Confidence History`、`Stage History` 追加在 `Exit Conditions` 之后。
- **新增文件不做强制要求**。旧 lead 若无 `analysis.md`，追单循环可以仅基于 Index.md + followups.md 工作，只是没有结构化知识积累能力。新 lead 从创建起就带 `analysis.md` 骨架。
- **followups.md 的 FUP 结构不变**。仅在 `status` 字段的值域中新增 `proposed`。

### 5.2 迁移路径

```
Phase 1: analysis.md 模板化
  为新 lead 生成 analysis.md 骨架模板（空 section 占位）。
  旧 lead 无 analysis.md 时 LLM 仅操作 Index.md + followups.md。

Phase 2: Index.md 字段扩展
  在 Index.md 尾部追加 Confidence / Confidence History / Stage History。

Phase 3: FUP status 扩展
  followups.md 的 status 值域扩展 proposed。LLM 写入的 FUP
  统一以 proposed 状态起步。

需要兼容的 case：旧 lead 没有 analysis.md 但开始一次追单循环
→ LLM 在首次分析时创建 analysis.md 并写入 initial 蒸馏。
  之前缺失的信息回溯为 unknown，不强行补写。
```

### 5.3 向后兼容检查清单

| 场景 | 兼容性 | 处理方式 |
|------|:------:|---------|
| 旧 lead 只有 Index.md | ✅ | LLM 读取 Index.md + followups.md，分析产出在内存中，不写入 analysis.md（除非显式请求创建） |
| 新 lead 从模板创建 | ✅ | 模板已含 analysis.md 骨架 |
| Index.md 无 Confidence 字段 | ✅ | LLM 追加到文件尾部 |
| followups.md 无 proposed 状态 | ✅ | status 是自由文本字段，新增 `proposed` 值不影响现有 FUPs |
| 人在 LLM 写入期间同时编辑 analysis.md | ⚠️ | 冲突概率低（analysis.md 设计为 LLM 主导），实践中通过约定避免 |

## 六、设计决策汇总

| 决策 | 内容 | 理由 |
|------|------|------|
| 写入闭环先于读取设计 | 写入格式决定检索模式，先定写入再定读取 | C-001/C-002 已共识 |
| analysis.md 而非嵌入 Index.md | 分析和元数据分离，避免 Index.md 膨胀 | Index.md 人扫读，analysis.md LLM 操作 |
| 蒸馏追加而非覆盖 | 需要知识积累的 timeline，覆盖会丢失推理链 | 信任度调试、回滚需要历史 |
| 信心单值 + 历史表 | 当前值给人看，历史表给趋势分析 | 结构化优于自由文本 |
| FUP message 需人确认 | 消息发出去有外部后果 | Amuro 是工作台，不是自动驾驶 |
| Exit Conditions LLM 不可写 | 退出标准是人的根本意图表达 | 一旦 LLM 可改 exit condition，lead 的生命周期就失控 |
| 不做实时冲突检测 | 分析区和操作区分离，冲突概率低 | 过度工程化（分布式锁、CRDT）在当前阶段是 premature |
| 单 lead 闭环先于跨 lead 知识调用 | 先把一个 lead 的知识积累链路跑通 | C-001 MVP 原则，C-002 已确认 |

## 七、NOT in scope（本轮明确不做）

| 不做的事 | 理由 |
|---------|------|
| 向量数据库 / embedding 选型 | 取决于写入格式，写入方案未定前选型无意义 |
| 知识调用（读取/检索）机制设计 | 写入格式决定检索模式，读取应后置 |
| 多 lead 交叉知识调用 | 先做好单 lead 闭环 |
| 通用知识库方案对比 | Amuro 不是通用知识库场景 |
| 写入冲突的分布式解决方案（CRDT、锁） | 当前阶段人-LLM 编辑模式冲突概率低，premature engineering |
| 知识版本回滚机制 | 追加式日志已提供基本回滚能力，正式版控后置 |
