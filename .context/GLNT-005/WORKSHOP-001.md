## 1. GLNT-5 Vision 概述

公司处于信贷领域，用户主要旅程可抽象为：登录、授信、用信，以及后续还款、复借、风险复核等常规路径。本 Vision 目标是建设一套**可配置、可追踪、可扩展**的设备信息采集能力，用于在关键业务节点采集用户当前设备侧信息（设备基础信息 / AppList / SmsList），并支持后续风控、反欺诈、贷中复核、运营分析等系统消费。

本文**暂不讨论**用户授权、PII、合规限制，仅聚焦设备信息采集功能本身（数据库设计、采集节点设计、采集开关设计）。

## 3. 设计骨架 — 数据模型

本 WORKSHOP-001 的主体是 snapshot 采集方案。当前核心 DDL 由 4 张表组成：1 张采集任务表 + 3 张采集结果 snapshot 表（基础信息 / AppList / SmsList）。设备身份建模、设备归并、用户设备关系不属于当前只读采集核心表，但未来需要单独解决。

### 3.0 关键口径

- `device_collect_task` 是一次采集指令或采集请求，不是某一种数据的结果表。
- 一条 `device_collect_task` 可要求采集一类、两类或三类数据，由 `collect_types` 决定。
- `device_basic_snapshot`、`device_app_snapshot`、`device_sms_snapshot` 是同一条采集任务下的三类结果表，不是三条独立任务。
- 当前设计按“一条任务下每类结果最多一条 snapshot”处理，建议分别对三张 snapshot 表增加 `unique(task_id)` 约束。
- 如果未来要支持分页或分批上传 SmsList / AppList，再引入 `batch_no` 或批次子表；MVP 不做该复杂化。
- 当前需求是严格只读采集，不对客户端采集结果做加工、归并、派生或设备身份生成。
- 采集结果只按原始 `raw_payload` 保存；`idfv`、`idfa`、`oaid`、`device_model`、`os_version` 等厂商或系统字段不提升为宽表字段。
- 不引入 `device_id`、`device_key` 等服务端衍生设备标识。
- `idfv`、`idfa`、`oaid` 等字段受厂商、系统版本和权限限制影响，不保证可取；不同系统约定也不同。
- 如果未来要把某类原始 key 提升为宽表字段，必须先定义明确选择标准，并按同类平行字段成组处理，例如不能只提 `idfv` 而遗漏 `idfa` / `oaid`。
- 如果未来要做宽表字段，字段名必须使用客户端原始 key，例如 `idfv` / `idfa` / `oaid`，不允许出现 `device_id` 这类加工或衍生命名。
- 当前核心设计不做任何宽表抽取。

### 3.1 采集任务表 `device_collect_task`

记录每一次采集请求的生命周期。

执行语义：

- 规则引擎或风控策略平台返回采集决策后，设备采集服务创建该任务。
- 客户端按该任务执行采集。
- 任务成功后，按 `collect_types` 写入对应 snapshot 表。
- `switch_snapshot` 保存当次命中的规则决策快照，用于审计和复盘，不是配置主表。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `task_no` | varchar | 采集任务编号 |
| `user_id` | bigint | 用户 ID |
| `journey_node` | varchar | 采集节点 |
| `collect_types` | json | 本次要求采集的数据类型 |
| `switch_snapshot` | json | 触发时命中的开关配置快照 |
| `strategy_version` | varchar | 采集策略版本 |
| `client_version` | varchar | 客户端版本 |
| `status` | varchar | pending、success、partial_success、failed、skipped |
| `failure_reason` | varchar | 失败原因 |
| `requested_at` | datetime | 请求时间 |
| `completed_at` | datetime | 完成时间 |
| `created_at` | datetime | 创建时间 |

### 3.2 设备基础信息快照表 `device_basic_snapshot`

保存每次采集到的设备基础信息。

与任务关系：

- 当 `device_collect_task.collect_types` 包含 `device_basic` 时写入。
- 同一 `task_id` 最多一条记录。
- 设备基础信息完整保存在 `raw_payload`，不抽取 `idfv`、`idfa`、`oaid` 或其他设备字段为宽表列。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `task_id` | bigint | 采集任务 ID |
| `user_id` | bigint | 用户 ID |
| `raw_payload` | json | 原始上报内容 |
| `collected_at` | datetime | 采集时间 |
| `created_at` | datetime | 创建时间 |

### 3.3 应用列表快照表 `device_app_snapshot`

保存一次 AppList 采集的批次信息。

与任务关系：

- 当 `device_collect_task.collect_types` 包含 `app_list` 时写入。
- 同一 `task_id` 最多一条记录。
- AppList 完整内容保存在 `raw_payload`，核心设计不拆 item 明细。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `task_id` | bigint | 采集任务 ID |
| `user_id` | bigint | 用户 ID |
| `raw_payload` | json | 原始 AppList |
| `collected_at` | datetime | 采集时间 |
| `created_at` | datetime | 创建时间 |

### 3.4 短信列表快照表 `device_sms_snapshot`

保存一次 SmsList 采集的批次信息。

与任务关系：

- 当 `device_collect_task.collect_types` 包含 `sms_list` 时写入。
- 同一 `task_id` 最多一条记录。
- SmsList 完整内容保存在 `raw_payload`，核心设计不拆 item 明细。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `task_id` | bigint | 采集任务 ID |
| `user_id` | bigint | 用户 ID |
| `raw_payload` | json | 原始 SmsList |
| `collected_at` | datetime | 采集时间 |
| `created_at` | datetime | 创建时间 |

### 3.5 明细表说明

核心设计不包含 `device_app_item` 与 `device_sms_item`。AppList 和 SmsList 在 MVP 中以 snapshot 批次表的 `raw_payload` 保存完整列表，不拆明细、不计算数量字段。

如果后续风控、特征工程或运营分析需要高频按单个 App / 单条短信检索，可在二期从 `raw_payload` 派生明细表或离线宽表，但这不属于当前核心库表设计。

## 4. 未来设备身份建模

当前方案不在采集链路中生成 `device_id` / `device_key`，也不维护 `device` / `user_device` 主档表。原因是当前需求被限定为严格只读采集，且 `idfv` / `idfa` / `oaid` 等原始 key 受厂商、系统版本和权限限制影响，不保证可取，不适合作为当前采集库的加工字段。

但从信贷业务长期演进看，设备身份和用户设备关系仍然是必须解决的问题。后续如果进入设备身份建模阶段，可以单独设计以下两张表。

### 4.3 未来建模前置问题

- 哪些原始 key 可以参与设备识别：`idfv`、`idfa`、`oaid`、Android ID、厂商 ID 等。

- 是否允许服务端生成 `device_key`，以及生成规则是否属于设备采集服务、风控平台或统一设备指纹服务。
- 多用户共用设备、一用户多设备、设备重置、App 重装等场景如何归并。
- 如果将原始 key 提升为宽表字段，必须使用原始 key 命名，并按同类平行字段成组设计。

## 5. 设计骨架 — 采集节点

按信贷主旅程拆分 7 个节点，按风险收益确定采集强度。

### 5.1 节点 1：登录成功后

- **采集**：设备基础信息
- **用途**：建立用户与设备关系；识别新设备登录、设备切换、异常环境
- **默认不采集**：AppList、SmsList
- **原因**：登录节点过早，重型采集影响登录体验

### 5.2 节点 2：授信申请开始

- **采集**：设备基础信息、AppList
- **可选**：SmsList（仅在风控策略命中高风险、资料不足、首贷用户等条件时触发）
- **用途**：授信前反欺诈与风险识别；识别设备环境、安装应用结构、潜在异常应用组合

### 5.3 节点 3：授信资料提交前

- **采集**：设备基础信息、AppList、SmsList
- **用途**：授信决策前补齐设备侧风险特征；降低决策后补采链路延迟
- **建议策略**：首次授信用户强采；复借或低风险用户按频率规则采集

### 5.4 节点 4：授信审批完成后

- **采集**：设备基础信息
- **用途**：记录审批时设备状态快照；支持审批后审计和风控回溯
- **默认不采集**：AppList、SmsList
- **原因**：决策已完结，重型采集对实时价值较低

### 5.5 节点 5：用信申请开始

- **采集**：设备基础信息、AppList
- **可选**：SmsList
- **用途**：识别授信后设备变化；支持贷前用信风险复核
- **建议策略**：若距上次完整采集超阈值则补采；设备变更 / IP 异常 / 登录异常时增强采集

### 5.6 节点 6：用信确认提交前

- **采集**：设备基础信息、AppList、SmsList
- **用途**：放款前最终风险复核；支持放款前反欺诈规则与模型特征更新
- **建议策略**：高金额 / 高风险 / 新设备 / 跨渠道场景优先触发完整采集；低风险用户只采基础信息

### 5.7 节点 7：贷中复核或风险召回

- **采集**：设备基础信息、AppList、SmsList
- **用途**：贷中风险监控；异常账户复核
- **建议策略**：由风控事件触发，而非固定每次打开 App 都触发

## 6. 设计骨架 — 采集开关与规则引擎

采集开关不在本业务库中用 `device_collect_switch` 表管理。真实业务中，节点、开关、频率、失败策略和人群条件应由统一规则引擎或风控策略平台管理。

设备采集服务只消费规则引擎的决策结果，并据此创建 `device_collect_task`。`device_collect_task.switch_snapshot` 保存当次命中的规则快照，用于审计和复盘；它不是开关配置主表。

### 6.1 规则引擎管理维度

至少支持以下维度：

- 总开关：控制整体启用
- 类型开关：分别控制 device_basic、app_list、sms_list
- 节点开关：按登录 / 授信 / 用信等业务节点配置
- 产品开关：按不同信贷产品配置
- 渠道开关：按渠道包 / 投放来源 / 合作方配置
- 客户端版本开关：按 App 版本控制是否采集
- 操作系统开关：按 iOS / Android 区分
- 用户分层开关：按首贷 / 复借 / 低风险 / 高风险等分层配置
- 灰度如果存在，也只是规则引擎内部配置；对前端来说只体现为是否采集的 true/false 结果
- 紧急熔断开关：客户端异常 / 服务端压力 / 数据异常时快速关闭

### 6.2 采集类型枚举

| 枚举 | 说明 |
| --- | --- |
| `device_basic` | 设备基础信息 |
| `app_list` | 当前设备安装应用列表 |
| `sms_list` | 当前设备短信列表 |

### 6.3 失败策略

| 策略 | 说明 | 适用场景 |
| --- | --- | --- |
| `ignore` | 采集失败不阻塞主流程 | 登录、低风险复借 |
| `retry_async` | 主流程继续，后台异步重试 | 授信开始、用信开始 |
| `block_until_success` | 采集成功前阻塞主流程 | 授信提交前、用信确认前的强风控场景 |
| `fallback_to_basic` | AppList 或 SmsList 失败时降级只采基础信息 | 客户端兼容性不足 |

### 6.4 频率规则

采集频率和强制突破条件是规则内容，由后端规则引擎或配置后台决定，本项目不讨论规则具体取值。

前端不判断“是否到达采集频率”或“是否需要突破频率限制”。如果后端规则判断需要采集，就下发采集任务；如果规则判断不需要采集，就不下发采集任务。

频率规则怎么执行值得单独设计，可作为 Q3.5 与规则下发问题一起讨论。

### 6.5 规则命中逻辑

按以下顺序计算：

1. 业务系统进入采集节点，调用规则引擎
2. 规则引擎检查总开关是否启用
3. 规则引擎根据业务节点、产品、渠道、操作系统、客户端版本过滤策略
4. 规则引擎根据用户分层和风控标签判断采集强度
5. 规则引擎应用频率规则，决定是否真正创建采集任务
6. 规则引擎返回决策结果：是否采集、采集类型、失败策略、策略版本、命中原因
7. 设备采集服务根据决策结果生成 `device_collect_task`，并将决策结果写入 `switch_snapshot`

## 7. 服务端流程

### 7.0 接口编排待设计问题

采集接口和业务表单提交接口是两个独立接口。采集服务不直接提交业务表单，业务表单提交接口也不直接承载设备采集 payload。

两者在前端侧是平行、串行，还是业务提交后异步采集，目前不在 USE 阶段判断。该关系由后续设计阶段结合后端规则引擎能力、前端流程和业务节点体验继续细化。

### 7.1 同步触发流程

1. 业务系统进入关键节点
2. 调用规则引擎或风控策略平台，传入用户、设备、产品、渠道、节点、客户端版本
3. 规则引擎返回采集决策
4. 若无需采集，返回 `skipped` 与原因
5. 若需要采集，创建 `device_collect_task`
6. 服务端返回采集指令给客户端，包含 `collect_types` 与各类型 `collect_rules`
7. 客户端必须按 `collect_rules` 执行采集、裁剪和上报，不允许自行扩大采集范围
8. 服务端按 `collect_types` 写入对应 snapshot：`device_basic_snapshot`、`device_app_snapshot`、`device_sms_snapshot`；未要求采集的类型不写对应 snapshot
9. 更新采集任务状态
10. 通知风控或特征系统消费

一条任务与结果表的关系：

```text
device_collect_task
  -> 0 或 1 条 device_basic_snapshot
  -> 0 或 1 条 device_app_snapshot
  -> 0 或 1 条 device_sms_snapshot
```

如果只采设备基础信息，则只产生 `device_basic_snapshot`；如果完整采集三类数据，则三张 snapshot 表各产生一条记录。

### 7.2 异步补采流程

1. 业务节点创建异步采集任务
2. 主流程继续
3. 客户端在合适时机执行采集并上报
4. 服务端保存数据
5. 后台任务将采集结果推送到风控、特征、审计系统

## 8. 接口设计草案

### 8.1 获取采集指令

请求：

```json
{
  "user_id": "123",

  "product_code": "cash_loan",
  "channel_code": "organic",
  "os_type": "android",
  "app_version": "3.2.1"
}
```

响应：

```json
{
  "task_no": "DCT202607010001",
  "required": true,
  "collect_types": ["device_basic", "app_list", "sms_list"],
```

## 10. 非目标边界

本设计**明确不覆盖**以下范围（C-001 已登记）：

- **用户授权**：用户何时同意、是否二次确认、如何撤回

- **合规限制**：金融监管 / 隐私法对设备字段采集、留存、跨境传输的限制
- **实际代码实现**：SQL DDL、API 实现、客户端 SDK 实现
- **数据量预估 / 归档策略 / 保留周期**的具体数字
- **iOS / Android 客户端实际可采集能力差异**：不在本项目讨论范围内；当前仅规定能力不可用时返回空数组
- **风控 / 特征系统**在生产消费采集结果的实际集成方案

如未来需要进入上述范围，应单独发起专项讨论；如果这些问题会影响 GLNT-5 是否解决，则应在 `Index.md` 追加下一轮 `WORKSHOP-NNN` 后继续推进。
