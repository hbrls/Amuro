## Vision 背景

公司处于信贷领域，用户主要旅程可抽象为：登录、授信、用信，以及后续还款、复借、风险复核等常规路径。

当前 Vision 要解决的问题是：设计设备信息采集能力。采集对象包括设备基础信息、AppList、SmsList。本 Vision 暂不讨论用户授权、PII、合规限制，聚焦采集功能本身。

## 工作流规范

本文件是 Vision 级路线图，用于记录每一轮 WORKSHOP 的方向和纲领。

标准流程：

1. 通过对话确认某一轮 WORKSHOP 的方向 / 纲领。
2. 将该轮纲领写入 `Index.md`，章节名使用 `WORKSHOP-001`、`WORKSHOP-002` 等。
3. 多轮讨论生成 `C-NNN` 文件；该部分由其它 Agent 负责。
4. checkpoint 汇总本轮 `C-001 ~ C-999` 讨论，写入对应 `WORKSHOP-NNN.md`；该部分由其它 Agent 负责。
5. checkpoint 在 `WORKSHOP-NNN.md` 中写入 USE 澄清部分。
6. 完成 USE 澄清后判断 Vision 是否解决。
7. 如果 Vision 没有解决，则在本文件追加 `WORKSHOP-002`，创建空的 `WORKSHOP-002.md`，开启下一轮讨论。
8. 如此往复，直到 Vision 解决。

## WORKSHOP-001：设备信息采集 snapshot 方案

### 状态

已完成 checkpoint。由于本轮是实验性推进，`Index.md` 的路线图结构是在事后补救时整理的；详细 checkpoint 成果以 `WORKSHOP-001.md` 为准。

### 本轮目标

围绕设备信息采集能力完成第一轮方案澄清，形成可评审的 snapshot 采集主体方案。

本轮重点讨论：

- 采集哪些设备信息。
- 在哪些信贷业务节点触发采集。
- 采集规则如何由后端控制，前端如何遵守。
- 采集结果如何保存为可追踪的 snapshot。
- 哪些问题属于当前项目范围，哪些应交由后续设计或其他 Agent 调研。

### 本轮范围

纳入范围：

- 设备基础信息、AppList、SmsList 三类采集对象。
- 严格只读采集，不对客户端采集结果做加工、归并、派生或设备身份生成。
- snapshot 采集作为当前主体方案。
- 规则驱动：后端规则引擎或配置后台决定是否采集、采集哪些类型、采集范围、频率、失败策略等。
- 前端按采集指令执行，不自行扩大采集范围，不自行判断规则。

不纳入范围：

- 用户授权、PII、合规限制。
- iOS / Android 具体系统能力可用性论证。
- 风控系统实时或异步消费采集结果的生产集成方案。
- 数据库保留周期、归档策略、TTL。
- 设备身份建模、设备归并、用户设备关系主档落地。

### 本轮设计方向

`WORKSHOP-001.md` 应围绕以下方向收束：

- 当前核心方案围绕 snapshot 采集展开。
- 一条采集任务可以对应设备基础信息、AppList、SmsList 三类结果。
- 采集结果以原始 `raw_payload` 保存。
- AppList / SmsList 不拆 item 明细表。
- 不新增 `device_current_profile` 当前画像表。
- 不在当前采集链路中生成 `device_id` / `device_key`。
- `device` / `user_device` 属于未来设备身份建模问题，不并入当前核心 DDL。
- 采集开关、范围、频率、灰度、失败策略等由规则引擎或配置后台控制。

### 本轮预期产物

`WORKSHOP-001.md` 应作为本轮阶段性成功产物，记录：

- 当前 snapshot 采集主体方案。
- 当前核心表设计。
- 未来设备身份建模问题。
- 采集节点和推荐采集矩阵。
- 规则驱动的采集开关与前端执行原则。
- USE 澄清问题、已对齐结论、设计提议、范围外问题和外部调研问题。

### 本轮后续判断

完成 `WORKSHOP-001.md` 的 USE 澄清后，需要判断 GLNT-5 是否已经解决。

如果仍未解决，应在本文件追加 `WORKSHOP-002` 章节，并创建空的 `WORKSHOP-002.md` 文件，进入第二轮讨论。

## WORKSHOP-002：采集执行契约与前端遵守规则

### 状态

调研中。

`WORKSHOP-001` 已完成 snapshot 采集主体方案的 checkpoint，但仍有若干执行层问题没有收束。`WORKSHOP-002` 应聚焦采集任务从“规则命中”到“前端执行并上报”的契约设计。

本轮已创建 `WORKSHOP-002.md` 作为 checkpoint 目标文件。后续多轮讨论产物 `C-NNN` 及 checkpoint 写入由其它 Agent 负责。

### 本轮目标

把设备采集从方案骨架推进到可派单的执行契约，明确：

- 业务节点如何触发采集指令获取。
- 采集接口与业务表单提交接口如何编排。
- 后端规则结果如何下发给前端。
- 前端如何遵守规则、执行采集、处理失败和上报结果。
- 任务状态、超时、重试、幂等、部分成功如何表达。

### 本轮范围

纳入范围：

- 采集指令获取的触发时机和调用方。
- 采集接口与业务提交接口的关系：串行、并行、提交后异步、阻断与不阻断。
- 规则结果下发契约：是否采集、采集类型、失败策略、频率命中结果、有效期、规则版本。
- 前端执行契约：按规则采集、按规则裁剪、不可自行扩大采集范围、能力不可用时如何返回。
- 任务生命周期：pending、success、partial_success、failed、skipped、expired 等状态是否需要，以及状态转换口径。
- 失败处理：超时、客户端采集失败、上报失败、部分类型失败、异步重试。
- 幂等与重复触发：同一业务节点重复进入、同一任务重复上报、任务过期后再上报的处理原则。
- 与 `device_collect_task.switch_snapshot` 的关系：规则命中结果如何随任务保存，便于复盘。

不纳入范围：

- `device` / `user_device` 设备身份建模；该问题留给 `WORKSHOP-003` 或更后。
- 设备归并、设备指纹、服务端生成 `device_id` / `device_key`。
- AppList / SmsList 明细 item 表。
- 数据库保留周期、归档策略、TTL。
- 风控系统实时或异步消费采集结果的生产集成方案。
- 用户授权、PII、合规限制。

### 本轮需要讨论的问题

#### Q1 业务节点如何拿到采集指令

需要讨论业务前端在登录、授信、用信等节点进入时，是直接调用采集指令接口，还是由业务接口响应中附带采集指令入口。

本问题只讨论采集指令在哪里下发、谁负责触发，不讨论规则内容本身。

#### Q2 采集接口与业务提交接口如何编排

需要讨论采集接口和业务表单提交接口之间是串行、并行、提交后异步，还是由规则结果决定。

重点是前端如何知道当前节点是否必须等待采集完成，以及采集失败、超时、跳过时业务提交是否继续。

#### Q3 规则结果如何下发给前端

需要讨论后端规则引擎或配置后台的结果如何进入采集指令，并被前端理解。

本轮只设计规则结果的执行契约，不讨论规则后台如何配置具体规则值。

#### Q4 采集频率如何执行

需要讨论频率规则由谁判断、何时判断，以及后端如何把频率裁决折算为“本次是否下发采集任务”。

原则方向：频率、跳过、复用、强制突破等规则语义均属于后端规则引擎或配置后台内部裁决；前端不理解频率窗口、下次可采时间或强制突破原因，只接收后端下发的可执行结果：本次是否需要采集，以及需要采集时的采集任务与编排指令。

#### Q5 前端如何表达采集能力不可用或部分失败

需要讨论平台能力不可用、某一类采集失败、采集为空、用户设备环境异常等情况如何上报。

本问题不讨论 iOS / Android 能力是否真的可用，只讨论契约表达。

#### Q6 任务状态机与幂等如何设计

需要讨论一条 `device_collect_task` 从创建到完成的状态转换，以及重复上报、重复创建、过期上报、异步重试时的处理原则。

该问题直接影响后端落库、前端重试和后续审计复盘。

#### Q7 switch_snapshot 应保存什么

需要讨论 `switch_snapshot` 保存的是规则命中结果快照，而不是开关配置主表。

本轮应明确它至少需要支持复盘：为什么本次采集、采了哪些类型、采用什么失败策略、规则版本是什么、是否命中频率跳过或强制突破。

### 本轮预期产物

`WORKSHOP-002.md` 应作为第二轮阶段性成功产物，记录：

- 采集指令下发方式。
- 采集接口与业务提交接口编排原则。
- 前端执行规则的契约。
- 采集频率执行口径。
- 任务状态机、失败处理、超时、重试、幂等原则。
- `switch_snapshot` 的保存口径。
- 仍需 USE 澄清的问题。

### 留给后续 WORKSHOP

`device` / `user_device`、设备身份建模、设备归并、设备指纹和服务端衍生设备标识不进入 `WORKSHOP-002`。

如果 GLNT-5 在 `WORKSHOP-002` 后仍未解决，应优先考虑在 `WORKSHOP-003` 或更后单独讨论设备身份建模。

### 本轮目标

建立设备基础信息原始字段的调研框架和候选清单，对每个候选字段进行有证据的语义分类与价值分析，形成可供后续字段设计使用的研究结论。

本轮输出的是字段类别、分类标准、字段示例、逐字段证据和研究结论，不确定最终客户端采集清单，不定义最终 `raw_payload` 契约，也不设计 device 归并或 user_device 绑定。

### 术语与边界

本轮使用以下术语：

- `Identity`：平台、系统或厂商直接提供，原始语义用于标识设备、安装实例、应用作用域主体或广告主体的值。字段是否稳定、是否可重置、作用域多大，必须逐项调研，不能因为名称像标识符就预设可用。
- `DeviceProfile`：相对稳定、直接描述设备、硬件、操作系统或构建配置的原始值。该名称只表示原始字段类别，不表示服务端生成的设备画像。
- `DeviceInfo`：采集时直接读取的设备能力、状态或环境原始值。字段进入本类别不等于值得采集，高波动字段仍需单独判断价值。
- `RiskSignal`：算法或检测逻辑根据一个或多个输入形成的风险结果。它属于算法团队，不是采集团队的原始字段类别，本轮不得设计或产出 RiskSignal。

本轮只处理原始值：

- 可以研究客户端、操作系统、平台 API 或厂商接口直接返回的原始值。
- 不生成、不设计、不保留拼接、哈希、指纹、评分、相似度、画像、规则判断、模型输出或时间序列结论。
- `is_rooted`、`is_jailbroken` 等字段如果来自检测逻辑，应视为 RiskSignal 并排除；检测过程依赖的原始系统值可以分别进入候选池分析。
- 即使某个原始字段未来可能成为算法输入，本轮也不得推导或设计对应算法结果。

### 分类与选择是两个维度

语义分类只使用 `Identity`、`DeviceProfile`、`DeviceInfo`。`RiskSignal` 只用于说明边界，不参与原始字段分类。

字段价值是逐项调研后的研究结论，不是预先设定的语义类别：

- `Selected`：现有证据支持进入后续字段设计评估。
- `NotSelected`：完成分析后，现有证据不支持进入后续字段设计评估。
- `Undetermined`：证据不足或存在关键不确定性，暂不能判断。

`Selected` 不代表已经进入最终采集契约；`NotSelected` 也不表示字段在所有业务中永久无价值。

### 已知输入与待验证示例

以下字段只用于启动候选池，不构成预先批准的清单：

- Identity 示例：IDFV、IDFA、OAID、GAID、Android ID、VAID、AAID，以及调研发现的其他平台原始标识。
- DeviceProfile 示例：brand、manufacturer、model、设备或产品名称、OS / ROM / Build 原始信息，以及相对稳定的硬件配置。
- DeviceInfo 示例：内存、存储、屏幕、电量、充电状态、语言、时区、网络类型、IP，以及调研发现的其他设备状态或环境值。
- RiskSignal 边界示例：root、jailbreak、emulator、hook、tamper 等检测结果不得作为原始采集维度；如存在对应原始输入，只分析原始输入本身。

当前明确约束：

- 电量和是否充电都是原始 DeviceInfo 候选值，但变化频繁且当前没有独立采集价值，研究结论记为 `NotSelected`。
- 禁止从电量和充电状态推导“长期满电”“持续充电”或任何 RiskSignal。
- 网络类型是否有独立采集价值尚未确定，必须区分具体字段概念、来源和使用证据后分析，不得把所有网络字段整体纳入或整体排除。
- 所有示例字段都必须接受同一套分析，不能因被列为示例而直接判定 `Selected`。

### 逐字段分析标准

每个候选字段至少需要记录：

1. 字段概念及可能出现的原始 key；
2. 适用平台；
3. 原始来源或读取 API；
4. 原始值类型、格式、空值和占位值；
5. 是否确为原始值，是否混入检测或推导逻辑；
6. 作用域、生命周期、重置条件和变化频率；
7. 权限、平台版本、厂商实现和可得性限制；
8. 独立采集价值及其证据；
9. `Identity` / `DeviceProfile` / `DeviceInfo` 语义分类及理由；
10. `Selected` / `NotSelected` / `Undetermined` 研究结论及理由；
11. 仍需验证的问题和证据缺口。

字段不能仅凭名称、行业厂商曾经使用、单个示例 JSON 或潜在算法用途判定有价值。

### 调研输入要求

候选池和证据应优先来自：

- GLNT-4 已整理的 Android 候选维度全集；
- 当前 Android `DeviceInfoRepository` 的真实读取实现；
- iOS 当前实现或可验证的平台 API；
- iOS / Android 官方平台资料；
- 当前项目真实 `raw_payload` 样例；
- 必要时使用可信厂商资料补充候选字段，但厂商声明不能替代当前项目实现证据。

必须区分“行业存在的候选字段”“客户端当前能够读取的字段”“当前项目实际已经上报的字段”。三者不得互相替代。

### 本轮需要依次解决的问题

#### Q1 分类与选择标准

确认 `Identity`、`DeviceProfile`、`DeviceInfo` 的判定标准、边界和交叉情况，确认 `RiskSignal` 不进入采集维度，并定义 `Selected`、`NotSelected`、`Undetermined` 的证据门槛。

#### Q2 候选字段池和证据结构

汇总 iOS 与 Android 的候选原始字段，建立统一分析矩阵。候选池必须保留来源，不得把行业调研字段误写为当前已实现字段。

#### Q3 逐字段分类与价值分析

按照统一标准逐项分析所有候选字段。不能按字段组批量假设结论，也不能只分析 Identity 而跳过 DeviceProfile 或 DeviceInfo。

#### Q4 研究结论与证据缺口

为每个字段给出语义分类和研究结论；证据不足时必须标记 `Undetermined`，不得通过推测补齐。汇总仍需客户端、数据或平台资料补充的问题。

#### Q5 完整性复核

复核候选字段覆盖、分类一致性、原始值边界和选择理由，确认没有混入 RiskSignal、归并规则、数据库设计或最终采集契约。

### 本轮不纳入范围

- 不确定最终客户端采集字段清单。
- 不定义或改变 `device_basic_snapshot.raw_payload` 的最终 Schema。
- 不要求客户端在本轮立即新增字段。
- 不设计 device 身份等价关系、归并规则、主字段、备用字段或冲突处理。
- 不设计 `device` / `user_device` 表结构、约束、索引、绑定、状态或生命周期。
- 不讨论历史归并规则升级、历史数据回填或处理结果审计。
