## 1. C-011 JoinCoordinator DO 对 GAP #5 的覆盖度确认

### 1.1 可直接复用的接口

| C-011 JoinCoordinator 接口 | GAP #5 语义映射 | 覆盖判断 | 备注 |
|---------------------------|---------------|---------|------|
| `register(instanceId: string, childIds: string[]) → void` | 主 Workflow 注册 N 个运行时生成的子 Workflow ID | **完全匹配** | GAP #1 的 childIds 是设计时分支名列表；GAP #5 的 childIds 是运行时 `["inst-" + i for i in 0..N-1]` 格式。签名无需改变。 |
| `reportDone(childId: string, result: Result) → void` | 每个多实例完成时上报结果 | **完全匹配** | 子 Workflow 模板出口可复用 C-011 定义的标准化 reportDone 逻辑。 |
| `awaitAll(instanceId: string) → Result[]` | "All complete" 完成条件——等待所有 N 个实例完成 | **完全匹配** | 覆盖 ~90% 场景（C-019 A2）。轮询逻辑和超时策略均可直接复用。 |
| DO 生命周期管理（过期清理、幂等去重） | 多实例实例 ID 的幂等处理 | **完全复用** | C-011 已设计 childId 级别的去重逻辑，多实例场景可直接复用。 |
| 超时策略 + 部分失败策略 | 批量处理中的超时和部分失败处理 | **完全复用** | C-011 §3.2 的超时策略（全局超时 + 部分成功标记）直接适用。 |
| 子 Workflow 模板（标准化入口 + reportDone 出口） | 多实例子 Workflow 的执行模板 | **可复用（需微调）** | 见 §5 详细分析。核心结构可复用，但需增加实例序号参数和提前终止检查。 |

### 1.2 需扩展的接口

| 需求 | C-011 当前状态 | GAP #5 新增 | 接口设计 |
|------|-------------|-----------|---------|
| `awaitN(instanceId: string, n: number, childIds: string[]) → Result[]` | ❌ 不存在 | N-of-M 完成条件 | 新增方法。DO 内部维护成功/失败计数器，当成功或失败总数达到阈值时返回。详见 §2.1。 |
| `signalStop(instanceId: string) → void` | ❌ 不存在 | 提前终止信号 | 新增方法。DO 写入 `stopFlag`，子 Workflow 的 step 间通过 `checkStopFlag()` 检查。详见 §2.2。 |
| `evaluateCompletion(instanceId: string, expression: string) → boolean` | ❌ 不存在 | 表达式完成条件 | 新增方法。DO 维护实例状态摘要，每次 `reportDone` 后求值。详见 §2.3。 |

### 1.3 覆盖度结论

C-011 JoinCoordinator DO 对 GAP #5 的覆盖度约为 **75-80%**（与 C-019 评估一致）。核心并行 Fork/Join 机制（register、reportDone、awaitAll、超时、幂等）完全复用，需增量开发的仅为完成条件变体（awaitN、signalStop、evaluateCompletion）和大基数分批策略。

## 2. GAP #5 增量接口设计

### 2.1 `awaitN(n, childIds)` ——N-of-M 完成条件

#### 签名

```typescript
awaitN(instanceId: string, n: number, childIds: string[]): Promise<Result[]>
```

#### 语义

等待 N 个实例中至少 `n` 个完成（无论成功/失败），或 `(childIds.length - n) + 1` 个失败（不可能达到 n 个成功时提前返回），或超时。

#### 设计要点

| 项目 | 决策 |
|------|------|
| **"完成"的定义** | 包含成功和失败。若业务需要"n 个成功"，由返回值中的 `status` 字段筛选。DO 不区分成功/失败完成，由调用方按需过滤。 |
| **提前终止逻辑** | 当 `childIds.length - nCompleted < n - nSucceeded` 时（剩余实例即使全部成功也无法达到 n），DO 立即返回失败。 |
| **超时** | 复用 C-011 的全局超时策略（默认 30min，可配置）。超时后返回已完成的结果 + `timeout: true` 标记。 |
| **幂等** | 复用 C-011 的 childId 去重。同一 childId 多次 `reportDone` 只计入一次。 |
| **返回值** | `{ results: Result[], reachedThreshold: boolean, reason: 'n_reached' | 'timeout' | 'impossible' }` |

#### 结论

`awaitN` 是 `awaitAll` 的参数化变体。在 DO 内部，`awaitAll` 可视为 `awaitN(childIds.length, childIds)` 的特例。实现时建议 `awaitAll` 内部委托给 `awaitN`，减少代码重复。

### 2.2 提前终止信号

#### 设计

```
signalStop(instanceId: string) → void
checkStopFlag(instanceId: string) → boolean
```

主 Workflow 或任一子 Workflow 可调用 `signalStop(instanceId)` 写入终止标志。子 Workflow 的关键 step 间应调用 `checkStopFlag(instanceId)` 主动检查，若返回 `true` 则立即中止执行并调用 `reportDone(childId, { status: 'cancelled' })`。

#### 终止延迟

| 场景 | 最大延迟 | 说明 |
|------|---------|------|
| 子 Workflow step 间 | 单个 step 的执行时间 | 子 Workflow 在 step 边界检查 stop flag |
| 子 Workflow 正在执行长时间操作 | 操作的剩余执行时间 | 不可中断的操作（如外部 API 调用）不受 stop flag 影响 |
| 子 Workflow 在 `workflow.sleep()` 中 | sleep 时长 | 无法中断 sleep。建议业务场景中避免在子 Workflow 中使用长 sleep |

**工程判断**：提前终止的最小延迟取决于子 Workflow step 粒度。秒级延迟对自动化场景可接受。方案 C（事件驱动）的毫秒级终止在本场景无实际收益，采用 DO flag 模式即可（与 C-011 放弃方案 C 的理由一致）。

### 2.3 完成条件表达式引擎

#### 范围压缩

基于 C-019 A2（完成条件以 "All complete" 为主，N-of-M 和 expression-based 为边缘需求 < 10%），**不建议在 GAP #5 一期实现通用表达式引擎**。

#### 一期策略：标准完成条件模板

在 DO 上提供三种标准完成条件，而非表达式引擎：

| 完成条件 | DO 方法 | 优先级 |
|---------|---------|--------|
| All complete | `awaitAll(instanceId)` | P0 |
| N-of-M complete | `awaitN(instanceId, n, childIds)` | P1 |
| First N success then cancel rest | `awaitN(instanceId, n, childIds)` + 调用方调用 `signalStop(instanceId)` | P1 |

#### 二期预留：表达式接口

```typescript
evaluateCompletion(instanceId: string, expression: CompletionExpression): boolean

interface CompletionExpression {
  type: 'all' | 'nOfM' | 'firstSuccess' | 'custom';
  params: Record<string, unknown>;
  // 预留：当实际场景出现复杂自定义表达式时，扩展为 DSL parser
}
```

**工程判断**：通用表达式引擎（类似 BPMN 的 `completionCondition`）需定义 DSL、实现 parser、测试边界条件，预估 3-5d。在没有实际业务需求驱动的情况下，一是过度设计。改为标准模板后一期投入降至 0（awaitN 已涵盖 N-of-M），未来如有实际表达式需求再扩展。

## 3. 大基数策略（N > 100）

### 3.1 问题分析

C-019 C1 和 C5 指出：CF Workflows step CPU 时间限制（30s paid / 15min standard）和 `workflow.start()` 潜在调用速率限制，可能使单 step 内循环启动 N 个实例（N > 500）成为瓶颈。

### 3.2 方案对比

| 维度 | 分批启动（Batched Start） | Queue 分发（Queue Dispatch） |
|------|--------------------------|---------------------------|
| **方案描述** | 主 Workflow 在 helper 中分批循环调用 `workflow.start()`，每批 N/BATCH_SIZE 个，批次间 sleep 100-200ms | 主 Workflow 向 CF Queue 投递 N 条消息，N 个独立 Workflow 实例消费处理，DO 聚合结果 |
| **基数上限** | 受 step CPU 时间限制。若按 50 个/批、每批 0.2s 计算，500 个实例约需 2s，1000 个约需 4s。**建议支持到 N ≤ 500**。 | 理论上无限（Queue 无积压上限） |
| **额外基础设施** | 无。只有 helper 函数 | 需要 CF Queues 实例 + Worker 消费者代码 |
| **运维复杂度** | 低。helper 函数是纯代码模式 | 中。新增 Queue 资源管理、消费者监控、死信处理 |
| **实现工作量** | 1d（分批 helper） | 3-4d（Queue 配置 + 消费者 + 监控） |
| **适用场景** | N ≤ 500 的典型批量处理 | N > 500 的超大批量处理 |
| **CF 依赖** | 仅依赖 `workflow.start()` | 依赖 CF Queues（需团队确认 CF Queues 在生产环境的可用性和 SLA） |

### 3.3 分批启动设计

```typescript
async function batchStartWorkflows(
  items: Item[],
  workflowName: string,
  batchSize: number = 50,
  delayMs: number = 200
): Promise<string[]> {
  const childIds: string[] = [];
  for (let i = 0; i < items.length; i += batchSize) {
    const batch = items.slice(i, i + batchSize);
    const batchIds = await Promise.all(
      batch.map((item, idx) =>
        workflow.start(workflowName, {
          payload: item,
          instanceId: `inst-${i + idx}`,
        })
      )
    );
    childIds.push(...batchIds);
    if (i + batchSize < items.length) {
      await workflow.sleep(delayMs);
    }
  }
  return childIds;
}
```

### 3.4 取舍结论

**推荐：分批启动作为默认策略，Queue 分发作为远期预留。**

| 决策 | 理由 |
|------|------|
| 一期（N ≤ 500） | 分批启动方案。基于 C-019 A3（动态基数 N 通常 ≤ 100），500 的上限已留足余量。1d 工作量可覆盖。 |
| 远期（N > 500） | 若 Q1 确认实际存在 N > 500 的场景，再启动 Queue 分发方案设计。Queue 方案引入的运维复杂度和外部依赖（CF Queues）不应在没有实际需求证明的情况下引入。 |

**并发控制**：无论 N 大小，子 Workflow 的并发执行由 CF Workflows 引擎自动管理。主 Workflow 只负责"启动"，不负责并发调度。分批策略解决的是**启动阶段的 step CPU 时间限制**，而非运行时的并发管理。

## 4. 顺序多实例的轻量方案标准化

### 4.1 核心判断

顺序多实例**不使用 JoinCoordinator DO**。其语义与 `workflow.call()` 的串行语义天然匹配，不需要聚合器参与。C-019 A1 判断其为低频需求，应从简设计。

### 4.2 契约定义

#### 主 Workflow 端

```typescript
async function sequentialMultiInstance(
  items: Item[],
  subWorkflowName: string,
  iterationTransformer: (prevResult: Result | null, item: Item, index: number) => SubWorkflowInput,
  stopCondition?: (result: Result, index: number) => boolean
): Promise<{ results: Result[]; stoppedEarly: boolean }> {
  const results: Result[] = [];
  let prevResult: Result | null = null;

  for (let i = 0; i < items.length; i++) {
    const input = iterationTransformer(prevResult, items[i], i);
    const result = await workflow.call(subWorkflowName, { input, instanceId: `seq-inst-${i}` });
    results.push(result);

    if (stopCondition?.(result, i)) {
      return { results, stoppedEarly: true };
    }
    prevResult = result;
  }

  return { results, stoppedEarly: false };
}
```

#### 关键设计点

| 设计点 | 方案 |
|--------|------|
| **实例间数据传递** | 通过 `iterationTransformer` 显式传递。前一实例的 `prevResult` 作为参数传入，由业务代码决定传递的内容（标量或完整上下文）。符合 C-019 C4 的处理方式。 |
| **提前终止** | 通过 `stopCondition` 回调实现。不支持从子 Workflow 内部发起终止（无 DO 协调通道）。这与顺序多实例的"串行"特性一致——当前实例完成后才决定是否继续下一实例。 |
| **错误处理** | 单实例失败不阻塞后续实例。失败信息记录在 `results[i].status = 'failed'` 中，后续实例根据 `prevResult` 决定行为。若业务需要"任一失败即终止"，由 `stopCondition` 实现。 |
| **无额外状态管理** | 所有状态（results、prevResult、index）在主 Workflow 的局部变量中管理，无 DO 依赖。 |

### 4.3 与并行多实例的边界

```
多实例执行模型选择
├── isSequential = true → 顺序多实例
│   └── 主 Workflow 内 serialMultiInstance() 循环
│       └── 无 JoinCoordinator 参与
│       └── 实例间数据传递：iterationTransformer 显式传递
│
└── isSequential = false → 并行多实例
    └── batchStartWorkflows() → JoinCoordinator
        ├── All complete → awaitAll()
        ├── N-of-M → awaitN()
        └── 提前终止 → signalStop() + checkStopFlag()
```

## 5. 多实例子 Workflow 模板标准化

### 5.1 模板结构

```typescript
interface MultiInstanceInput {
  parentInstanceId: string;
  instanceIndex: number;       // 在多实例中的序号（0-based）
  totalInstances: number;      // 总实例数（N）
  payload: unknown;            // 业务数据
}

interface MultiInstanceOutput {
  status: 'success' | 'failed' | 'cancelled';
  result: unknown;
  error?: string;
}
```

### 5.2 子 Workflow 模板伪代码

```typescript
export async function multiInstanceChild(input: MultiInstanceInput): Promise<void> {
  const { parentInstanceId, instanceIndex, totalInstances, payload } = input;

  // Step 1: 前置处理
  const prepared = await prepareStep(payload, instanceIndex);

  // Step 2: 核心逻辑（step 间检查提前终止）
  let result: unknown;
  let status: 'success' | 'failed' | 'cancelled' = 'success';
  let error: string | undefined;

  try {
    // 核心处理前检查终止标志
    if (await checkStopFlag(parentInstanceId)) {
      status = 'cancelled';
    } else {
      result = await coreLogicStep(prepared);
    }
  } catch (e) {
    status = 'failed';
    error = e.message;
  }

  // Step 3: 上报结果
  await reportDone(parentInstanceId, instanceIndex, {
    status,
    result,
    error,
  });
}

async function checkStopFlag(parentInstanceId: string): Promise<boolean> {
  const id = do.jcoord.idFromName(`multi-instance-${parentInstanceId}`);
  const stub = do.jcoord.get(id);
  return await stub.checkStopFlag(parentInstanceId);
}

async function reportDone(
  parentInstanceId: string,
  instanceIndex: number,
  output: MultiInstanceOutput
): Promise<void> {
  const id = do.jcoord.idFromName(`multi-instance-${parentInstanceId}`);
  const stub = do.jcoord.get(id);
  await stub.reportDone(`inst-${instanceIndex}`, {
    instanceIndex,
    status: output.status,
    result: output.result ?? null,
    error: output.error ?? null,
    completedAt: Date.now(),
  });
}
```

### 5.3 模板标准化要点

| 要点 | 规范 |
|------|------|
| **入口参数** | `MultiInstanceInput` 统一结构。`parentInstanceId` 用于关联 DO；`instanceIndex` 标识实例序号；`totalInstances` 供子 Workflow 了解自己在批次中的位置。 |
| **出口协议** | `MultiInstanceOutput` 统一结构。`status` 三态（success / failed / cancelled），`result` 和 `error` 互斥。 |
| **提前终止检查** | 核心逻辑执行前调用 `checkStopFlag()`。建议在多步子 Workflow 的每个关键 step 前都插入检查（以 step 为检查粒度）。 |
| **错误处理** | 子 Workflow 内部 try/catch 后统一调用 `reportDone`，确保主 Workflow 不会因子 Workflow 异常而永远无法收到完成通知。 |
| **与 C-011 模板的关系** | C-011 的子 Workflow 模板（parentInstanceId + branchId + payload → reportDone → Result）是 GAP #5 模板的超集简化版。GAP #5 增加 `instanceIndex`、`totalInstances` 和 `checkStopFlag()`，其余结构完全兼容。 |

## 7. 接受/不接受判定

### 7.1 判定结论

**建议不接受此 GAP（即进行补偿）。**

补偿方案：以 C-011 JoinCoordinator DO 为底座，增加完成条件扩展（awaitN、提前终止信号）、分批启动 helper、顺序多实例轻量方案。一期总工作量约 5d。分两阶段交付：P0 覆盖 All complete 并行多实例（高频场景），P1 覆盖 N-of-M + 顺序多实例（中低频场景）。

### 7.2 理由

| 因素 | 分析 |
|------|------|
| **GAP 性质** | 结构性 GAP——CF Workflows 无原生的循环基数、完成条件评估、并行实例启动等能力。这不是配置层缺口。 |
| **业务影响** | 并行多实例（批量审批、批量同步）在自动化场景中是高频需求（C-019 §2.3）。不接受补偿意味着所有批量处理需退化为串行，端到端延迟将随 N 线性增长。 |
| **补偿可行性** | 约 75-80% 补偿基础设施由 C-011 JoinCoordinator DO 直接覆盖，增量工作量约 5d，可控。不存在"无可行补偿"的困境。 |
| **边际收益** | 与 C-011 的 DO 投入形成协同——"一次投入，两项复用"，GAP #1 和 #5 共享 JoinCoordinator 底座。 |
| **风险可控** | 主要风险（大基数瓶颈、完成条件复杂度）均有缓解措施（分批启动上限评估、标准模板策略）。Q1 假设的不确定性通过分阶段交付对冲（P0 覆盖确定的高频场景，P1 在 Q1 答案明确后启动）。 |

### 7.3 分阶段策略

```
P0（一期，约 3.5d）：覆盖 90% 场景
├── DO JoinCoordinator 扩展：awaitN + signalStop + checkStopFlag（1d）
├── batchStartWorkflows helper + cardinalityCalc helper（1d）
├── 并行多实例子 Workflow 模板（基于 C-011 模板扩展）（0.5d）
└── 集成测试 + 标杆流程验证（1d）

P1（二期，约 1.5d）：剩余 10% 场景
├── 顺序多实例 helper（workflow.call() 串行循环）（0.5d）
├── N-of-M / First-N-success 业务场景适配（0.5d）
└── 补充测试（0.5d）
```

**启动前提**：
- C-011 JoinCoordinator DO 的 P0 代码基就绪（register + reportDone + awaitAll）
- Q1 答案建议在 P1 启动前拿到（确认顺序多实例实际占比和复杂完成条件分布），但不阻塞 P0

## 8. 工程风险评估

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| C-011 JoinCoordinator DO 未在 GAP #5 开发时可用 | 中 | **阻塞**——GAP #5 P0 的核心依赖不可用 | 调度级保证：GAP #1 排在 GAP #5 之前；C-011 接口签名已预留 awaitN/signalStop |

## 9. 本期结论

GAP #5 多实例**建议不接受**（即进行补偿）。补偿方案以 C-011 JoinCoordinator DO 为底座，无需重新设计独立聚合器。

**工程方案核心**：
- 复用 C-011 的 register / reportDone / awaitAll，覆盖 All complete 场景（~90%）
- 扩展 awaitN（N-of-M）、signalStop（提前终止），分别 0.5d
- 分批启动 helper 解决大基数启动瓶颈（1d）
- 顺序多实例独立轻量方案：workflow.call() 串行循环（0.5d）
- 子 Workflow 模板在 C-011 模板基础上扩展（0.5d）
- **总工作量：约 5d**（不含表达引擎），分 P0（3.5d）+ P1（1.5d）两阶段交付

**需要决策者确认**：D1（是否启动补偿开发）、D2（是否接受分阶段策略）、D3（暂不实现表达式引擎）、D5（C-011 JoinCoordinator DO 时序保证）。
