## 2. 补偿方案设计

基于 CF Workflows 实际能力边界，设计三条可选补偿路径，从轻到重排列。

### 2.1 引擎能力分析

CF Workflows 可用原语：

| 原语 | 能力 | 与并行网关的相关性 |
|------|------|-------------------|
| `workflow.call()` | 同步调用子 Workflow，传入参数、等待返回 | 可用于启动"分支"（子 Workflow），但默认串行等待 |
| `workflow.start()` | 异步启动子 Workflow，不等待返回 | 可同时启动多个子 Workflow 实现"fork"语义 |
| `workflow.waitForEvent()` | 阻塞当前步骤直到事件到达 | 可用于 Join 场景：等待所有分支完成的信号 |
| `workflow.sleep()` | 阻塞当前步骤指定时长 | 可用于轮询模式中控制检查间隔 |
| `workflow.do()` | 获取绑定到当前 Workflow 的 DO stub | 可用于 DO 聚合器方案中的状态共享 |
| 单 Step 内 `Promise.all()` | 在单个 Step 内并行执行多个异步操作 | 可用于轻量 Fork/Join（无独立子 Workflow 生命周期） |
| Workers `fetch()` | 外部 HTTP 调用 | 并行 API 调用的基础能力 |

---

### 2.2 方案 A：内联并行（Inline Parallelism）

#### 方案描述

在单个 Workflow step 内使用 `Promise.all()` 同时调用多个外部 API，在 step 级别完成 fork/join，不涉及子 Workflow。

```
Step N-1 → Step N: [fetchA, fetchB, fetchC] via Promise.all → Step N+1
```

适用场景：**场景 1（并行调用外部服务）**，且满足以下条件：
- 所有并行操作是外部 API 调用（`fetch`）
- 分支间无依赖关系
- 不需要各分支有独立的生命周期管理（暂停/恢复/重试）
- 总执行时间在单个 step 允许范围内（Workers 的 CPU 时间限制为 30s paid / 15min standard；IO-bound 的 `fetch` 不受此严格限制）

#### 适用场景

| 场景 | 是否适用 | 说明 |
|------|---------|------|
| 场景 1：并行调用外部服务 | ✅ 完全适用 | `Promise.all([fetchA, fetchB, fetchC])` 天然匹配 |
| 场景 3：并行子流程 | ❌ 不适用 | 子流程需要独立生命周期，方案 A 无法实现 |
| 场景 4：并行消息发送 | ✅ 适用 | 多渠道通知/消息并行发送 |

#### 工作量

| 项目 | 时间 |
|------|------|
| 开发标准化模式（template/helper） | 0.5d |
| 现有流程适配 | 0.5d / 流程 |
| 合计（假设 5 个流程使用并行网关） | **约 3d** |

#### 风险等级：低

- 纯代码模式，无额外基础设施
- 无状态一致性问题（单 step 内执行）
- 但不支持单分支失败后的独立重试（全部重试或全部成功）

#### 对现有流程定义的变更影响

- **流程定义**：并行网关的 fork/join 图形被压缩为单个 "parallelCall" step
- **流程结构变更**：中等——BPMN 的 fork→多分支→join 被折叠为单 step，若原流程图包含分支内的多步操作，需全部折叠进一个 step 或改用方案 B/C
- **可读性**：图形化并行语义丢失，需靠 step 命名和注释表达并发意图

---

### 2.3 方案 B：子 Workflow Fork + 简单聚合（Sub-workflow Dispatch + Polling）

#### 方案描述

主 Workflow 使用 `workflow.start()` 异步启动多个子 Workflow（Fork），然后通过轮询 DO 状态等待所有子 Workflow 完成（Join）。

```
Step 0: start(childA), start(childB), start(childC)  ← Fork
Step 1: do.joinCoordinator.awaitAll(["childA", "childB", "childC"])  ← Join
Step 2: do.joinCoordinator.getResults()  ← 聚合结果
Step N: ... 继续主流程
```

每个子 Workflow 完成后调用 `do.joinCoordinator.reportDone(childId, result)`。

聚合器（Durable Object）职责：
- 注册分支（记录需要等待的子 Workflow ID 列表）
- 收集完成信号（每个分支完成后调用 reportDone）
- 判定聚合条件（所有分支完成 / 超时 / 部分失败）
- 存储各分支结果供主 Workflow 读取

#### 适用场景

| 场景 | 是否适用 | 说明 |
|------|---------|------|
| 场景 1：并行调用外部服务 | ⚠️ 过度设计 | 方案 A 足够，方案 B 额外复杂度不必要 |
| 场景 3：并行子流程 | ✅ 完全适用 | 每个分支有独立生命周期，可暂停/恢复/重试 |
| 场景 4：并行消息发送 | ⚠️ 过度设计 | 方案 A 足够 |

#### 工作量

| 项目 | 时间 |
|------|------|
| DO 聚合器（JoinCoordinator）设计实现 | 2d |
| 聚合器超时/部分失败策略 | 1d |
| 子 Workflow 模板（标准化入口+reportDone） | 1d |
| 主 Workflow 调度 helper | 1d |
| 单元测试 + 集成测试 | 1d |
| 现有流程适配 | 0.5d / 流程 |
| **合计** | **约 7-8d**（含测试） |

#### 风险等级：中

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 部分分支失败导致聚合卡住 | 主 Workflow 永久阻塞 | DO 设置超时 + 部分成功策略；失败分支单独标记 |
| DO 状态不一致（如子 Workflow 完成后重试导致重复 report） | 结果计数错误 | DO 内部幂等处理（基于 childId 去重） |
| 子 Workflow 数量多时 DO 并发压力 | 聚合器性能瓶颈 | DO 的 `awaitAll` 基于轮询，不要求高并发写入 |
| 子 Workflow 完成但主 Workflow 未收到通知 | 主流程 hang | 轮询 + 超时双重保障 |

#### 对现有流程定义的变更影响

- **流程定义**：BPMN 并行网关被映射为 "fork" step（启动子 Workflow）+ "join" step（等待聚合）的固定模式
- **分支内容**：每个并行分支从"并行路径"变为独立子 Workflow 文件，分支参数通过 `workflow.start()` 传递
- **可读性**：主流程文件清晰（fork→join），分支逻辑独立文件管理，可维护性中等偏上
- **与后续 GAP 的关系**：方案 B 的 DO 聚合器可直接复用于 GAP #2（包含网关）和 GAP #5（多实例），降低边际成本

### 2.4 方案 C：事件驱动 Fork/Join（Event-driven via waitForEvent）

#### 方案描述

主 Workflow 使用 `workflow.start()` 启动子 Workflow 后，通过 `workflow.waitForEvent()` 阻塞等待，由 DO 聚合器在条件满足时推送事件唤醒主 Workflow。

与方案 B 的区别：
- 方案 B：主 Workflow 主动轮询 DO（轮询间隔造成延迟）
- 方案 C：主 Workflow 被动等待事件（DO 聚合完成后调用 `workflow.sendEvent()` 唤醒主 Workflow，或主 Workflow 的 `waitForEvent` 由外部 webhook 触发）

这是方案 B 的**性能优化版**，消除轮询延迟。

```
Step 0: start(childA), start(childB), start(childC)  ← Fork
Step 1: workflow.waitForEvent("forkJoin.complete")    ← Join（事件驱动）
Step 2: do.joinCoordinator.getResults()               ← 聚合结果
Step N: ... 继续主流程
```

#### 适用场景

与方案 B 相同，额外适用于对 join 延迟敏感的场景（要求分支完成后立即汇合，不接受轮询间隔延迟）。

#### 工作量

| 项目 | 时间 |
|------|------|
| DO 聚合器（含 sendEvent 集成） | 2.5d |
| 聚合器超时/部分失败策略 | 1d |
| 子 Workflow 模板 | 1d |
| 主 Workflow 调度 helper | 1d |
| 事件注册/路由（event type 命名规范 + 解析） | 0.5d |
| 单元测试 + 集成测试 | 1.5d |
| 现有流程适配 | 0.5d / 流程 |
| **合计** | **约 8-10d**（含测试） |

#### 风险等级：中高

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 事件丢失（DO 发送事件时主 Workflow 尚未进入 waitForEvent） | 主 Workflow 永久等待 | DO 存储 "pending event"，waitForEvent 时先查是否有已到达的事件 |
| DO 生命周期与 Workflow 生命周期不同步 | 状态泄漏或过早清理 | DO 设置过期时间 + 主动清理机制 |
| 事件路由错误（多个并行 fork/join 实例的区分） | 错收其他实例的信号 | 事件名包含 workflow instance ID，严格隔离 |
| 复杂度高于方案 B | 维护成本上升 | 仅在对 join 延迟有严格要求的场景使用；大多数场景推荐方案 B |

#### 对现有流程定义的变更影响

与方案 B 一致（流程结构不变，仅 join step 的实现从轮询改为事件驱动）。

## 3. 方案对比分析

### 3.1 多维度对比

| 维度 | 方案 A（内联并行） | 方案 B（轮询聚合） | 方案 C（事件驱动） |
|------|------------------|-------------------|-------------------|
| **工作量** | 3d | 7-8d | 8-10d |
| **风险** | 低 | 中 | 中高 |
| **覆盖场景** | 场景 1、4 | 场景 1、3、4 | 场景 1、3、4 |
| **子 Workflow 独立生命周期** | ❌ | ✅ | ✅ |
| **单分支独立重试** | ❌ | ✅ | ✅ |
| **Join 延迟** | 无（同 step） | 轮询间隔（~秒级） | 事件驱动（~毫秒级） |
| **额外基础设施** | 无 | 1 个 DO 类 | 1 个 DO 类 + 事件路由 |
| **对现有流程定义的影响** | 中等（折叠 fork/join） | 中等（映射为独立子 Workflow） | 与 B 相同 |
| **与 GAP #2/#5 的复用性** | 低 | 高 | 高 |
| **运维复杂度** | 低 | 中 | 中高 |

### 3.2 取舍建议

**推荐策略：方案 A + 方案 B 分层采用，放弃方案 C**

1. **方案 A 作为默认首选**——覆盖 80% 的并行网关使用场景（场景 1：并行 API 调用）。优势在于零基础设施、低风险、低工作量。对现有流程的改造是"折叠"而非"重构"，学习成本低。

2. **方案 B 作为复杂场景补充**——覆盖需要子 Workflow 独立生命周期的场景（场景 3：并行子流程）。仅在方案 A 无法满足时升级到方案 B。

3. **方案 C 不推荐**——额外引入事件丢失和路由错误的风险，工作量增加 1-2d，收益（消除轮询延迟）在自动化场景中价值有限。秒级轮询延迟对业务流程完全可接受。

**分层决策流程：**

```
并行网关使用场景
├── 场景 1（并行 API 调用）→ 方案 A
├── 场景 4（并行消息发送）→ 方案 A
└── 场景 3（并行子流程）
    ├── 子流程逻辑简单，可内联化 → 方案 A
    └── 子流程需独立生命周期 → 方案 B
```

## 4. 接受/不接受判定

### 4.1 判定结论

**建议不接受此 GAP（即进行补偿），分层采用方案 A + 方案 B。**

### 4.2 理由

| 因素 | 分析 |
|------|------|
| **GAP 性质** | 结构性 GAP——CF Workflows 引擎模型与 BPMN 的 Token-based 并发模型根本不同。这不是配置层缺口，是架构层缺口。 |
| **业务影响** | 并行网关在自动化场景中有实际需求（并行 API 调用、批量消息发送、订单拆分并行处理）。若不做任何补偿（接受 GAP），所有并行逻辑需退化为串行，端到端延迟将线性增长。 |
| **补偿可行性** | 方案 A 覆盖最常见场景的成本极低（3d），方案 B 覆盖复杂场景的成本可控（7-8d）。不存在"无可行补偿"的困境。 |
| **边际收益** | 方案 B 的 DO 聚合器可复用于 GAP #2（包含网关）和 GAP #5（多实例），边际成本递减。并行网关的补偿基础设施是后续多项高 GAP 补偿的共同基础。 |
| **风险可控** | 方案 A 零风险；方案 B 有中等风险（部分失败处理），但都有明确的缓解措施。没有不可控的系统性风险。 |
| **团队能力** | DO、Workflows、`workflow.start()`/`waitForEvent()` 均为 CF 标准能力，团队无需学习额外技术栈。 |

### 4.3 若不接受 GAP，对应的工程计划

#### 阶段与里程碑

```
Phase 1：内联并行模式标准化（W1，约 3d）
├── D1-2：parallelCall() helper 开发
│   ├── 输入：API 调用配置数组 [{url, method, headers, body, timeout}]
│   ├── 输出：{results: [...], errors: [...], allOk: boolean}

├── D3：现有流程中场景 1/4 的适配验证
│   └── 选取 1 个标杆流程完成适配并验证端到端正确性
└── 里程碑 M1：方案 A 开发完成，可用于场景 1/4 的并行 API 调用

Phase 2：DO 聚合器开发（W2-W3，约 7-8d）
├── D1-3：JoinCoordinator DO 实现
│   ├── 核心接口：register(instanceId, childIds), reportDone(childId, result), awaitAll()
│   ├── 超时策略：全局超时 + 部分成功
│   ├── 幂等处理：同一 childId 重复 reportDone 不重复计数
│   └── 单元测试
├── D4-5：子 Workflow 模板开发
│   ├── 标准化入口：接收 parentInstanceId + branchId + payload
│   ├── 标准化出口：reportDone + 返回统一结构
│   └── 单元测试
├── D6：主 Workflow fork/join helper
│   ├── fork(): 批量 workflow.start()
│   ├── join(): 调用 DO.awaitAll() 轮询
│   └── 集成测试
├── D7-8：端到端测试 + 场景 3 标杆流程适配验证
└── 里程碑 M2：方案 B 开发完成，并联动作的场景 3

Phase 3：全量流程适配（W4+，按需）
├── 逐个流程评审并行网关使用情况（回答 Q1）
├── 按分层决策流程为每个流程选择方案 A 或 B
├── 改造 + 验证
└── 里程碑 M3：所有使用并行网关的流程完成适配
```

| 阶段 | 工作量 | 建议角色 |

#### 与其他高 GAP 的依赖关系

```
GAP #1（本期）
├── 方案 B 的 DO 聚合器  ──复用于──→ GAP #2（包含网关）
├── 方案 B 的 DO 聚合器  ──复用于──→ GAP #5（多实例）
```

| D4 | Q1（现有流程并行网关使用模式）是否需要在本期补偿开发启动前完成统计？ | 需要 / 可延后 | **可延后到 Phase 3**——方案 A 覆盖 80% 场景，其余场景在适配时逐流程评审即可 |

### 5.3 本期结论

GAP #1 并行网关**建议不接受**（即进行补偿）。推荐分层方案：方案 A（内联并行，3d）覆盖最常见的并行 API 调用场景；方案 B（DO 聚合器 + 子 Workflow，7-8d）覆盖复杂并行子流程场景。DO 聚合器作为共享基础设施，可复用于 GAP #2 和 #5，总工作量约 12-15d（含 5 个流程适配）。

在开发启动前，需决策者确认 D1-D4 四项事项。
