## 1. 假设验证

### 1.1 CF Workflows 文档验证（Q2, Q3）

通过查阅 CF Workflows 最新文档（2026-05），关键能力验证如下：

**Q2：`waitForEvent()` 是否支持同时等待多个事件类型？**

| 项目 | 结论 |
|------|------|
| 单次 `waitForEvent` | 仅支持单一 `type` 参数（`{ type: "cancel", timeout: "..." }`） |
| 多事件等待方案 | ✅ 使用 `Promise.race([step.waitForEvent("a", {...}), step.waitForEvent("b", {...})])` |
| 官方文档引用 | "This allows you to wait for multiple events at once, or use `Promise.race` to wait for multiple events" |
| short-timeout 轮询方案 | ✅ `try { await step.waitForEvent("check", { type: "cancel", timeout: "1s" }); } catch { /* 继续 */ }` |

**Q3：`sleep()` 或 `waitForEvent()` 期间是否可通过外部 `sendEvent()` 唤醒？**

| 项目 | 结论 |
|------|------|
| `waitForEvent` + `sendEvent` | ✅ 核心设计——`sendEvent` 唤醒匹配的 `waitForEvent` |
| 事件缓冲机制 | ✅ **关键发现**：事件可在 `waitForEvent` 到达前发送，CF 缓冲并即时交付——"You can send an event to a Workflow instance _before_ it reaches the corresponding `waitForEvent` call" |
| `sleep()` 期间被事件唤醒 | ❌ 文档未提及——`sleep()` 应完成其 duration 后才继续 |

**对方案设计的关键影响**：
- 中断检查点模式成立：外部 cancel 信号可在 workflow 仍在 `step.do` 中时发送，CF 缓冲后在 `waitForEvent` 到达时立即交付，无额外延迟
- `Promise.race` 多事件等待模式成立，可同时监听 "cancel" + "timeout" + "approval" 等
- short-timeout 轮询模式成立：`waitForEvent({type: "cancel", timeout: "1s"})` + try/catch 可实现 step 边界的非阻塞中断检查

### 1.3 假设验证结论

**确认的关键能力**：CF Workflows 的事件缓冲机制（pre-waitForEvent sendEvent）是方案设计的核心使能器。这意味着中断信号的"提前到达"不会丢失，方案设计的焦点集中在"如何让 step 边界检查足够紧凑"而非"如何处理先行到达的信号"。

**唯一硬限制仍在 P2**：step 执行中不可中断。所有方案都需要 step 粒度设计作为配套。

## 3. 方案 A——轻量补偿：step 边界检查点模式

### 3.1 方案描述

在每个 step 之后插入中断检查点，使用 CF Workflows 原生能力，不引入独立 DO。

**核心模式**：

```typescript
async run(event: WorkflowEvent, step: WorkflowStep) {
  // === Step N ===
  await step.do("step N", async () => { /* 业务逻辑 */ });

  // === 中断检查点 ===
  const interruptEvent = await checkInterrupt(step, {
    eventTypes: ["cancel"],
    checkDelayMs: 1000,  // short-timeout 轮询间隔
  });

  if (interruptEvent) {
    if (interruptEvent.type === "cancel") {
      await handleCancel(step, interruptEvent.payload);
      return;  // 流程结束
    }
  }

  // === Step N+1 ===
  await step.do("step N+1", async () => { /* 业务逻辑 */ });

  // ... 继续
}
```

**`checkInterrupt()` helper 实现**：

```typescript
async function checkInterrupt(
  step: WorkflowStep,
  opts: { eventTypes: string[]; checkDelayMs: number }
): Promise<InterruptEvent | null> {
  try {
    const result = await step.waitForEvent("interrupt check", {
      type: opts.eventTypes[0],
      timeout: `${Math.ceil(opts.checkDelayMs / 1000)} seconds`,
    });
    return { type: opts.eventTypes[0], payload: result };
  } catch {
    return null;  // timeout → 无中断信号
  }
}
```

**多事件版本（Promise.race）**：

```typescript
async function checkMultiInterrupt(
  step: WorkflowStep,
  opts: { eventTypes: string[]; checkDelayMs: number }
): Promise<InterruptEvent | null> {
  const duration = `${Math.ceil(opts.checkDelayMs / 1000)} seconds`;
  const races = opts.eventTypes.map(type =>
    step.waitForEvent(`check ${type}`, { type, timeout: duration })
  );
  try {
    const result = await Promise.race(races);
    // 找到哪个 type 赢了
    // 注：Promise.race 无法直接知道哪个 promise 获胜，
    //   实际实现中需包装为 { type, value } 结构
    return wrapRaceResults(opts.eventTypes, races);
  } catch {
    return null;
  }
}
```

### 3.2 适用场景

| 场景 | 是否适用 | 说明 |
|------|---------|------|
| 场景 1：外部取消指令（Message 中断型） | ✅ | `sendEvent({type: "cancel", payload: {reason}})` → `checkInterrupt` 捕获 |
| 场景 2：全局超时取消（Timer 中断型） | ✅ | 外部 Cron Trigger 或 sleep 完成后 `sendEvent({type: "timeout"})` |
| 场景 3：配置/策略热更新（Signal 非中断型） | ⚠️ 不适用 | 非中断型不通过 waitForEvent 实现——用 DO 状态标记 + step 边界查询（见方案 B 非中断型模式） |
| 场景 4：外部状态变更通知（非中断型） | ⚠️ 不适用 | 同场景 3 |
| 场景 5：补偿触发（Compensation 中断型） | ❌ 归入 GAP #8 | Saga 编排器接管 |

### 3.3 中断处理模板

```typescript
async function handleCancel(step: WorkflowStep, payload: CancelPayload) {
  await step.do("log cancellation", async () => {
    await log.info("workflow cancelled", { reason: payload.reason });
  });

  // 如有需要：清理 DO 状态
  if (payload.cleanupRequired) {
    await step.do("cleanup resources", async () => {
      await doMap.delete(workflowInstanceId);
    });
  }

  // 如有需要：触发 Saga 补偿链（对接 GAP #8）
  if (payload.compensationRequired) {
    await step.do("trigger saga compensation", async () => {
      await sagaCoordinator.triggerCompensation(workflowInstanceId);
    });
  }

  // 终止：return/throw from run()
}
```

### 3.4 风险等级：低

| 风险 | 影响 | 缓解 |
|------|------|------|
| 短超时轮询在每个 step 边界增加固定延迟 | 端到端延迟增加 N × checkDelayMs | checkDelayMs 默认 1s，5 个 step 仅增加 5s |
| short-timeout 的 timeout 被误判为 "无中断" | 正常——轮询语义，下次 step 边界再次检查 | 无风险 |
| waitForEvent 的 short timeout 无法区分 "无事件" 和 "真正的超时异常" | 两者用 try/catch 统一处理为 "继续执行" | 若确实需要区分，使用 Promise.race 多事件方案 |

### 3.5 对现有流程的变更影响

| 维度 | 影响 |
|------|------|
| 流程结构 | 每个 step 后插入 `checkInterrupt` 调用——约 1-3 行代码/step |
| 可读性 | 检查点一目了然，不混淆业务逻辑 |
| 迁移方式 | pattern-based 插入：对每个使用事件子流程的流程，在 step 间插入检查点 |

## 4. 方案 B——完整补偿：DO InterruptCoordinator

### 4.1 方案描述

引入 DO InterruptCoordinator 作为中断信号的管理中心，提供统一的：信号暂存主动管理、多事件优先级、超时策略、中断/非中断型统一接口、生命周期管理。

方案 B 不是替代方案 A，而是方案 A 的**增强层**——在基础检查点模式上叠加 DO 协调能力。

**核心架构**：

```
外部系统
   │
   │ sendEvent({type: "cancel", payload: {...}})   ← CF 原生缓冲
   │  或
   │ DO.interruptCoordinator.signal(instanceId, {type: "cancel", ...})  ← DO 主动信号
   │
   ▼
CF Workflows 实例
   │
   │ step.do("work") → checkInterrupt(step) → DO.checkFlags()  ← 双重检查
   │                   ├── waitForEvent 唤醒（方案 A 机制）
   │                   └── DO 中断标志查询（方案 B 增强）
   │
   ▼
中断处理步骤序列
   │
   ▼
流程结束 / 恢复 / Saga 补偿
```

### 4.2 InterruptCoordinator DO 接口设计

```typescript
interface InterruptCoordinator {
  // === 中断信号管理 ===

  /**
   * 发送中断信号到指定 workflow 实例
   * 调用方：外部系统、sendEvent handler、Cron Trigger
   */
  signal(instanceId: string, signal: InterruptSignal): Promise<void>;

  /**
   * 查询是否有待处理的中断信号
   * 调用方：step 边界 checkInterrupt() helper
   * 返回：时间序最早的高优中断信号，无则 null
   */
  check(instanceId: string): Promise<InterruptSignal | null>;

  /**
   * 确认中断信号已处理（消费）
   * 防止重复处理
   */
  acknowledge(instanceId: string, signalId: string): Promise<void>;

  // === 中断监听注册 ===

  /**
   * 注册该 workflow 实例对哪些事件类型感兴趣
   * 调用方：workflow 初始化时
   */
  registerInterests(instanceId: string, eventTypes: string[]): Promise<void>;

  /**
   * 查询已注册的事件类型（用于 checkInterrupt 确定 waitForEvent type）
   */
  getInterests(instanceId: string): Promise<string[]>;

  // === 非中断型事件管理 ===

  /**
   * 发布非中断型事件（不打断主流程，仅状态通知）
   * 调用方：外部系统或 Signal handler
   */
  publishNonInterrupting(instanceId: string, event: NonInterruptingEvent): Promise<void>;

  /**
   * 获取并清理已消费的非中断型事件
   * 调用方：step 边界查询（不阻塞主流程）
   */
  consumeNonInterrupting(instanceId: string): Promise<NonInterruptingEvent[]>;

  // === 生命周期管理 ===

  /**
   * 清理指定实例的所有中断状态
   * 调用方：workflow 完成或终止时
   */
  cleanup(instanceId: string): Promise<void>;

  /**
   * 设置 DO 的自动过期（兜底清理，防止泄漏）
   */
  setTTL(instanceId: string, ttlSeconds: number): Promise<void>;
}

interface InterruptSignal {
  id: string;            // 信号唯一标识（幂等去重）
  type: string;          // cancel / timeout / config-update / ...
  priority: SignalPriority;
  payload: Record<string, unknown>;
  timestamp: number;
  ttl: number;           // 信号有效期（秒）
}

enum SignalPriority {
  LOW = 0,
  MEDIUM = 1,
  HIGH = 2,        // cancel 类
  CRITICAL = 3,    // 系统级强制终止
}

interface NonInterruptingEvent {
  id: string;
  type: string;
  payload: Record<string, unknown>;
  timestamp: number;
}
```

### 4.3 InterruptCoordinator 状态机

```
DO 中每个 workflow 实例维护以下状态：

States:
  IDLE        — 无中断信号，主流程正常运行
  SIGNALED    — 有中断信号已到达，等待主流程在 step 边界查询
  PROCESSING  — 主流程已获取中断信号，正在执行中断处理步骤
  RESOLVED    — 中断已处理完成（已 acknowledge）
  CLEANED     — DO 状态已清理

Transitions:
  IDLE → SIGNALED        signal() 被调用
  SIGNALED → PROCESSING  check() 返回中断信号（主流程获取）
  PROCESSING → RESOLVED  acknowledge() 确认处理完成
  SIGNALED → SIGNALED    signal() 再次调用（多信号排队，按 priority + timestamp 排序）
  RESOLVED → CLEANED     cleanup() 或 过期自动清理
```

### 4.4 step 边界 checkInterrupt（方案 B 增强版）

```typescript
async function checkInterruptEnhanced(
  step: WorkflowStep,
  do: InterruptCoordinator,
  instanceId: string,
  opts: { pollDelayMs: number }
): Promise<InterruptSignal | null> {
  // 1. 优先检查 DO 中是否有已缓存的中断信号（零延迟，不进入 waitForEvent）
  const cachedSignal = await do.check(instanceId);
  if (cachedSignal) {
    return cachedSignal;
  }

  // 2. 若无缓存信号，进入 waitForEvent short-timeout 轮询
  //    同时监听 sendEvent 可能推送到 waitForEvent 的原生事件
  try {
    const event = await step.waitForEvent("interrupt check", {
      type: "cancel",  // 可从 DO.getInterests() 获取动态列表
      timeout: `${Math.ceil(opts.pollDelayMs / 1000)} seconds`,
    });

    // sendEvent 到达 → 同时写入 DO（用于后续查重）
    const signal: InterruptSignal = {
      id: crypto.randomUUID(),
      type: "cancel",
      priority: SignalPriority.HIGH,
      payload: event as Record<string, unknown>,
      timestamp: Date.now(),
      ttl: 300,
    };
    await do.signal(instanceId, signal);
    return signal;
  } catch {
    return null;
  }
}
```

### 4.5 中断型 vs 非中断型分层策略

| 维度 | 中断型 | 非中断型 |
|------|--------|---------|
| **触发 effect** | 打断主流程正常执行 | 不影响主流程——并行记录/更新 |
| **实现模式** | `checkInterrupt()` → 捕获信号 → 执行中断处理 → 流程结束/恢复 | step 边界 `consumeNonInterrupting()` → 应用状态变更 → 继续 |
| **延迟要求** | 低延迟（≤ step 执行时长 + checkDelayMs） | 容忍延迟（step 边界即可，无需 waitForEvent 轮询） |
| **DO 使用** | signal/check/acknowledge 全流程 | publishNonInterrupting/consumeNonInterrupting |
| **waitForEvent** | ✅ 用于原生事件捕获 | ❌ 不阻塞，仅 DO 查询 |

**分层策略建议**：中断型走方案 B 完整路径（DO + waitForEvent 双重保障）；非中断型走极简路径（DO 状态标记 + step 边界读取），开发成本可忽略。

### 4.6 DO 作为信号缓冲区 vs CF 原生缓冲的定位

| 机制 | 用途 | 备注 |
|------|------|------|
| CF 原生事件缓冲（sendEvent + waitForEvent） | 唤醒处于 step 边界的 workflow | 平台级缓冲，零代码 |
| DO InterruptCoordinator | 多事件优先级、信号去重、超时管理、历史记录、非中断型事件存储 | 应用级管理 |

**结论**：两者互补而非替代。CF 原生缓冲负责"即时唤醒"，DO 负责"信号管理"。方案 A 只用前者，方案 B 叠加后者。

### 4.7 风险等级与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| DO signal() 与 sendEvent() 重复投递 | 中断信号被处理两次 | 中 | DO.acknowledge() 幂等处理；信号 id 去重 |
| DO 状态泄漏（workflow 异常终止未清理） | DO 中残留过期实例状态 | 中 | DO.setTTL() 自动过期；定期清理脚本扫描 |
| 多中断信号并发时的优先级错乱 | 低优信号先于高优信号被处理 | 低 | DO check() 按 priority → timestamp 排序，高优先返回 |
| DO 故障导致 check() 失败 | step 边界检查阻塞 | 低 | checkInterrupt 中 DO 调用失败不抛异常，降级为仅 waitForEvent 轮询 |
| 中断处理步骤自身也长时间执行 | 中断处理过程中又收到新信号 | 低 | INTERRUPT DURING INTERRUPT: 中断处理中不检查中断，先完成当前处理 |

### 4.8 与 Saga 编排器（GAP #8）的接口预留

```typescript
interface SagaIntegration {
  /**
   * 中断信号标记"是否需要触发 Saga 补偿"
   */
  signal: InterruptSignal & {
    compensationRequired?: boolean;
    compensationScope?: "all" | "since-last-snapshot" | "custom";
    compensationSteps?: string[];  // 指定需补偿的 step 列表
  };

  /**
   * InterruptCoordinator 在 acknowledge 后，如标记 compensationRequired
   * 调用 SagaCoordinator.triggerCompensation()
   */
  triggerCompensation(instanceId: string, scope: CompensationScope): Promise<void>;
}
```

GAP #8 的 Saga 编排器需实现：
- `triggerCompensation(instanceId, scope)` — 根据已执行步骤列表，逆序调用各 step 的 compensate 回调
- InterruptCoordinator 在接收到 `compensationRequired: true` 的中断信号并完成中断处理后，调用此接口

**本期不设计 Saga 编排器细节**，仅预留接口定义。

## 5. 方案对比

### 5.1 多维度对比

| 维度 | 方案 A（轻量检查点） | 方案 B（DO InterruptCoordinator） |
|------|---------------------|----------------------------------|
| **工作量** | 1-2d（helper 开发） + step 粒度重构按需 | 5-7d（DO 实现 + helper + 测试） |
| **风险** | 低 | 中 |
| **覆盖场景** | 中断型 Message/Timer 场景 1、2 | 所有中断型 + 非中断型（场景 1-4） |
| **额外基础设施** | 无 | 1 个 DO 类（InterruptCoordinator） |
| **中断响应延迟** | step 执行时长 + checkDelayMs（~1s） | step 执行时长 + 0ms（DO check 零延迟）|
| **多事件支持** | Promise.race 多 waitForEvent | DO 优先级队列 + Promise.race |
| **非中断型支持** | ❌ 需额外实现 | ✅ 内置 publish/consume |
| **信号管理能力** | 依赖 CF 原生缓冲 | DO 优先级 + 去重 + 超时 + 历史 + 主动缓存 |
| **运维复杂度** | 极低 | 低（单个 DO，不涉及额外服务） |
| **与 GAP #6 复用** | 无 | 非中断型 DO 检查模式可部分复用 |
| **与 GAP #8 接口** | 手动在中断 handler 中调用 | InterruptCoordinator 预留 Saga 接口 |
| **对现有流程的影响** | 插入 checkInterrupt 调用 | 同左 + DO 初始化/清理两步 |

### 5.2 方案选择标准

```
中断型事件子流程需求
├── 仅响应简单的 "cancel" 事件（单事件类型） → 方案 A
├── 需响应多种中断事件且有优先级 → 方案 B
├── 同时有非中断型事件需求 → 方案 B
├── 需要中断信号的可观测性（审计/日志） → 方案 B
└── step 数量多且 checkDelayMs 的累积延迟不可接受 → 方案 B（DO 零延迟 check）
```

### 5.3 推荐策略

**推荐：方案 A 为基线，方案 B 按需增强**

- **方案 A** 覆盖 80% 场景——使用 `checkInterrupt()` helper 在每个 step 后插入中断检查，零基础设施
- **方案 B** 仅在有明确需求时启用——多事件优先级、非中断型事件、或对 checkDelayMs 累积延迟敏感

**论据**：
- 方案 A 已由 CF 原生事件缓冲机制强力支撑——外部 cancel 信号可在 step 执行中发出，CF 平台缓冲，step 边界瞬时交付
- scheme B 的附加值在于"管理能力"（优先级、去重、多事件协同）而非"可行性"——若业务不需要管理能力，方案 A 已充分满足
- 方案 B 可作为 Phase 2 渐进增强，不与方案 A 的 Phase 1 冲突

## 6. Step 粒度设计指南

### 6.1 P2 硬限制的缓解原则

> P2：CF Workflows step 执行期间不可被中断。中断只能在 step 边界响应。

**核心原则：将长时间执行的操作拆分为多个短 step，每个 step 完成后检查中断信号。**

### 6.2 规范化 step 拆分策略

| 场景 | 当前设计（反模式） | 推荐设计 |
|------|-------------------|---------|
| 长时间 API 调用 | `await step.do("big-fetch", async () => { await fetch(...) })` — 单 step 阻塞 30s | `await step.do("fetch-part-1", paginatedFetch(1))` → checkInterrupt → `await step.do("fetch-part-2", paginatedFetch(2))` |
| 批量数据处理 | 单 step 处理 1000 条记录 | 每 100 条一个 step，step 间 checkInterrupt |
| 等待外部审批 | `await step.sleep("wait", "30 days")` — 30 天不可中断 | `await step.waitForEvent("approval", { type: "approved", timeout: "30 days" })` — 可被 sendEvent 立即唤醒 |
| 链式多个 API 调用 | 单 step 内链式调用 5 个 API | 每个 API 一个 step，step 间 checkInterrupt（同时提高重试粒度和可观测性） |

### 6.3 拆分阈值建议

| 参数 | 建议值 | 理由 |
|------|--------|------|
| 单 step 推荐执行时长 | ≤ 5s | 中断响应延迟可接受 |
| 单 step 最大执行时长 | ≤ 30s | 避免接近 CPU 超时限制；超过 30s 强制拆分 |
| step 间 checkInterrupt 延迟 | 1s | 几乎可忽略的感知延迟 |
| 中断响应最坏总延迟 | step 执行时长 + 1s | 设计目标：≤ 6s（5s step + 1s check） |

### 6.4 与 sleep/等待类 step 的交互

```typescript
// ❌ 反模式：sleep 期间不可被中断唤醒
await step.sleep("wait 1 hour", "1 hour");
await checkInterrupt(step, { eventTypes: ["cancel"] });

// ✅ 推荐：使用 waitForEvent 替代 sleep，可被 sendEvent 即时唤醒
try {
  await step.waitForEvent("wait with cancel", {
    type: "timer-continue",
    timeout: "1 hour",
  });
  // 正常超时→继续
} catch {
  // timeout → 继续
}
await checkInterrupt(step, { eventTypes: ["cancel"] });

// ✅ 更好的方案：Promise.race 同时等待继续和取消
const result = await Promise.race([
  step.waitForEvent("cancel check", { type: "cancel", timeout: "1 hour" }),
  step.waitForEvent("continue check", { type: "timer-continue", timeout: "1 hour" }),
]);
```

### 6.5 反模式与注意事项

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 在 step.do callback 内部 `while(true)` 循环 | 永不退出的 step，中断永远无法响应 | 循环改为多次 step.do 迭代，每次迭代后检查中断 |
| 将多个不相关操作合并为一个 step | step 执行时间过长，中断延迟放大 | 正交操作拆分为独立 step，每个 step 后检查 |
| 中断处理步骤（handler）内部不再设置检查点 | 中断处理中收到新中断无法响应（虽罕见但存在） | 中断处理步骤超过 3 个时，在 handler 内部也插入 checkInterrupt |
| 使用 `step.sleep` 作为"等待被中断"的手段 | sleep 不可被 sendEvent 唤醒 | 使用 `step.waitForEvent` 替代 |

## 8. 接受/不接受判定

### 8.1 判定结论

**建议不接受此 GAP（即进行补偿），采用方案 A 为基线。**

### 8.2 理由

| 因素 | 分析 |
|------|------|
| **GAP 性质** | 结构性 GAP——BPMN 事件子流程的"全局事件监听 + 任意时刻中断"语义与 CF Workflows 的 step 原子执行模型存在根本差异 |
| **硬限制** | P2（step 执行中不可中断）无法通过补偿消除，但可通过 step 粒度设计（§6）将中断响应延迟控制在 ≤ 6s |
| **补偿可行性** | CF Workflows 原生事件缓冲机制是强大的使能器——外部中断信号可在 step 执行中发出、由平台缓冲、在 step 边界即时交付。方案 A 的核心仅需在每个 step 后插入约 1-3 行代码 |
| **工作量可接受** | 方案 A 基础开发 3d，方案 B DO 按需 6d。即使完整方案 A+B 也仅约 10.5d，在 8 项高 GAP 的 30-45d 总预算中占比合理 |
| **风险可控** | 方案 A 零新基础设施，方案 B 单个 DO。两者均有明确的故障降级策略（DO 故障 → 降级为纯 waitForEvent） |
| **业务影响** | 自动化场景中的外部取消指令（场景 1）是业务正确性的硬需求——不能取消的运行流程会产生错误业务结果。不做任何补偿（接受 GAP）不可接受 |
