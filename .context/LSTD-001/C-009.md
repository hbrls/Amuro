## 2. 核心问题识别

### 2.1 并行网关的本质

并行网关（Parallel Gateway）是 BPMN 2.0 的核心分支/合并构造：

| 方向 | 语义 | 行为 |
|------|------|------|
| Fork（分裂） | 流程到达后，同时激活所有出边 | 并发执行所有分支，不等待 |
| Join（汇聚） | 等待**所有**入边到达后，才继续 | 同步等待，所有分支完成后汇合 |

关键属性：
- Fork 后多个执行路径**同时**推进
- Join 必须等**所有**入边到达（不同于包含网关）
- 不依赖条件判断（不同于排他网关）

### 2.2 核心冲突

Cloudflare Workflows 的引擎模型与 Flowable/BPMN 有根本差异：

| 维度 | Flowable (BPMN) | Cloudflare Workflows | GAP 等级 |
|------|-----------------|---------------------|---------|
| 执行模型 | Token-based 图遍历 | Step/step 线性执行 | 高 |
| 并发机制 | 天然支持多 token 并发 | 单执行路径，无原生 fork/join | 高 |
| 同步原语 | Join 自动等待所有 token | 无内置等待多路机制 | 高 |
| 事务边界 | 每个 token 独立事务 | 整个 workflow 单次执行 | 中 |
| 状态管理 | 引擎管理 token 状态 | 开发者自行管理 | 高 |

**结论**：并行网关是结构性 GAP，不是简单配置映射可以解决的。它触及 BPMN 引擎与 CF Workflows 在**并发执行模型**上的根本差异。

### 2.3 自动化场景下的影响分析

根据已知约束（自动化场景为主，人工审核忽略），并行网关在自动化场景中的典型使用包括：

1. **并行调用外部服务**：同时调用多个 API，汇合结果后继续（如：同时查库存+查价格+查用户等级）
2. **并行审批**（可忽略，人工审核场景）
3. **并行子流程**：同时启动多个子流程（如：订单拆分为多子单并行处理）
4. **并行消息发送**：同时发送多渠道通知

对于场景 1、3、4，并行网关的作用是**缩短端到端延迟**和**表达业务并发语义**。

## 5. Goal LENS 视角结论

### 5.1 结论

**本期目标清晰且可执行**。GAP #1 并行网关是 8 项高 GAP 中优先级最高的一项，也是触及引擎模型差异的**结构性 GAP**。

建议从以下两条主线推进本期分析：

1. **现状调研**：梳理现有 Flowable 流程中使用并行网关的实际场景和模式（回答 Q1），这是后续所有讨论的事实基础。
2. **补偿方案探索**：基于 CF Workflows 引擎能力边界，设计可能的补偿路径，评估工作量和风险。

### 5.2 关键提醒

- 并行网关的补偿方案可能直接影响后续 GAP #2（包含网关）和 GAP #5（多实例）的补偿设计，因为它们共享"并发/分支/汇聚"底层语义。
- **本期目标不包括**产出最终补偿方案或工程排期——那是后续 LENS（如 solution、architecture）的任务。本期聚焦于：明确影响范围 + 勾勒可选补偿方向 + 给出接受/不接受的初步判断依据。
