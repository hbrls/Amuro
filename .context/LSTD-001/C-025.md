## 2. 中断型定时器：标准化模式设计

### 2.1 核心工程判断

C-023 §3.3 的结论成立：**中断型定时器在 code-as-workflow 范式中是一种"设计模式"而非"基础设施缺口"**。理由：

1. HTTP call 超时由 `fetch` 的 `AbortSignal.timeout()` 处理（CF Workers 内建）
2. step 执行超时可用 "sleep + 状态检查" 模式表达
3. Workflow 总超时（execution timeout）可通过 CF Workflows 配置设定

本节的工程命题是：**将"sleep + 状态检查"提炼为标准化、可复用的模式，降低每个流程的改造工作量。**

### 2.2 标准 Pattern：step 间超时检查

#### 2.2.1 模式定义

```
Step X（被定时的活动）
    ↓
Step X+1: checkTimeout(startTime, timeoutMs)  ← 检查点（标准插入点）
    ├── 未超时 → Step X+2（正常路径）
    └── 已超时 → Step Y（替代路径 / 定时边界事件出口）
```

**核心约束**：BPMN 定时边界事件的"边界"语义（附着在活动上、与活动并行监听）无法在 CF Workflows 中直接表达。替代方案是**将超时检查显式化为 step 间检查点**。这意味着：
- 被定时的活动必须拆分为可检查的 step 序列
- 超时检查的粒度 = step 间检查点数量 = 被定时 activity 的 step 数

#### 2.2.2 checkTimeout 契约

```typescript
interface TimeoutCheck {
  startTime: number;       // Date.now() 或从 DO 读取的活动开始时间
  timeoutMs: number;       // 超时时长（ms）
  alternativePath: string; // 超时后跳转的 step 名称或路由标识
}

function checkTimeout(check: TimeoutCheck): 'continue' | 'timeout' {
  if (Date.now() - check.startTime > check.timeoutMs) {
    return 'timeout';
  }
  return 'continue';
}
```

#### 2.2.3 模式变体

| 变体 | BPMN 对应 | CF Workflows 实现 |
|------|----------|-------------------|
| **单检查点** | 定时器附着在单 step 活动上 | 在该 step 后插入 1 个 `checkTimeout` step |
| **多检查点（粗粒度）** | 定时器附着在多 step 子流程上 | 在子流程的每个 step 后插入 `checkTimeout` step |
| **多检查点（细粒度）** | 同上，但精确度要求高 | 在 step 内部的关键操作后也进行时间检查（非标准 pattern，按流程自定义） |
| **sleep-based（简化版）** | 被定时的活动本身是快速操作，超时是主要逻辑 | 用 `workflow.sleep(timeoutMs)` 代替精确检查——直接 sleep 到超时时间，然后检查被定时的 step 是否已完成（通过状态标记） |

#### 2.2.4 简化版 sleep-based pattern（推荐默认首选）

对于最常见的"外部 API 调用 + 超时保护"场景，实际上 `fetch` 已内置 timeout 能力，不需要 Workflow 层面的超时语义。对于"内部逻辑 step + 超时保护"，简化版更实用：

```typescript
// 被定时的 step
const startTime = Date.now();
await doLogicStep(input);

// 定时边界：sleep 到超时边界 + 状态检查
const elapsed = Date.now() - startTime;
const remaining = TIMEOUT_MS - elapsed;
if (remaining > 0) {
  await workflow.sleep(remaining);
}

// 超时后检查：被定时的 step 是否真的完成了？
// 由于 CF Workflows 无法中断已完成的 step，此 pattern 只在"被定时的 step 执行时间 < timeout"时有意义
```

**但是**——如果被定时的 step 在 sleep 之前已经完成，sleep + 状态检查就变成了无效等待，且超时路径永远不会被执行。这说明 **sleep-based pattern 仅在"被定时的 step 执行时间 > timeout"时有意义**，而这是一个矛盾（step 在执行中无法被 sleep 中断）。

**因此**：sleep-based pattern 的实际适用场景是 **"step 本身包含异步等待且 step 执行时长不确定"** 的情况。对于纯同步/CPU-bound step，CF Workflows 无法在执行中检查超时。

### 2.3 实际有效 Pattern：手工拆分 + 循环检查

基于以上分析，中断型定时器在 CF Workflows 中的实际可行模式是：

```
被 BPMN 定时边界包裹的 activity
    ↓ 在 CF Workflows 中分解为
Loop: 
  Step A: 执行一小段逻辑（如单次 API 调用、单条记录处理）
  Step B: checkTimeout(startTime, timeoutMs)
    ├── 未超时 → 继续 Loop（处理下一个迭代）
    └── 已超时 → Step Z（超时替代路径）
```

此模式的核心是**将长时间运行的 activity 分解为多次迭代，每次迭代后检查超时**。这适用于：
- 批量处理场景（每批处理后检查超时）
- 多步骤子流程（每个子 step 后检查超时）
- HTTP API 调用（`fetch` 自带 timeout，不需要额外检查）

#### 2.3.1 标准 helper：`withTimeout`

```typescript
async function withTimeout<T>(
  steps: (() => Promise<StepResult>)[],
  timeoutMs: number,
  onTimeout: () => Promise<T>,
  startTime?: number
): Promise<T | StepResult> {
  const start = startTime ?? Date.now();

  for (const step of steps) {
    const remaining = timeoutMs - (Date.now() - start);
    if (remaining <= 0) {
      return await onTimeout();
    }
    // 可选：在"剩余时间 < 典型 step 时长"时提前走超时路径
    // if (remaining < STEP_DURATION_ESTIMATE) return await onTimeout();

    const result = await step();
    // step 完成后可立即继续下一个 step（无需 sleep）
  }

  // 所有 step 完成，未超时
  return { status: 'completed', result: await steps[steps.length - 1]() };
}
```

**约束与限制**：
- `steps` 数组的每个函数必须是独立可执行的 Workflow step（或 step 的一部分）
- 超时检查在 step 粒度，非实时。最坏情况延迟 = 单个 step 的最长执行时间
- 如果单个 step 的执行时间可能 > timeoutMs，则此模式失效——需要将 step 进一步拆小
- 这不是 BPMN 的"并行监听 + 打断"语义，而是"串行执行 + step 间检查"模式

#### 2.3.2 withTimeout 的实际使用示例

```typescript
// BPMN: "审批订单"活动 + 5分钟定时边界（超时后自动拒绝）
// CF Workflows 等价：

const steps = [
  async () => await validateOrder(orderData),          // step 1: 校验
  async () => await checkInventory(orderData),          // step 2: 查库存
  async () => await calculatePrice(orderData),          // step 3: 计算价格
];

const result = await withTimeout(steps, 5 * 60 * 1000, async () => {
  await rejectOrder(orderData, 'timeout');
  return { status: 'timeout_rejected' };
});
```

### 2.4 模式覆盖度评估

| 场景 | 模式适用性 | 说明 |
|------|----------|------|
| HTTP API 调用超时 | ✅ 不需要此模式 | `fetch` 的 `AbortSignal.timeout()` 已覆盖 |
| 批量处理（单条/批超时） | ✅ withTimeout | 每批处理后在 step 间检查 |
| 多步骤子流程超时 | ✅ withTimeout | 每个子 step 后检查 |
| 单步骤长计算超时 | ❌ 无法覆盖 | 如需 CPU-bound 长计算超时保护，需将计算拆分为多次 yield 或使用外部 Worker 执行 |
| 人工任务超时（如审批超时） | ⚠️ 不在自动化场景范围 | C-007 已将用户任务(#9)降级为低 |

**结论**：withTimeout 模式覆盖中断型定时器在自动化场景中 **约 90% 的实际需求**（基于 H1）。剩余 10%（单步长计算超时）受限于 CF Workflows 的执行模型，无法在单 step 内中断执行，需要从流程设计层面将长计算拆小。

## 3. 非中断型定时器：取舍决策

### 3.1 问题定位

非中断型定时器的 BPMN 语义是：**定时器与所附活动并行运行，超时后触发边界事件路径，但原活动不中断，继续执行到完成**。

在自动化场景下，此语义对应的实际需求是：
- "订单处理超过 5 分钟后**同时**发送提醒通知"
- "流程运行超过 1 小时后**同时**发出告警"
- "数据同步超过 10 分钟后**同时**触发降级方案"

### 3.2 三种可选策略

| 策略 | 描述 | 与 BPMN 语义的差异 |
|------|------|-------------------|
| **策略 A：降级为 sleep + action step** | 在原流程中插入 `workflow.sleep(300s)` + `发送通知 step`，然后继续后续流程 | 不再是"并行提醒"——通知在原活动完成后才发出。如果原活动执行 > timeout，通知在 timeout 时刻发出（符合预期）；如果原活动执行 < timeout，通知延后（不符合"准时提醒"语义） |
| **策略 B：外部 Cron Trigger + DO 状态检查** | Cron Trigger 每分钟扫描 D1 中运行中的 Workflow 实例，检查 `started_at` 字段是否超过阈值，超时则发 webhook 通知 | 实现了真正的"并行提醒"（外部触发），但轮询间隔导致通知延迟可达 60s（Cron Trigger 最小频次），且存在状态同步不一致风险（DO/D1 中记录的 `started_at` 可能不是最新的） |
| **策略 C：DO Alarm** | 利用 Durable Object 的 Alarm API 设置单次或周期定时器，到期时 DO 的 `alarm()` 方法触发通知 | 精度最高（秒级），但每个 Workflow 实例需要独立的 DO Alarm，成本和管理复杂度较高 |

### 3.3 取舍决策

**推荐：策略 A（降级为 sleep + action step），非中断型定时器不在本期工程范围。**

理由：

| 因素 | 分析 |
|------|------|
| **自动化场景需求频率** | C-023 §3.2 判断非中断型需求**低**。H2 置信度 5/10 偏低，但 Q3 验证前的保守策略是暂不投入外部基础设施。 |
| **投入产出比** | 策略 B（Cron Trigger + DO）工作量 3-4d（C-007 预估），策略 C（DO Alarm）更高。在需求未确认时投入不合理。 |
| **策略 A 的可用性** | 对于大部分自动化场景，"在原步骤完成后发送通知"的时序差异在业务上是可接受的。如果业务确实需要严格的"定时提醒"（而非"完成后提醒"），那说明该场景有非中断型定时器的硬需求——此时再启动策略 B/C。 |
| **与 GAP #4 的统一机会** | 非中断型的外部 Cron Trigger 检查模式与事件子流程（#4）的 `waitForEvent` 模式有重叠。如果 #4 的 plan-eng-review 确认需要外部事件监听基础设施，非中断型定时器可复用其 Cron Trigger + DO 检查通道，边际成本显著降低。 |

### 3.4 非中断型纳入范围的触发条件

如果 Q3 确认存在以下**任一**不可替代用例，则启动非中断型定时器的独立工程评审：

- 业务需要在活动**执行过程中**（而非完成后）准时发送通知
- 通知必须在 timeout 时刻精确触发（误差 < 10s），不能接受 step 完成后才发
- 业务需要在活动执行期间周期性发提醒（如每 5 分钟报告一次进度）

触发后，优先评估是否可复用 #4 事件子流程的外部事件监听基础设施。

### 3.5 当前状态下的 GAP 等级再判定

|--------|-----------|-----------|---------|

## 4. sleep 精度/可靠性边界测试方案

### 4.1 测试动机

H5 假设 `workflow.sleep()` 的精度和可靠性足够（秒级偏差可接受），但**未经实际环境验证**。如果 sleep 的实际精度偏差显著（如 ±10s 以上）或长时间 sleep 不可靠（如 sleep 1h+ 后 Workflow 被意外终止），则 `withTimeout` 模式和一些依赖 sleep 的补偿方案需要重新设计。

### 4.2 测试方案

#### 4.2.1 测试矩阵

| 测试维度 | 测试值 | 测试目标 |
|---------|--------|---------|
| **短 duration** | 1s, 5s, 10s, 30s | 验证秒级 sleep 的精度（偏差 < ±2s） |
| **中 duration** | 1min, 5min, 10min | 验证分钟级 sleep 的精度（偏差 < ±5s） |
| **长 duration** | 30min, 1h, 2h | 验证长时间 sleep 的可靠性（不因 Workflow GC / 平台限制而提前终止） |
| **边界 duration** | `workflow.sleep(0)`, `workflow.sleep(Number.MAX_SAFE_INTEGER)` | 验证极端输入处理 |
| **并发 sleep** | 10 个并行 Workflow 同时 sleep 不同时长 | 验证引擎对多实例 sleep 的调度公平性和精度一致性 |

#### 4.2.2 测试 Workflow 设计

```typescript
// 测试 Workflow: 单个 sleep 精度测试
export async function sleepPrecisionTest(params: {
  durationMs: number;
  testId: string;
}): Promise<SleepTestResult> {
  const scheduledStart = Date.now();
  
  // Step 1: 记录 sleep 前时间
  const beforeSleep = Date.now();
  
  // Step 2: 执行 sleep
  await workflow.sleep(params.durationMs);
  
  // Step 3: 记录 sleep 后时间
  const afterSleep = Date.now();
  
  const result: SleepTestResult = {
    testId: params.testId,
    durationMs: params.durationMs,
    scheduledStart,
    beforeSleep,
    afterSleep,
    actualSleepMs: afterSleep - beforeSleep,
    deviationMs: (afterSleep - beforeSleep) - params.durationMs,
    totalElapsedMs: afterSleep - scheduledStart,
  };
  
  // 存入 D1 供分析
  await storeTestResult(result);
  
  return result;
}
```

#### 4.2.3 可靠性测试

| 测试 | 方法 | 成功标准 |
|------|------|---------|
| **长 sleep 不乱序恢复** | sleep 30min 后执行时间戳记录 step，比较 step 起始时间 vs 预期恢复时间 | Workflow 在 sleep 后正确恢复，seq 编号连续 |
| **sleep 中断测试** | sleep 过程中挂起 Workflow（`workflow.pause()`），恢复后检查 sleep 是继续还是重新开始 | 明确 `workflow.pause()` 对 sleep 的影响 |
| **多级 sleep 叠加** | `sleep(10s)` → `step` → `sleep(20s)` → `step` | 多次 sleep 的累计偏差应在可接受范围 |
| **sleep + step 混合** | `sleep(5s)` → `fetch(known-slow-url)` → `sleep(5s)` | step 执行时间不干扰后续 sleep 精度 |

#### 4.2.4 测试基础设施

| 组件 | 说明 |
|------|------|
| 测试 Worker | 部署 sleep 精度测试 Workflow 定义 |
| D1 结果表 | `sleep_test_results`：`(test_id, duration_ms, actual_sleep_ms, deviation_ms, created_at, workflow_instance_id, cf_region, notes)` |
| 触发方式 | API 端点 `/test/sleep-precision` 接受 `{durations: number[]}` 参数，触发多个测试 Workflow |
| 分析查询 | D1 SQL 按 `duration_ms` 分组，统计 mean deviation、p50/p95/p99 deviation、max deviation |

#### 4.2.5 测试执行计划

| 阶段 | 内容 | 时间 |
|------|------|------|
| Phase 0（快速验证） | 短 + 中 duration（1s-10min），10 个采样点各 3 次重复 | 0.5d |
| Phase 1（完整验证） | 全矩阵（含长 duration），各 5 次重复，并行 sleep 测试 | 1d（含等待长 sleep 的时间） |
| Phase 2（分析报告） | D1 查询 + 统计分析 + 结论报告 | 0.5d |
| **合计** | | **约 2d** |

### 4.3 测试结论判定标准

| 精度级别 | 偏差范围 | 对补偿方案的影响 |
|---------|---------|----------------|
| **优秀** | ±1s 内 | withTimeout 模式完美可用，超时检查无需 tolerance 参数 |
| **可接受** | ±5s 内 | withTimeout 模式可用，需增加 tolerance 参数（如 `timeoutMs + 5s` 作为宽松边界） |
| **边界** | ±30s 内 | withTimeout 模式需大幅增加 tolerance，对分钟级超时的场景可能不适用 |
| **不可接受** | ±30s 以上或长 sleep 不可靠 | 中断型定时器补偿方案需重新设计——可能转向外部 Cron Trigger + DO 状态检查（类似非中断型策略 B） |

**测试的阻塞性**：sleep 精度测试**建议在 withTimeout helper 开发完成后立即执行**，不应阻塞模式设计本身。withTimeout 的接口设计中预留 `toleranceMs` 参数，根据测试结果填充默认值。

## 5. 与 #4、#5 中断信号的统一设计评估

### 5.1 三个 GAP 的中断/信号需求分析

C-023 §4.2 提出的 `WorkflowObserverDO` 概念需要在本期进行工程可行性评估。先对比三个 GAP 对"中断信号/状态观察"的需求：

| GAP | 中断触发条件 | 中断信号方向 | 信号传递方式 | 检查点位置 |
|-----|------------|------------|------------|----------|
| **#6 定时边界（中断型）** | 时间条件（elapsed > timeout） | 内部（Workflow 自身判断） | step 间调用 `checkTimeout()` | 每个 step 后 |
| **#5 多实例提前终止（C-021）** | 外部信号（任一实例完成且满足 N-of-M / First-N 条件） | 外部 → 子 Workflow | DO 写入 `stopFlag`，子 Workflow 调用 `checkStopFlag()` | 子 Workflow 的关键 step 前 |
| **#4 事件子流程** | 外部事件（取消订单、退款申请、配置变更） | 外部 → 主 Workflow | `waitForEvent()` 或 DO 中断标志 | 主 Workflow 的关键 step 前 |

**共性识别**：三个 GAP 都需要 **"在 step 间检查某个条件/信号，根据检查结果决定是否走替代路径"**。C-021 的 `checkStopFlag()` 模式和本期设计的 `checkTimeout()` 模式在工程上是同构的。

### 5.2 统一 WorkflowObserverDO 可行性评估

C-023 提出了以下统一架构：

```
WorkflowObserverDO
├── 状态追踪：当前 step、开始时间、预期完成时间
├── 超时配置：每个 Workflow 定义各 step 的超时阈值
├── 中断信号：外部 Cron Trigger 可设置 "should_abort" 标志
└── Workflow 端检查：在 step 间调用 observer.getState() 检查是否有中断信号
```

#### 5.2.1 可行性结论

**WorkflowObserverDO 在当前阶段不建议作为独立基础设施实现。**

理由：

| 因素 | 分析 |
|------|------|
| **收益有限** | 三个 GAP 的中断检查机制虽然模式相似，但**触发条件截然不同**（时间、外部信号、外部事件）。统一的 DO 接口需要在内部承载三种不同的判定逻辑，复杂度超过各独立实现的简单方案。 |
| **#4 方案未定** | 事件子流程（#4）的 plan-eng-review 尚未完成，其最终方案可能选择 `waitForEvent()` 而非 DO poll 模式。WorkflowObserverDO 如果在 #4 决策前设计，可能包含不必要的功能或遗漏关键需求。 |
| **C-021 已有方案** | C-021 的 `signalStop() + checkStopFlag()` 已在 JoinCoordinator DO 上实现，且 C-021 明确判定"早期终止信号不需要独立 DO"，方案已经落地。 |
| **本期已有轻量方案** | 中断型定时器的 `withTimeout` 是纯代码模式（无 DO 依赖），复杂度最低，不需要统一的 Observer DO。 |

#### 5.2.2 替代策略：标准化检查点 Pattern，而非统一 DO

建议将统一设计从"统一 DO"调整为**"统一的 step 间检查点 Pattern 规范"**：

```
Step N-1 执行完成
    ↓
Step N: 检查点（由业务代码决定检查什么）
    ├── checkTimeout(startTime, timeoutMs)          ← #6: 时间条件
    ├── checkStopFlag(parentInstanceId)              ← #5: 外部信号
    ├── checkEvent(eventType)                        ← #4: 外部事件
    └── checkComposite([...])                        ← 组合多种条件
    ↓
    根据检查结果路由到正常路径或替代路径
```

检查点 Pattern 的统一带来的好处：
1. **代码结构一致**：所有流程的 step 间检查点位置和路由逻辑使用相同的代码风格
2. **审计友好**：检查点统一写入 D1 审计表（`step_checks`：instance_id, step_name, check_type, check_result, checked_at）
3. **可组合**：一个检查点可同时检查多种条件（如检查超时 AND 检查外部信号）
4. **无基础设施依赖**：纯代码 pattern，不引入新的运行时依赖

#### 5.2.3 何时重新评估 WorkflowObserverDO

当以下条件**同时**满足时，应重新评估统一 WorkflowObserverDO：

1. #4 事件子流程的 plan-eng-review 完成，且方案选择 **DO poll** 模式（而非 `waitForEvent` 或 Queue 事件）
2. 非中断型定时器（GAP #6 策略 B/C）被确认需要，且选择 **Cron Trigger + DO** 模式
3. 三个 GAP 的检查点 Pattern 在至少 5 个流程中落地后，表现出明显的代码重复和维护负担

在以上条件满足前，**不建议**提前投入 3-5d 建设统一的 WorkflowObserverDO。

## 6. 状态同步的最终一致性方案（非中断型——若纳入范围）

### 6.1 问题定义

非中断型定时器的策略 B/C 依赖于外部组件（Cron Trigger / DO Alarm）检查 Workflow 的状态。核心问题是：

> **外部组件的检查时刻，Workflow 的真实状态是什么？是否存在不一致窗口？**

场景：Workflow 在 step 3 执行中，Cron Trigger 在此时查询 D1 中记录的 `current_step` 为 "step 2"（因为 step 3 尚未更新 D1 状态记录），导致 Cron Trigger 基于过期状态做出判断。

### 6.2 若纳入范围，可采用的一致性策略

| 策略 | 描述 | 一致性级别 | 复杂度 |
|------|------|----------|--------|
| **Tolerate staleness** | 接受 Cron Trigger 读取到的状态可能有 1-2 step 的延迟。由于非中断型是"提醒"而非"中断"语义，短暂的状态不一致的后果是"晚一点才提醒"，对业务流程影响可接受。 | 最终一致（容忍 1-2 step 延迟） | **低** |
| **Heartbeat + stale threshold** | DO 维护 `last_heartbeat_at`（Workflow 每个 step 结束时更新 heartbeat）。Cron Trigger 判断"若 heartbeat 超时 + D1 中 state 显示在运行中 → 可能卡住而非正常执行"。 | 最终一致（heartbeat 超时窗口内不确定） | **中** |
| **Duplex signal（推拉结合）** | DO Alarm 设置单次提醒定时器。若 Workflow 在 alarm 触发前完成 → Workflow 主动取消 alarm。若 alarm 触发 → 检查 DO 状态决定是否发提醒。 | 强一致（alarm 取消 = Workflow 已完成） | **高** |

### 6.3 本期建议

**非中断型降级策略下，状态同步方案不在本期工程范围。** 如果 Q3 确认需要非中断型定时器，建议采用策略 A（Tolerate staleness）作为默认方案——"提醒延迟 1-2 step 可接受"的判断与 C-023 H6（秒级精度可接受）一致。在实际实现阶段，通过 heartbeat 机制（Strategy B）提供额外的卡住检测能力作为增强。

## 9. 接受/不接受判定

### 9.1 判定结论

**建议不接受此 GAP（即进行补偿）。** 中断型定时器通过 `withTimeout` 标准化模式补偿，非中断型定时器通过降级策略（sleep + action step）接受。

### 9.2 理由

| 因素 | 分析 |
|------|------|
| **GAP 性质** | 结构性 GAP——CF Workflows 顺序执行模型与 BPMN 的"并行监听 + 打断"语义根本不同。 |
| **业务影响** | 定时边界事件在自动化场景中需求中等（C-023 判断中断型中高、非中断型低）。放弃补偿意味着所有超时保护需完全依赖 HTTP client 层或 Workflow 执行超时，缺乏流程级别的超时分支控制。 |
| **补偿可行性** | 中断型补偿成本低（withTimeout helper 1.5d + sleep 精度测试 2d = 3.5d）。不存在"无可行补偿"的困境。 |
| **降级策略的合理性** | 非中断型在自动化场景中需求未确认。在 Q3 回答前，降级为 sleep + action step 是合理的临时策略——代价低（0d），且可在 Q3 确认需求后随时升级到完整的外部基础设施方案。 |
| **风险可控** | withTimeout 的核心逻辑基于 `Date.now()` 差量计算，不依赖 sleep 精度。主要风险（长 sleep 不可靠、单 CPU step 无法中断）均有缓解措施或明确的逃生路径。 |
| **与其他 GAP 的关系** | withTimeout 是自包含模式，不依赖 #4、#5 的任何产出。未来如需统一检查点规范，withTimeout 可直接作为规范的一部分融入。 |

### 9.3 若接受 GAP（不补偿），对应的代价

不补偿意味着所有定时边界事件的 BPMN 语义在迁移到 CF Workflows 后消失。后果：

1. 所有流程的超时保护退化为仅依赖 `fetch` 的 AbortSignal 和 Workflow 执行超时
2. 超时后无法执行替代路径（如超时后自动拒绝、超时后走降级逻辑）
3. 无法表达"步骤 A 超时后执行步骤 B"的控制流语义——所有逻辑必须在步骤内通过 try/catch + 自定义超时逻辑实现

## 11. 本期结论

GAP #6 定时边界事件**建议不接受**（即进行补偿）。

**工程方案核心**：
- **中断型定时器**：`withTimeout` 标准化模式——将长时间活动拆为 step 序列，每个 step 后检查 elapsed time vs timeout，超时则走替代路径。工作量 1.5d（helper 开发 + 文档化 + 验证）。
- **非中断型定时器**：降级为 sleep + action step 替代（0d）。若 Q3 确认有不可替代用例，启动独立的 Cron Trigger + DO 方案（+3-4d）。
- **sleep 精度测试**：必须验证 CF Workflows `workflow.sleep()` 的实际精度和长 sleep 可靠性。测试矩阵覆盖 1s 到 2h 的 duration 范围，工作量 2d。
- **统一检查点 Pattern**：暂不建设统一的 WorkflowObserverDO。本期 `withTimeout` 与 C-021 的 `checkStopFlag()` 共享"step 间检查"模式，在 #4 方案确定后评估是否需要统一的检查点规范。
- **总工作量**：约 3.5d（与 C-007 的 4-6d 相比，节省来自非中断型降级；与 C-023 的 0.5-1d 相比，增加来自 sleep 精度测试）。

**需要决策者确认**：D1（是否启动补偿开发）、D2（是否接受非中断型降级）、D3（测试并行执行）。
