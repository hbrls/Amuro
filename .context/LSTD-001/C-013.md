## 2. 核心问题识别

### 2.1 包含网关的本质

包含网关（Inclusive Gateway）是 BPMN 2.0 的条件分支/汇聚构造：

| 方向 | 语义 | 行为 | 与并行网关的差异 |
|------|------|------|----------------|
| Fork（分裂） | 流程到达后，**按条件**激活满足条件的所有出边 | 评估每条出边的条件，激活条件为 true 的所有分支（0 到 N 条） | 并行网关无条件激活所有出边；包含网关有条件筛选 |
| Join（汇聚） | 等待**所有已激活的入边**到达后，才继续 | 同步等待已激活分支完成，未激活分支不参与 join | 并行网关等待所有入边（全部 N 条）；包含网关仅等待实际激活的入边 |

关键属性：
- Fork：条件驱动的多分支选择——"满足条件的都走"
- Join：动态等待——"走了几个分支就等几个"
- Fork 可能激活 0 条分支（所有条件为 false）——此时流程直接跳过分支区域
- Fork 可能激活 1 条分支——退化为排他网关的行为
- Fork 可能激活所有 N 条分支——退化为并行网关的行为

### 2.2 核心冲突

包含网关的 GAP 层级与并行网关一致（C-007 判定等级相同），但有其独特难点：

| 维度 | 并行网关 (#1) | 包含网关 (#2) | 额外复杂度 |
|------|--------------|--------------|-----------|
| Fork 语义 | 无条件激活所有 N 条分支 | 条件筛选后激活 M 条（0 ≤ M ≤ N） | 需在 fork 前动态计算 `childIds` |
| Join 语义 | 等待所有 N 条分支完成 | 等待已激活的 M 条分支完成 | 需记录"哪些分支被激活了"，join 只等这些 |
| 分支间关系 | N 条始终固定 | M 条动态变化 | DO 聚合器需支持动态注册 |
| 条件评估时机 | 无 | fork 前必须完成条件计算 | 条件逻辑嵌入 fork step 之前 |
| 无分支激活场景（M=0） | 不会出现 | 可能出现（所有条件 false） | 主 Workflow 需支持"零分支"跳过路径 |

**结论**：包含网关是并行网关在"条件筛选"维度上的扩展。它在 CF Workflows 引擎模型下的 GAP 与并行网关**层级相同但语义叠加**。

### 2.3 C-007 初步判定的可靠性

C-007 对 GAP #2 的初步分析：
- 本质是"条件筛选后的并行网关"
- 补偿方案"同 #1，在并行前增加条件评估步骤"
- 额外增加条件判断逻辑（低开销）

此判定在 C-011（GAP #1 的 plan-eng-review）完成前做出，未对 DO 聚合器接口做具体推演。本期需基于 C-011 的 JoinCoordinator 设计，重新检验该判定的充分性。

### 2.4 自动化场景下的影响分析

根据已知约束（自动化场景为主，人工审核忽略），包含网关在自动化场景中的典型使用包括：

1. **条件并行 API 调用**：根据业务条件同时调用部分 API（如：VIP 用户额外查专属优惠 + 查库存 + 查价格；普通用户只查库存 + 查价格）
2. **条件并行子流程**：根据订单类型同时启动部分子流程（如：跨境订单额外启动物流清关子流程 + 支付子流程 + 通知子流程）
3. **条件并行消息发送**：根据用户偏好选择性地并行发送多渠道通知
4. **条件-结果型分支**（M=1）：实际退化为排他网关——只有一个分支被激活

对于场景 1-3，包含网关的技术价值在于：
- **避免无效分支执行**（对比并行网关无条件激活所有分支）
- **Join 时无需等待未激活分支**（对比并行网关需处理"未激活分支永不完成"的边界情况）

## 3. 与 GAP #1 DO 聚合器（JoinCoordinator）的接口兼容性分析

### 3.1 C-011 已定义的 JoinCoordinator 接口

来自 C-011 §4.3 Phase 2：

| 接口 | 语义 | 所需输入 |
|------|------|---------|
| `register(instanceId, childIds)` | 注册需等待的子 Workflow ID 列表 | `childIds`: 固定列表 |
| `reportDone(childId, result)` | 子 Workflow 完成时上报 | — |
| `awaitAll()` | 等待所有已注册子 Workflow 完成 | — |

### 3.2 包含网关对接口的额外需求

| 改造点 | 现状（针对 GAP #1） | 包含网关需求 | 改动评估 |
|--------|-------------------|-------------|---------|
| 注册时机 | fork 时注册固定 `childIds` | fork 前条件计算 → 注册动态 `childIds` | **无需接口改动**——`register` 已接受任意 `string[]`，条件计算结果直接传入 |
| 空分支集（M=0） | 不会出现 | 可能出现 | **需增加语义**——若 `childIds` 为空，`register` 应直接标记为"完成"（无分支需等待），`awaitAll` 立即返回 |
| Join 逻辑 | 等待 `childIds.length` 个完成信号 | 等待已注册的 M 个完成信号 | **无需改动**——已注册的子 Workflow 数 = M，等待逻辑不变 |
| 条件计算 | 无 | fork 前需执行条件判断 | **不属于 DO 聚合器职责**——条件计算在 Workflow step 中执行，结果作为 `childIds` 传入 Register |
| 未注册分支的废弃处理 | 不适用 | 条件为 false 的分支不被启动 | **天然满足**——未被启动的子 Workflow 无需 `reportDone`，DO 不感知 |

### 3.3 结论

GAP #2 对 JoinCoordinator 仅需 **一个语义增强**：支持空 `childIds` 注册（M=0 场景，直接跳过 fork/join）。此改动约 0.5d，其余接口完全复用。条件计算的职责在 Workflow step 侧，不侵入 DO 聚合器。

## 4. 方案复用性分析

### 4.1 方案 A（内联并行）在包含网关下的适配

**C-011 方案 A 设计**：单 step 内使用 `Promise.all()` 并行调用外部 API。

**包含网关适配**：在 `Promise.all()` 之前增加条件判断逻辑，动态构造待调用的 API 数组。

```
Step N: 条件评估 → 构建 apiCalls = [] → 按条件 push fetchA/fetchB/fetchC
Step N: await Promise.all(apiCalls)  → 只有满足条件的 API 被调用
```

**适配工作量**：约 0.1d / 流程——条件判断是纯代码逻辑，无基础设施变更。

**结论**：方案 A 完美适配包含网关，无需独立版本。条件筛选逻辑以 if/else 自然表达，在 code-as-workflow 范式下甚至比 BPMN 的条件表达式更直观。

### 4.2 方案 B（DO 聚合器 + 子 Workflow）在包含网关下的适配

**C-011 方案 B 设计**：主 Workflow 的 `fork` step 中 `workflow.start()` 所有子 Workflow，`join` step 调用 DO `awaitAll()`。

**包含网关适配**：

```
Step 0: 条件评估 → 动态计算 activeBranches = ["childA", "childB"]  ← 条件筛选
Step 1: activeBranches.forEach(id => workflow.start(id))              ← 按条件 fork
Step 2: do.joinCoordinator.register(instanceId, activeBranches)       ← 动态注册
Step 3: do.joinCoordinator.awaitAll()                                 ← 等待 M 个分支
Step 4: do.joinCoordinator.getResults()                               ← 聚合
```

**变更范围**：
- 主 Workflow step 增加条件计算逻辑（低开销）
- DO 聚合器：空 `childIds` 场景处理（约 0.5d，见 §3.3）
- 其他：无变更

**结论**：方案 B 适配包含网关的增量成本极低（~0.5d），**无需独立版本**。条件评估 → 动态 childIds → register 的调用链与方案 B 现有设计无缝衔接。

### 4.3 总体判定

| 维度 | 结论 |
|------|------|
| 是否需要独立的方案 A/B 适配 | **否**——方案 A 和方案 B 均可直接复用，条件筛选以代码逻辑嵌入现有流程 |
| 增量工作量 | 方案 A：约 0.1d/流程；方案 B：约 0.5d（DO 空分支处理）+ 0.1d/流程 |
| 是否需要替代方案 C | **否**——C-011 已放弃方案 C，同理适用于包含网关 |
| 整体风险评估 | **低**——条件筛选是纯代码逻辑，不引入额外架构复杂度 |

## 7. 与后续 GAP 的联动关系

### 7.1 与 GAP #5（多实例）的联动

| 维度 | GAP #2 包含网关 | GAP #5 多实例 | 交集 |
|------|----------------|-------------|------|
| Fork 语义 | 条件选择 M 个不同分支 | 对同一模板创建 N 个实例 | 共享 DO 聚合器的"批量启动 + 等待"模型 |
| childIds 来源 | 条件计算动态生成（异构分支） | 列表数据展开（同构实例） | 均传入 `register(instanceId, childIds)` |
| 复用影响 | — | — | GAP #2 引入的"动态 childIds + 空分支处理"为 GAP #5 中的"0 实例"边界场景（如空列表）提供既有效用 |

### 7.2 与 GAP #8（补偿边界事件）的联动

| 维度 | 分析 |
|------|------|
| 分支失败场景 | 包含网关的 M 条分支中任一条失败——与并行网关相同，需 Saga 编排器协调补偿 |
| 补偿复杂性 | 包含网关仅需对**已激活**的 M 条分支做补偿（非全部 N 条），补偿范围可能小于并行网关 |
| DO 聚合器交互 | DO 聚合器在检测到分支失败时可触发 Saga 补偿链（通过 `getResults()` 返回失败分支列表），接口级联动 |

### 7.3 结论

GAP #2 与 GAP #5、#8 的联动路径与 GAP #1 一致，不需要为包含网关单独建立联动框架。C-011 已确认的"DO 聚合器作为共享基础设施"策略覆盖 GAP #2。

## 8. Goal LENS 视角结论

### 8.1 结论

**GAP #2 包含网关的补偿方案可完全站在 GAP #1 的肩上。** 包含网关的本质差异——条件筛选——在 code-as-workflow 范式下是 **零架构成本的增量**（纯代码条件判断），不需要独立的补偿方案设计。

C-011 的方案 A + 方案 B 分层采用、DO 聚合器作为共享基础设施的策略可直接覆盖 GAP #2。

### 8.2 与 GAP #1 的差异总结

| 差异点 | 影响 | 额外成本 |
|--------|------|---------|
| 条件计算逻辑 | 嵌入 fork step 前的代码判断 | ~0.1d / 流程 |
| 动态 childIds | register 接口无需改动，直接传入条件计算结果 | 0 |
| M=0 场景 | DO 需支持空 childIds 注册 | ~0.5d |
| Join 语义 | 等待 M 个而非全 N 个——register 接口已支持 | 0 |

**总增量成本：约 0.5d + 0.1d/流程**。相比 GAP #1 的 12-15d 总投入，GAP #2 几乎可以认为是 GAP #1 投入的自然延伸收益。

### 8.3 关键提醒

- 本期 goal LENS 的核心发现是：**GAP #2 无需独立的 plan-eng-review**。在 C-011 已完成的方案 A+B + DO 聚合器设计下，GAP #2 是"零新增架构、零新增方案"的邻接 GAP。建议 pilot 收束（TASK-014）直接判定将 GAP #2 的结论归入 C-013 即可，不需要另开一期的 plan-eng-review。
- 若 Q1（使用模式分布）的答案是"现有流程中所有包含网关实际 M=1（退化排他）或 M=N（退化并行）"，则 GAP #2 事实上可以被 GAP #1 和 C-007 中 #3 复杂网关（已降级）共同覆盖，进一步简化。
- 条件筛选逻辑的实现虽简单，但若涉及调用外部服务做条件判断（如查询用户等级决定是否启动某分支），需关注外部调用失败时的降级策略（是安全地不激活该分支，还是默认激活该分支）。这在方案设计中属于条件编写者的职责，不属于 DO 聚合器或方案 B 基础设施的范畴。
