## 1. 语义解构：补偿边界事件

### 1.1 BPMN 补偿边界事件本质

补偿（Compensation）是 BPMN 2.0 中一种特殊的"撤销"机制。与错误处理不同——错误处理针对"执行失败"的步骤，补偿处理的是"已成功完成但需要在事后撤销"的步骤。

补偿边界事件的核心语义：

| 维度 | 说明 |
|------|------|
| **附着位置** | 附着在特定活动（Task / Sub-process）的边界上 |
| **触发条件** | 显式抛出补偿事件（`throwCompensateEvent`）时，按 scope 向上传播，触发该活动上的补偿处理逻辑 |
| **补偿处理器** | 被附着活动的补偿处理器（Compensation Handler）——该活动内部定义的一个子流程/任务，专门用于撤销该活动的副作用。活动必须标记 `isForCompensation="true"` |
| **执行顺序** | 逆序执行——先完成的活动的补偿处理器后执行（类似于栈的 LIFO 语义） |
| **与错误边界事件的关键区别** | 错误边界事件：活动**执行中**出现错误时触发（活动未完成）。补偿边界事件：活动**已成功完成**，但由于上游或其他分支的失败，需要"撤销"该已完成活动的副作用 |

### 1.2 补偿边界事件 vs 补偿事件子流程

BPMN 中有两种与补偿相关的构造：

| 维度 | 补偿边界事件 | 补偿事件子流程 |
|------|-----------|-------------|
| **作用域** | 附着在**特定活动**边界上 | **流程级别**——只要父作用域活跃，任何地方抛出补偿事件都可能触发它 |
| **触发粒度** | 只补偿所附着的**单个活动** | 可在补偿子流程内部编排**多个活动的补偿** |
| **典型使用模式** | 每个需要支持补偿的活动单独定义其补偿处理器 | 全局补偿逻辑，统一处理多种补偿触发场景 |
| **与 #4 事件子流程的关系** | 补偿边界事件是一种特殊类型的**边界事件**（有中断型语义） | 补偿事件子流程是**事件子流程**的补偿启动事件变体 |

在自动化场景下，两者的实际差异缩小：在一个代码定义的 Saga 编排器中，"边界事件级别的补偿"就是每个 step 的 `compensate()` 函数，"流程级别的补偿"就是 Saga 编排器的全局补偿协调逻辑。

### 1.3 补偿 vs 错误处理 vs Saga：三角关系的厘清

这是分析 GAP #8 的核心认知起点：

| 概念 | 触发时机 | 语义 | BPMN 表达 | Saga 等价 |
|------|---------|------|----------|----------|
| **错误处理** | 步骤**执行中失败** | 捕获异常，执行替代路径或重试 | 错误边界事件 + 错误事件子流程 | Saga 的 `catch` + retry 或 abort |
| **补偿** | 步骤**已成功后**需撤销 | 回滚已完成的副作用 | 补偿边界事件 + 补偿处理器 | Saga 的 `compensate()` 逆序回滚 |
| **中断事件** | 外部信号触发流程中断 | 停止当前执行，转特殊路径 | 中断事件子流程（#4 覆盖） | Saga 的 abort 触发点 |
| **三者关系** | 错误处理是 reactive（响应失败），补偿是 corrective（修正已完成的工作），中断事件是 orchestrating（调度层面决定放弃当前事务） | — | 三者可在同一流程中组合使用 | Saga 编排器统一管理三者 |

**关键洞见**：在 CF Workflows 迁移场景中，补偿边界事件（#8）不是孤立的 GAP——它是 **Saga 编排器的核心模块**，同时与错误处理（#19、#23）和中断事件（#4）有深度的语义耦合。将 #8 独立设计而不考虑这三者之间的关系，会导致架构碎片化。

### 1.4 中断型补偿 vs 非中断型补偿

| 维度 | 中断型补偿 | 非中断型补偿 |
|------|----------|-------------|
| | BPMN 默认行为：补偿边界事件为中断型（compensate activity 执行时主流程被中断） | 需将补偿边界事件的 `cancelActivity` 属性设为 `false` |
| **主流程行为** | 补偿执行期间主流程暂停/终止 | 主流程继续执行，补偿并行进行 |
| **使用场景** | 核心事务回滚（流程正确性依赖补偿结果） | 辅助清理操作（如日志修正、缓存失效），不需要阻塞主流程 |
| **在 Saga 中的等价** | 同步补偿——Saga 按逆序执行所有 compensate 后才继续/结束 | 异步补偿——fire-and-forget 补偿，主流程不等待补偿结果 |

### 1.5 BPMN 补偿执行机制：scope 与逆序传播

BPMN 补偿的完整执行流程：

```
1. 某处抛出 Compensate Event（通常由错误/中断事件子流程触发）
2. 事件沿 scope 层级向上冒泡
3. 遇到有 Compensation Handler 的活动时，触发其补偿处理器执行
4. 执行顺序：最内层 scope 先补偿，外层 scope 后补偿
5. 每个 scope 内部：LIFO（后完成的活动先补偿）
6. 补偿完成（或全部补偿执行完毕）后，流程实例根据抛出补偿的上下文确定结束方式
```

这些概念在 CF Workflows 的代码模型中映射为：
- **Scope** → Workflow 函数或子 Workflow
- **活动** → Step（Workflow 内的单个步骤）
- **补偿处理器** → step 的 companion `compensate()` 函数
- **逆序传播** → Saga 编排器基于"已执行步骤记录"逆序遍历并执行 compensate
- **Scope 冒泡** → 子 Workflow 失败时，父 Workflow 的 Saga 编排器检测并触发对应层级的补偿

## 2. C-007 初始判定再评估

### 2.1 C-007 对 #8 的判定回顾

> "自动化场景中，涉及多步外部系统调用时，补偿事务（Saga）仍然是刚需——如订单创建→库存扣减→支付，任一步失败需回滚前序步骤。补偿方案：Saga 模式——每个 step 提供 `compensate()` 函数，Workflow 在步骤失败时按逆序执行 compensate。代价评估：中高（需 Workflow 层面设计 Saga 编排器，每个流程需编写补偿逻辑，基础结构约 5-7d，但每个流程的补偿逻辑需按业务编写）。修正后等级：维持高。"

### 2.2 覆盖度分析

| 语义维度 | C-007 是否覆盖 | 覆盖情况 |
|----------|--------------|---------|
| Saga 编排器基础设计 | ✅ 已覆盖 | 正确识别了 Saga 作为核心补偿方案，"每个 step 提供 `compensate()` 函数"是正确方向 |
| 补偿的逆序执行（LIFO） | ✅ 已覆盖 | "按逆序执行 compensate"明确指出了 LIFO 语义 |
| 多分支并行场景下的补偿协调 | ❌ 未提及 | 并行网关（#1）+ 补偿的组合：若 3 个并行分支中 2 个成功、1 个失败，需要补偿的只是那 2 个成功分支，而非所有分支或整个流程。C-007 只在 #1 的 Q4 中提及"对 GAP #8 的依赖"，未具体分析并行→补偿的协调逻辑 |
| 补偿与中断事件子流程（#4）的集成 | ❌ 未提及 | #4 的中断型事件子流程是最常见的补偿触发器之一（如订单取消→触发补偿）。C-007 未讨论 #4 与 #8 的耦合关系 |
| 子 Workflow 层级的补偿冒泡 | ❌ 未提及 | 当子 Workflow（#15 Call Activity）内部失败时，父 Workflow 是否需要补偿？补偿的 scope 边界如何定义？C-007 未覆盖 |
| 补偿失败的处理（compensate 执行本身可能失败） | ❌ 未提及 | compensate 步骤是 API 调用，本身可能超时或失败。C-007 的方案假设 compensate 总是成功，但分布式中不存在"保证成功的撤销"。补偿失败需要退化为"人工介入"或"补偿重试" |
| 补偿与定时边界事件（#6）的交互 | ❌ 未提及 | timeout 后触发补偿的场景——step 超时后，已完成的 step 是否需要补偿？ |
| Saga 编排器状态的持久化需求 | ⚠️ 隐含但未显式说明 | "逆序执行 compensate"隐含了"需要记录哪些 step 已执行/已成功"的状态追踪需求，但未将其作为基础设施需求明确提出 |
| 已执行步骤的补偿幂等性 | ❌ 未提及 | 补偿可能被重复触发（网络重试、DO 事件重复投递）。compensate() 必须是幂等的——这个约束在单次调用中不明显，但在实际分布式环境中是关键 |
| 与 CF Workflows 原生重试机制的冲突 | ❌ 未提及 | CF Workflows 在 step 失败时可能自动重试该 step。Saga 应在此重试机制在何时介入？——在 step 重试耗尽后？还是 first-failure 时立即启动补偿？ |

### 2.3 再评估结论

**C-007 的"Saga 模式"判定在核心方向上正确，但存在四处结构性遗漏：**

1. **补偿的 scope 和层级问题被简化**。C-007 将补偿模型简化为"一个流程内所有 step 按逆序 compensate"，但未讨论：(a) 子 Workflow 内部的补偿如何与父 Workflow 的补偿协调？(b) 并行分支的补偿是部分回滚还是全局回滚？(c) 补偿的 scope 边界在哪里——是整个 Workflow 实例还是单个"事务边界"？

2. **补偿失败（compensate 执行失败）的处理未被覆盖**。在 CF Workflows 的分布式环境下，compensate 步骤本身是外部 API 调用，可能因网络故障、下游服务不可用等原因失败。C-007 的 5-7d 估算假设补偿执行总是成功，这低估了补偿可靠性保障的工程复杂度。

3. **并行网关（#1）+ 补偿（#8）的交叉场景未被分析**。这是最重要的遗漏——在方案 B（DO 聚合器 + 子 Workflow）下，并行分支的失败处理与 Saga 的补偿逻辑需要深度集成。C-007 只在 #1 的依赖关系图中标注了"对齐于 GAP #8"但未做交叉分析。

4. **Saga 编排器的状态持久化设计未被提出**。逆序补偿需要记录"哪些 step 已成功执行"，这个状态存储在何处（DO？D1？内存？）决定了 Saga 编排器的可靠性基线。C-007 未将状态存储作为独立的基础设施需求。

**C-007 的"维持高"判定在本期分析中得到强化**——上述遗漏意味着 #8 的实际工程复杂度高于 C-007 的原始估算。

## 3. 自动化场景需求分析

### 3.1 补偿边界事件在 BPMN 流程中的典型模式及自动化等价

| 模式 | 描述 | BPMN 表达 | 在自动化场景中的等价表达 | 与 Saga 的映射 |
|------|------|----------|------------------------|-------------|
| **多步外部调用的事务回滚** | 步骤 A→B→C 中 C 失败，需回滚 A 和 B 的副作用 | A/B 上有补偿边界事件 + C 失败时 throw compensate | Saga 编排器：记录已完成步骤 [A, B]→C 失败→逆序执行 compensate(B)→compensate(A) | **Saga 核心模式** |
| **订单取消触发的全流程回滚** | 订单创建→库存扣减→支付→发货中，收到取消信号 | 中断型消息事件子流程（#4）触发 compensate | (#4) waitForEvent("cancel") → (#8) saga.compensateAll() | #4 中断→#8 补偿的组合模式 |
| **并行分支部分失败的部分补偿** | 3 个并行分支（A、B、C），B 失败但 A 和 C 已完成 | B 上的错误事件 + A 和 C 的补偿边界事件 | (#1) DO 聚合器检测 B 失败→(#8) saga.compensatePartial([A, C]) | #1 并行→#8 补偿的交叉模式 |
| **超时触发的补偿** | step X 执行超过 timeout，已执行的步骤 Y、Z 需补偿 | 定时边界事件（#6）触发 compensate | (#6) stepTimeout() → (#8) saga.compensateCompleted([Y, Z]) | #6 定时→#8 补偿的交叉模式 |
| **子 Workflow 失败后的父流程补偿** | 父 Workflow 调用子 Workflow，子 Workflow 内部部分步骤成功但在父流程看来整体失败 | 子流程的错误边界事件（#19）→ 父流程的 compensate | 子 Workflow 返回 `{success: false, completedSteps: [...], results: {...}}` → 父 Saga 编排器根据 completedSteps 决定补偿范围 | #19 错误冒泡→#8 补偿的交叉模式 |
| **补偿清理（非中断型）** | 主流程继续执行，补偿操作并行进行（如清理临时数据、失效缓存） | 非中断型补偿（cancelActivity=false） | (#1 方案 A/B) `workflow.start(cleanupWorkflow)` fire-and-forget，主流程不等待 | 非核心补偿，异步执行 |

### 3.2 与其他 GAP 的重叠度分析

这是本期分析的核心产出——#8 的补偿工程不是孤立的 Saga 编排器，而是与多项 GAP 有深度交叉：

| 关联 GAP | 重叠维度 | 重叠度 | 分析 |
|----------|---------|--------|------|
| **#1 并行网关** | 并行分支的部分补偿 | **高（80%）** | 这是最重要的交叉场景。#1 方案 B 的 DO 聚合器在检测到分支失败后，需要调用 Saga 编排器的 `compensatePartial()` 补偿已成功的分支。两者在"哪些分支已完成→需要补偿什么"的信息流上有接口级耦合。C-011 §4 已明确将此对齐列为 #1 的依赖项。 |
| **#4 事件子流程** | 中断事件→补偿触发 | **高（70%）** | #4 SP2 的中断控制流在检测到 cancel 事件后，进入事件子流程的执行——而事件子流程的内容通常是"触发补偿"。#4 的中断行为与 #8 的补偿执行是上下游关系。C-029 §4.2 明确将"中断后对接 #8 Saga 的 compensate 链条"列为 SP2 的设计考量。 |
| **#2 包含网关** | 条件并行分支的部分补偿 | **高（70%）** | #2 可视为 #1 的超集——条件筛选后的并行分支。其补偿需求与 #1 完全相同，只是触发补偿的分支集合由条件动态决定。复用 #1+#8 的联合方案即可，无独立补偿需求。 |
| **#5 多实例** | 批量操作中部分实例失败的部分补偿 | **中高（60%）** | 多实例并行处理 100 个订单，其中 5 个失败——是补偿全部 95 个已完成订单，还是只标记失败的 5 个？或者补偿策略从"all-or-nothing"退化为"partial-success-with-retry"？多实例模式的补偿粒度与单流程 Saga 有本质不同。 |
| **#6 定时边界事件** | timeout→补偿触发 | **中（50%）** | step 超时后，取决于业务语义——(a) 超时视为失败，触发已执行步骤的补偿；(b) 超时后流程继续，补偿不需要触发。仅场景 (a) 需要 #6 与 #8 的集成。 |
| **#19 错误边界事件** | 子 Workflow 失败后的向上冒泡与补偿 | **中（45%）** | 子 Workflow 失败后，父 Workflow 需要决定：是补偿父 Workflow 内部已执行的步骤（scope 限于父 Workflow），还是将补偿信号传递到更高层级。这涉及 #19 的错误冒泡机制与 #8 的补偿 scope 定义之间的接口。 |
| **#23 死信/重试管理** | compensate 步骤失败的重试 | **中（40%）** | compensate 执行本身可能失败。失败后应：(a) 重试（复用 #23 的 retry wrapper）；(b) 写入死信队列；(c) 告警人工介入。compensate 的"重试"与普通 step 的重试在策略上可能不同（补偿通常不宜指数退避——越快补偿越好）。 |
| **#11 运行时查询** | Saga 编排器的补偿状态可观测性 | **中低（35%）** | 运行时需要能查询"哪些实例正在执行补偿"、"补偿进行到哪一步"——这些信息需要写入 #11 的运行时索引。 |
| **#12 历史查询** | 补偿执行的审计轨迹 | **中低（35%）** | 补偿操作（撤销已完成的操作）是需要记录的最高优先级审计事件之一。#12 的历史存储必须记录每次补偿的触发原因、被执行步骤、compensate 结果、时间戳。 |
| **#17 消息边界事件** | waitForEvent 作为补偿触发源 | **低（20%）** | 理论上外部消息可触发补偿，但在自动化场景中极少——补偿通常由流程内部逻辑（失败、中断、超时）触发，而非外部信号。 |
| **#18 信号边界事件** | 全局补偿信号 | **低（15%）** | "全局补偿所有运行中实例"是极端运维场景（如发现严重bug需要回滚所有进行中的事务）。触发机制可复用 #18 的信号总线，但补偿执行仍是 #8 的职责。 |

**核心发现**：#8 补偿边界事件是 8 项高 GAP 中**交叉依赖最多的 GAP**——它与 #1、#2、#4、#5、#6、#19、#23 共 7 项 GAP 有中高度重叠（≥40%）。这意味着：

1. **Saga 编排器的接口设计不能在 #8 的独立讨论中封闭完成**——它必须预留给 #1、#4、#5、#6 等的集成点。
2. **#8 的 5-7d 基础结构估算不包括交叉 GAP 的集成工作量**。加上各交叉 GAP 的集成适配，实际增量可能在 2-4d（取决于各 GAP 对补偿的需求复杂度）。
3. **C-007 将 #8 放在 Phase 1 是合理的**——Saga 编排器越早就位，后续 GAP 的补偿相关需求可以一次性集成，而非在每个 GAP 中分别造轮子。

### 3.3 在自动化流程中的预期使用频率

- **补偿的核心场景**（多步外部调用事务）在自动化场景中属于**高频基础模式**。任何涉及多个外部系统且要求数据最终一致性的流程都需要 Saga。自动化场景不是"减少 Saga 需求"——恰恰相反，自动化消除了人工补偿的 fallback 路径，Saga 的可靠性要求反而更高。
- **补偿的交叉场景**（并行 + 补偿、中断 + 补偿、超时 + 补偿）的频率取决于 #1、#4、#6 的实际使用情况。若并行网关和事件子流程的使用占比中等，则交叉场景是中等频率。
- **总体使用频率预估**：补偿边界事件的基础模式（多步事务 Saga）是高频需求，交叉模式是中等频率。在 8 项高 GAP 中，#8 的**使用频率可能仅次于 #11（运行时查询）和 #12（历史查询）**，高于 #4（事件子流程）和 #6（定时边界事件）。

│   │
│   └── 与 C-007 方案的差异：C-007 描述的是"每个 step 提供 compensate 函数"的概念。

│
├── SP2 补偿状态持久化 ──→ DO + D1 双写模式（开发量 1-2d）
│   │
│   │   状态存储选择：
│   │   - 内存（Workflow 变量）→ 简单但不可恢复（若 Workflow 实例挂了，补偿状态丢失）
│   │   - DO → 可靠（DO 持久化），但增加依赖
│   │   - D1 → 可查询（便于 #11/#12），但写入延迟
│   │
│   │   推荐：DO 作为补偿状态的主存储（可靠、低延迟），异步写 D1（供 #11/#12 查询）。
│   │   与 #1 方案 B 的 DO 聚合器是同一个 DO 还是独立 DO？

│   │     虽然增加一个 DO 类，但责任边界清晰，各自独立演化。
│   │
│   └── 补偿状态 schema：
│       {
│         instanceId: string,
│         txnBoundary: string,        // 事务边界 ID（一个 Workflow 可有多个事务边界）
│         completedSteps: [{stepId, compensateFnId, input?, output?, completedAt}],
│         compensationStatus: 'idle' | 'compensating' | 'completed' | 'partial_failure',

│   │   type CompensateFn = (input: CompensateInput) => Promise<CompensateResult>
│   │
│   │   interface CompensateInput {

│   │     stepInput?: unknown         // 原始 step 的输入

│   │   }
│   │
│   │   interface CompensateResult {
│   │     success: boolean
│   │     error?: string
│   │     compensatingActions: string[]  // 供审计
│   │   }
│   │
│   │   幂等性契约：compensate 必须能安全地多次调用（同一 txnId + stepId 的第二次调用
│   │   应返回已补偿结果，不重复执行副作用）。
│   │
│   └── 这是对 C-007 方案的精确化补充。

│   │
│   │   compensate 步骤失败的处置层次：
│   │   L1: 立即重试（1 次，无延迟）——补偿不应指数退避
│   │   L2: 标记"补偿未完成" → 写入 D1 pending_compensations 表

│   │

│   │   - 普通 step：指数退避，允许 longer wait（系统暂时不可用可等待）
│   │   - compensate：积极重试，不宜长期等待（补偿拖得越久，外部系统的
│   │     中间状态越复杂，undo 的窗口可能关闭）
│   │
│   └── 复用 #23 的 retry wrapper 基础设施，但配置独立的 compensate 重试策略。

│   │   - 子 Workflow 内部独立 Saga（scope = 子 Workflow）
│   │     → 子 Workflow 失败后，子 Saga 自动执行内部补偿
│   │     → 子 Workflow 返回 { success: false, compensationDone: true, ... }
│   │     → 父 Saga 知晓子已补偿完成，父自己的 Saga 只处理自己 scope 内的步骤
│   │   - 子 Workflow 无独立 Saga（scope 扁平化）
│   │     → 子 Workflow 返回已完成步骤清单 { completedSteps: [...] }
│   │     → 父 Saga 编排器将子 Workflow 的步骤视为自己的步骤统一补偿
│   │
│   │   推荐：默认为"子 Workflow 内部独立 Saga"模式——scope 隔离是最清晰、
│   │   最不容易出错的模型。仅在全异步无状态子 Workflow 时使用扁平化。
│   │
│   └── 依赖 #19 的标准化错误返回结构（{ success, error?, data? }），
│       需增加 compensationDone 和 completedSteps 字段。
│
├── SP8 补偿超时策略 ──→ 策略文档 + 配置化（开发量 0.5d）
│   │
│   │   compensate 的 timeout：
│   │   推荐：不设置 compensate 的硬超时。理由：
│   │   - 补偿是保证最终一致性的最后手段
│   │   - compensate 的 timeout 意味"放弃撤销"，留下不一致的中间状态
│   │   - 与其 timeout 后放弃，不如让运维人工介入
│   │   但如果 compensate 实际 hang（如死锁），需 SP6 的告警 + 人工介入。
│   │
│   └── 在 Saga 编排器的 compensate 执行层增加可配置的超时和心跳检测。
│
└── SP9 可观测性集成 ──→ 结构化日志 + D1 补偿事件表（开发量 1d）
    │
    │   补偿相关事件需要注册到观测性基础设施：
    │   - compensation.started: { instanceId, reason, completedStepCount }
    │   - compensation.step_executed: { stepId, result }
    │   - compensation.completed: { totalSteps, failedSteps, duration }
    │   - compensation.failed: { stepId, error, retries }
    │
    └── 写入 D1 compensation_events 表（#12 审计查询使用）

## 5. 关键假设与未决问题

### 5.1 关键假设

| # | 假设 | 置信度 | 来源/依据 |
|---|------|--------|----------|
| **AH1** | 原始 BPMN 流程中使用补偿边界事件的活动数 ≤ 5 个/流程，且补偿处理器的内容为单步 API 调用（少数可能为 2-3 步） | **中** | 补偿边界事件在 BPMN 实践中属于低频特性，大多数流程不显式使用。但若现有流程大量使用补偿（如金融/支付场景），每个 compensate 的实现复杂度会影响总工作量 |
| **AH2** | 自动化场景中，补偿的触发源主要是三个：step 执行失败（Saga 自动触发）、中断事件（#4 触发）、并行分支部分失败（#1 触发）。几乎没有"纯外部补偿信号"触发 | **中高** | 自动化场景消除了人工取消/回滚操作（#9/#10），外部触发补偿的需求相应减少。"纯外部补偿信号"指不经过 #4 中断子流程直接触发补偿的外部事件——在自动化场景中几乎不存在 |
| **AH3** | 补偿不需要支持"嵌套补偿"（即 compensate 内部又注册了补偿步骤） | **高** | BPMN 规范理论上允许（compensation handler 内部的活动可以有它自己的 compensation boundary event），但实践中极其罕见。在 CF Workflows 迁移中接受此限制——若有此类流程，需重构为多层 Saga |
| **AH4** | compensate 步骤的输入数据（原始 step 的 output）适合存储在 DO 中（单 step output 通常 ≤ 10KB） | **中高** | 如果单个 step 的 output 大于 DO 值限制，需像 #28（1MB payload 限制）一样使用 R2 引用。但在补偿场景中，compensate 通常只需要原始 step 的"关键输出 ID"（如 orderId、paymentId），而非完整 payload |
| **AH5** | 补偿的"事务边界"与 Workflow 的执行边界一致——一个 Workflow 实例 = 一个 Saga 事务 | **中** | 如果单个 Workflow 内包含多个独立的事务边界（如"阶段 1：创建用户 + 发送邮件"和"阶段 2：扣款 + 发货"是两个独立事务），需要在 Workflow 内支持多个 Saga 作用域。若此假设不成立，SP1 的 Saga 编排器需要支持"嵌套/分段 Saga" |
| **AH6** | 补偿不需要"部分回滚"后再"继续执行"的模式——补偿 = 全量逆序回滚 + 流程结束 | **中低** | BPMN 的补偿语义是"执行补偿后流程继续"还是"补偿后结束"取决于抛出补偿事件的上下文。在 Saga 模式中，标准实践是"补偿后流程结束（或至少该事务结束）"。若业务需要"补偿后换个路径继续执行"，则需要 Saga 编排器支持"补偿 + 恢复"的高级模式 |

## 6. 是否需要独立 plan-eng-review 的建议

### 6.1 建议：需要独立 plan-eng-review，且不缩减范围

**理由**：

1. **#8 不是任何已有 GAP 的附属品**。与 GAP #2（寄生在 #1 上）不同，Saga 编排器是独立的基础设施组件，有 9 个子问题需要设计。它虽然与多项 GAP 有交叉，但这些交叉是"Saga 编排器被其他 GAP 调用"的关系，而非"已由其他 GAP 覆盖"的关系。

2. **#8 是 Phase 1 的基础设施核心**。C-007 的 Phase 划分将 Saga 编排器放在 Phase 1 第一位——这意味着它的设计必须在 #1、#4、#5、#6 的详细设计之前完成，否则这些 GAP 的补偿接口将没有基线可对齐。plan-eng-review 的输出即为这一基线的核心部分。

3. **C-007 的 5-7d 估算需要具体化为可执行的工作包**。plan-eng-review 需要将 SP1-SP9 拆解为具体的设计决策、接口定义和工作量分解，而非停留在"需要 Saga 编排器"的概念层面。

4. **plan-eng-review 的交付重点**：
   - **SP1**：Saga 编排器核心 API 接口设计（register / markSucceeded / markFailed / compensateAll / compensatePartial / getStatus）
   - **SP2**：补偿状态持久化方案选择（DO vs D1 vs 内存）及 schema 设计
   - **SP3**：compensate 函数契约的 TypeScript 类型定义
   - **SP4**：与 #1 方案 B DO 聚合器的接口约定（JoinCoordinator → SagaCoordinator 的调用协议）
   - **SP5**：与 #4 中断控制流的集成点定义（cancelEventHandler 的回调签名）
   - **SP6**：compensate 步骤失败的重试策略与降级路径
   - **SP7**：子 Workflow 层级的补偿 scope 协议
   - **SP8**：补偿超时策略
   - **SP9**：可观测性集成点定义

5. **plan-eng-review 的产出范围约为 C-011 的 1.5 倍**。与 C-011（GAP #1）相比，Saga 编排器的子问题更多（9 vs 3-4），交叉 GAP 依赖更复杂（7 项 vs 3 项），但其核心概念（Saga）已是成熟模式，不需要像 #1 的 DO 聚合器那样从头探索。实际的增量工作量是各子问题的具体设计决策和接口定义。

**维持并强化理由**：

1. **交叉依赖广度在 8 项高 GAP 中居首位**。本期分析确认 #8 与 7 项其他 GAP 有中高度交叉耦合。这意味着 #1、#4、#5、#6 的补偿能力**都依赖 #8 就位**。Saga 编排器不是单点的补偿方案，而是 **"使所有其他 GAP 的失败处理逻辑完整"** 的基础设施层。如果 #8 不优先处理，其他 GAP 的方案设计都只能处理"成功分支"不能处理"失败分支"——即方案不完整。

4. **Phase 1 的时序位置决定了其设计基线性**。#8 在 C-007 Phase 1 首位——如果它的设计不完备，后续 #1/#4/#5/#6 在需要补偿集成时将各自造轮子，造成三倍的工作量浪费和后期的接口统一成本。

## 8. 本期结论

1. **语义层面**：补偿边界事件是 BPMN 中"撤销已成功完成的活动副作用"的机制，与 Saga 模式天然映射。其关键特征：(a) 逆序执行（LIFO），(b) scope 层级冒泡，(c) 与错误处理（执行中失败）有本质区别——补偿处理"已完成但需撤销"的步骤，(d) BPMN 还有"补偿事件子流程"变体（流程级别 vs 活动级别），但在自动化场景中差异缩小为 Saga 编排器的全局/局部 compensate。

2. **C-007 判定**：方向正确（Saga 模式），但存在四处遗漏——(a) 补偿 scope 和层级问题未讨论，(b) compensate 步骤本身的失败处理未覆盖，(c) 并行网关（#1）与补偿（#8）的交叉场景未分析，(d) 补偿状态持久化未作为独立基础设施需求提出。本期将这些遗漏识别为 SP4（并行部分补偿）、SP6（补偿失败处理）、SP7（子 WF 层级补偿）、SP2（状态持久化），构成对 C-007 方案的关键补充。

3. **补偿工程**：9 个子问题中，SP1-SP3 是 Saga 编排器的核心交付（6-7d），SP4-SP7 是与其他 GAP 的交叉集成（3.5-5d），SP8-SP9 是可靠性保障和可观测性（1.5d）。在前提 C（其他 GAP 部分就位）下，合计 5.5-8d——与 C-007 的 5-7d 基本一致但更精确化，且补充了编译器未覆盖的补偿失败处理和交叉集成。

4. **交叉依赖**：#8 是 8 项高 GAP 中交叉依赖最多的 GAP——与 #1、#2、#4、#5、#6、#19、#23 共 7 项 GAP 有中高度（≥40%）重叠。这决定了 Saga 编排器的接口设计必须在 #1/#4/#5/#6 的设计就位之前完成（以预留集成点），但也意味着 Saga 编排器的最终完整度需要等待这些 GAP 的逐步集成。

5. **等级建议**：维持高，且等级强化。理由：交叉依赖广度第一（7 项）、Phase 1 基线性（先就位决定其他 GAP 设计完整性）、补偿失败可靠性风险（C-007 未覆盖的盲区）。

6. **是否独立 plan-eng-review**：需要独立 plan-eng-review，不缩减范围。产出规模约为 C-011 的 1.5 倍，核心交付：Saga 编排器 API 设计（SP1-SP3）、交叉 GAP 接口设计（SP4-SP5）、补偿失败与可靠性保障（SP6-SP8）、可观测性集成（SP9）。

7. **未决问题处理**：QU1（补偿使用模式统计）和 QU2（补偿后结束 vs 继续）为高优先级，应在 plan-eng-review 前确认。QU3（多事务边界）、QU4（人工介入渠道）、QU5（外部系统 undo 能力）为中等优先级，可在 plan-eng-review 中并行分析。

8. **C-007 Phase 排布**：将 #8 放在 Phase 1 首位（Saga 编排器）的策略正确且已在本期分析中得到加强——推荐坚持此排布。Saga 编排器就位后，Phase 2 的 #1/#2/#4/#5/#6 可以在失败处理逻辑中直接调用 Saga，无需各自实现补偿逻辑的临时版本。
