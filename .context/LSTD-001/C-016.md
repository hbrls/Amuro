## 2. 六个判断问题回应

### 2.1 TASK-015 产出（C-015）是否充分界定了 GAP #4 在自动化场景下的影响范围和核心问题？

**是。** C-015 完整覆盖：

- §2.3：核心冲突——CF Workflows 引擎模型与 BPMN 事件子流程在"中断能力""事件监听范围""事件与流程耦合"上的五项根本差异
- §2.4：5 种自动化场景下的使用模式分析，确定"中断型 Message 驱动（外部取消指令）"为最高优场景
- §2.5：中断型事件子流程的 5 个关键子问题（P1-P5），明确 P2（任意时刻取消不可实现）为 CF Workflows 硬限制
- §3：与 GAP #1/#2 的技术语义差异（并发模型 vs 中断模型）、DO 基础设施复用可行性逐项分析
- §4：10 项关键假设（A1-A10），含置信度和验证方式
- §5：10 项未决问题（Q1-Q10），均已标明优先级和依赖
- §6-7：goal LENS 视角结论——与 GAP #1/#2 技术语义正交，需独立 plan-eng-review

### 2.2 补偿方案在 goal 阶段是否已勾勒出足够清晰的方向？是否需要进入 plan-eng-review 深度设计？

**方向已清晰，需进入 plan-eng-review。** C-015 §2.5 和 §7.2 已给出核心补偿方向：

| 方向要素 | 是否已勾勒 | 说明 |
|---------|----------|------|
| 核心补偿方向 | ✅ | DO InterruptCoordinator + step 边界 waitForEvent 检查点 + 中断处理步骤序列 |
| 中断响应机制 | ✅ | step 边界检查——CF Workflows 不支持 step 中途中断（硬限制 P2） |
| 信号暂存 | ✅ | 识别为关键子问题（Q7），但方案未推演 |
| DO 设计方向 | ✅ | InterruptCoordinator（中断标志存储 + 信号暂存），独立于 JoinCoordinator |

但以下内容必须在 plan-eng-review 中深化：

| 未推演内容 | 说明 |
|-----------|------|
| DO InterruptCoordinator 接口设计 | register/listen/cancel/signal 等接口的完整定义和状态机 |
| step 检查点模式标准化 | 每个 step 插入检查点的模板和 helper 设计 |
| 中断型 vs 非中断型分层策略 | 是否需要两套处理路径，还是统一抽象 |
| step 粒度设计指南 | "将长 step 拆分为短 step"的具体规范和阈值 |
| 中断信号在 step 运行期间到达的暂存机制 | DO 作为信号缓冲区 vs waitForEvent pending event 机制——需基于 Q2/Q3 验证结果确定 |
| 与 Saga 编排器（GAP #8）的接口预留 | 中断后是否需要补偿已执行步骤 |


与 GAP #2 的关键区别：GAP #2 因可完全复用 GAP #1 方案（"零新增架构"）而**不需要**独立 plan-eng-review。GAP #4 与 GAP #1/#2 在技术语义上**正交**（并发模型 vs 中断模型），C-015 §3.2 已确认 JoinCoordinator 不可直接复用，需要独立的 InterruptCoordinator 设计。

**结论：GAP #4 必须进入独立的 plan-eng-review。**

### 2.3 与 GAP #1/#2 的已有基础设施（DO 聚合器）是否有可复用的交集？若无，是否需要独立的补偿基础设施设计？

| 复用维度 | 结论 |
|---------|------|
| JoinCoordinator DO | ❌ 不可复用——管理"多子 Workflow 完成等待"与"外部中断信号接收传播"是不同的 DO 职责 |
| `workflow.start()` 子 Workflow 模式 | ❌ 不适用——事件子流程非 fork 语义 |
| `parallelCall()` helper（方案 A） | ❌ 不适用——内联并行与中断响应正交 |
| DO 作为状态存储模式 | ✅ 可复用——DO 作为"中断标志"的存储和查询中心，模式经验可迁移 |
| 子 Workflow 标准化模板 | ❌ 不适用 |

**需独立设计 DO InterruptCoordinator**，与 JoinCoordinator 并行存在。两者共享 DO 使用模式经验（幂等、超时、生命周期管理），但接口和状态机设计迥异。

对后续 GAP 的复用展望（C-015 §3.3）：
- GAP #6（定时边界事件）：非中断型的 DO 检查模式可部分复用
- GAP #8（补偿边界事件）：低复用——Saga 的触发源（步骤失败）与外部事件异步到达有不同的触发路径

### 2.4 是否仍有关键未决问题需要继续深入？

**有 3 项高优未决问题需在 plan-eng-review 阶段处理：**

| # | 问题 | 处理方式 |
|---|------|---------|
| Q1 | 现有 Flowable 流程中事件子流程的实际使用模式分布 | 需审查流程定义仓库；影响补偿方案设计重点。建议在 plan-eng-review 开始时获取，或在假设 A3 下先行设计 |
| Q2 | CF Workflows `waitForEvent()` 是否支持同时等待多个事件类型 | 需查阅 CF Workflows 最新文档；决定主流程中"同时等待 cancel 事件 + 正常完成信号"的实现方式。这是方案设计的基础能力假设 |
| Q3 | CF Workflows 在 `sleep()` 或 `waitForEvent()` 期间是否可通过 `sendEvent()` 唤醒 | 需查阅文档；如果等待期间不可被 sendEvent 唤醒，则轮询 DO 标志成为唯一选项 |

| Q4-Q7 | 中优先级 | 归入 plan-eng-review 阶段评估 |
| Q8-Q10 | 低优先级 | 不阻塞 plan-eng-review 推进，按需处理 |

Q1-Q3 均为阻塞性问题——若在不验证这些假设的情况下进入方案细节设计，可能导致方案在基础能力假设层面不成立。**建议 plan-eng-review 阶段首先处理 Q1-Q3。**

| 因素 | 分析 |
|------|------|

| 阻塞性假设 | Q1-Q3 高优先级假设若被推翻（如 waitForEvent 不支持多事件等待），方案设计可能需转向不同方向 |
