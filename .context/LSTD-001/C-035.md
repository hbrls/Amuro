## 1. 语义解构：历史流程实例查询

### 1.1 BPMN 历史查询的本质

在 Flowable/BPMN 引擎中，历史查询是通过引擎内置 API 对历史数据库表（`ACT_HI_*`）的直接查询。与运行时查询（`ACT_RU_*`）不同，历史表存储的是**已完成流程实例的完整执行记录**——实例完成后，运行时数据自动迁移到历史表。

BPMN 历史查询的核心能力：

| 查询维度 | BPMN API 示例 | 返回信息 |
|----------|-------------|---------|
| **历史流程实例列表** | `historyService.createHistoricProcessInstanceQuery()` | instanceId, processDefinitionKey, businessKey, startTime, endTime, duration, startUserId, deleteReason |
| **历史活动实例** | `historyService.createHistoricActivityInstanceQuery()` | 每个已执行的活动节点的 activityId, activityName, activityType, startTime, endTime, duration, assignee |
| **历史变量** | `historyService.createHistoricVariableInstanceQuery()` | 流程执行过程中每个变量的创建、更新、删除记录（带时间戳） |
| **历史任务实例** | `historyService.createHistoricTaskInstanceQuery()` | 每个任务的创建、分配、完成时间，包含 assignee 和审批意见 |
| **历史详情（form properties）** | `historyService.createHistoricDetailQuery()` | 流程推进过程中表单属性的变更记录 |
| **过滤与分页** | `.processDefinitionKey("orderProcess").finished().listPage(0, 50)` | 按流程定义、完成状态、时间范围、业务键等过滤 |

**关键特征**：
- 数据由引擎自动写入（开发者无需手动上报）
- 运行时数据和历史数据分离（不同表，ACT_RU_* vs ACT_HI_*）
- 历史表是**追加型**（append-only）——实例完成后的快照不再变更
- 历史变量记录了**每次变更**的时间线（不只是终值）

### 1.2 CF Workflows 的历史查询能力缺口

CF Workflows 是 Serverless 工作流引擎，**没有内置历史存储**。实例完成后，CF 引擎内部保留的记录及其可用程度：

| 手段 | 能力 | 缺口 |
|------|------|------|
| `wrangler workflows instances describe <id>` | 查看已完成实例（status, steps, output） | **保留期未知**（CF 未承诺保留期限）；不可程序化查询；不可按业务键检索 |
| `wrangler workflows instances list` | 列出实例（含已完成的） | **保留期未知**；返回字段有限（仅 id, status, created_on, version） |
| CF Dashboard → Workflows | 图形化查看已完成的实例 | 仅手工查看，无审计级保留保证 |

**核心缺口**：CF Workflows 没有"完整执行记录的持久化存储"。BPMN 历史表的核心价值——"完整的审计轨迹（audit trail）"——在 CF Workflows 中需要完全自建。

与 #11 运行时查询的对比——同样是"引擎不替你维护状态表"，但历史查询有本质区别：

| 维度 | 运行时查询（#11） | 历史查询（#12） |
|------|-----------------|---------------|
| **数据生命周期** | 活跃实例期间（分钟-小时） | 永久/长期保留（月-年） |
| **写入频率** | 高（每个 step 推进时更新） | 低（实例完成时一次性写入） |
| **数据量增长** | 稳态（完成即清理） | **持续增长**（永不删除，需归档策略） |
| **查询延迟要求** | 低延迟（ms 级，用于 Dashboard 轮询和流程内检查） | 中延迟（运维排查和审计查询，秒级可接受） |
| **数据完整性要求** | 可接受一定丢失（下一轮 step 推进自然修复） | **不可丢失**（审计数据缺失是合规缺陷） |
| **存储成本** | 低（仅活跃实例，~1KB/条 × 100-1000 条） | 持续累积（~10KB/实例 × 日完成量 × 保留年限） |

### 1.3 历史查询在 code-as-workflow 范式下的等价需求

在 BPMN 中，历史数据的写入是引擎自动完成的。在 CF Workouts 中，必须在 Workflow 完成时显式写入历史记录。这引出以下等价需求清单——在"自动审核 + 过程审计"约束下，历史查询需要回答：

| # | 问题 | 查询方 | 实时性要求 | 历史期限 |
|---|------|--------|----------|---------|
| Q1 | 某业务对象（如订单 X）关联的所有 Workflow 实例历史（含每次重试/补偿的完整执行链路） | 审计/运维排查 | 秒级 | 永久 |
| Q2 | 某时间段内某类流程的所有完成/失败实例列表及执行摘要 | 审计报表/运维分析 | 分钟级 | N 年 |
| Q3 | 某历史实例的完整执行轨迹——每一步的输入变量、输出结果、执行耗时、决策分支 | 审计/调试 | 秒级 | N 年 |
| Q4 | 某历史实例在每一步时所有变量的快照值（用于回溯"为什么当时判断走分支 A 而不是 B"） | 审计合规 | 秒级 | 合规期限 |
| Q5 | 某时间段内的流程执行统计——通过率、平均耗时、失败分布、补偿触发频率 | 运维分析/报表 | 分钟-小时级 | N 年 |
| Q6 | 按 businessKey 去重的实例历史（排除重试/补偿的中间实例，只看最终结果） | 审计/业务查询 | 秒级 | N 年 |
| Q7 | 某租户在某时间段内的所有历史实例（合规审计场景——"请提供 2025Q3 所有审批记录"） | 外部审计/合规 | 分钟-小时级 | 合规期限 |
| Q8 | 历史实例的补偿链路追踪——"原始实例 → 补偿实例 → 补偿的补偿"的完整因果链 | 审计/调试 | 分钟级 | N 年 |

**关键发现**：历史查询与运行时查询（#11）在 Q1-Q8 中有三个本质区别：

1. **时间窗口**：运行时查"现在"，历史查"过去"。历史查询需要处理的时间跨度是年级别，不是秒级别。
2. **查询目的不同**：运行时查询的目的是**运维**（"现在什么状态？"），历史查询的目的是**审计和追溯**（"当时发生了什么？为什么？"）。
3. **数据完整性要求不同**：运行时状态丢失可容忍（下一个 step 推进自然修复），但历史数据丢失不可逆——一旦 Workflow 完成且没有写入历史，审计链路断裂。

### 1.4 "历史"的时间边界与数据范围

```
实例生命周期：
CREATED → RUNNING → [WAITING / SLEEPING / PAUSED] → COMPLETED / FAILED / TERMINATED
│                                                      │
└── 运行时查询（#11）的范围 ────────────────────────────┘
                                                       │
                                                       └── 历史查询（#12）的范围
```

边界清晰——实例状态变为 `completed` / `failed` / `terminated` 的瞬间，从"运行时"进入"历史"。

但有几个边界模糊地带需要决策：

| 边界场景 | 问题 | 处理方式 |
|---------|------|---------|
| **实例完成后仍在运行时表中？** | 迁移到历史表还是保留在运行时表并标记 completed？ | C-033 SP5 推荐"独立双表 + 完成时迁移"（方案 A）。迁移是 #11 和 #12 的接口点 |
| **重试/补偿产生的新实例？** | 每次重试是一个新实例，但逻辑上是同一业务操作的"第 N 次尝试"。历史查询应能看到"订单 X 的所有执行尝试" | 需要在历史表中记录 `business_key` + `attempt_number`，或通过 `correlation_id` 关联 |
| **Saga 补偿产生的执行？** | 补偿 step 的执行是否也记录为历史？还是仅记录"补偿事件"？答案：需要记录补偿执行历史——审计需要知道"补偿做了什么" | 补偿 step 的执行也作为普通 step 记录写入历史（通过 #25 步骤追踪） |
| **挂起后恢复的实例？** | 多次挂起-恢复的实例，历史应记录什么？ | 历史记录最终执行轨迹（所有实际执行过的 step），挂起/恢复作为状态变更事件记录 |

## 2. C-007 判定再评估

### 2.1 C-007 对 #12 的判定回顾

> "历史查询是'过程审计'的核心依赖——审计需要追溯某次自动化审核的每一步决策依据、变量值、时间戳。这是用户明确确认需要的'自动审核 + 过程审计'能力的一部分。补偿方案：D1 存储每个完成的 Workflow 实例的完整执行记录（步骤、变量快照、时间戳）+ R2 归档超过 N 天的历史数据 + Worker API 提供查询接口。代价评估：中（D1 历史表设计 + 归档策略 + 查询 API，开发量约 5-7d）。修正后等级：维持高。维持理由：审计是明确需求，需完整的历史存储方案。"

### 2.2 覆盖度分析

| 语义维度 | C-007 是否覆盖 | 覆盖情况 |
|----------|--------------|---------|
| D1 作为历史存储 | ✅ 已覆盖 | D1 是合理的在线历史存储选择（可 SQL 查询、Serverless） |
| R2 归档 | ✅ 已覆盖 | R2 是大容量对象存储，适合归档冷数据 |
| Worker API 查询接口 | ✅ 已覆盖 | 与 #11 共享 Worker API 模式 |
| 历史表 schema 设计 | ❌ 未提及 | 与 #11 运行时表的关系（独立表 vs 单表 + status 区分）未定义。C-033 SP1 推荐独立两张表（方案 A），但历史表的独立字段（如 execution_summary、step_logs 嵌入等）未在 C-007 中设计 |
| 历史数据的写入时机与可靠性 | ❌ 未提及 | 实例完成时写入历史表。如果写入失败（D1 限流、网络故障、实例已完成但 D1 历史写入未成功）——历史数据永久丢失，审计链路断裂。C-007 未讨论这个"一次写入，不可重试"的可靠性风险 |
| 历史数据与步骤追踪日志的关系 | ❌ 未提及 | C-007 中 #25（流程追踪）和 #12（历史查询）是独立条目。但历史查询的"完整执行轨迹"依赖 #25 的步骤追踪数据——如果 #25 的 workflow_step_logs 表与历史表是独立的，历史查询 API 需要 JOIN 或两次查询，影响性能和复杂度 |
| 变量快照的粒度与存储策略 | ❌ 未提及 | C-007 说"变量快照"——但变量快照是每个 step 完整记录（类似 BPMN ACT_HI_VARINST 的每次变更记录），还是仅实例级别的起始/结束变量快照？前者存储量巨大（每实例 10 steps × 10 variables = 100 条记录），后者丢失了"中间步骤的变量演变过程" |
| R2 归档的迁移策略与反向查询 | ❌ 未提及 | "超过 N 天的历史数据归档到 R2"——归档后的数据是否仍可在线查询？还是仅可"恢复后查询"？归档是整条记录迁移，还是冷热分离（D1 保留摘要 + R2 存储详情）？这直接影响审计查询的响应时间 |
| 审计合规的保留期限 | ❌ 未提及 | 不同类型流程的审计保留期可能不同（金融流程 7 年 vs 普通流程 1 年）。C-007 未区分历史数据的保留策略 |
| D1 历史表的持续增长与查询性能退化 | ❌ 未提及 | 日完成 1000 实例 × 30 天 = 30000 条；日完成 1000 实例 × 365 天 = 365000 条；日完成 10000 实例（业务增长）× 365 天 = 3650000 条。D1 作为 SQLite，365 万行的全表扫描是不可接受的——必须设计分区、归档或时间分表策略 |

### 2.3 再评估结论

**C-007 的"D1 历史表 + R2 归档 + Worker API"方案在核心方向上正确，但存在五个结构性遗漏：**

1. **历史写入的"一次性窗口"风险未分析**。这是 #12 与 #11 的最关键区别。运行时查询的写入失败可以补偿（下一个 step 会更新状态），但历史写入在实例完成时仅有一次机会——实例已经不存在了，无法重试"再次完成"来写入历史。这意味着历史写入需要更强的可靠性保障（事务、重试队列、或离线补偿）。

2. **历史表 schema 设计未提出**。历史表与运行时表的关系（独立表 vs 共享表）是关键设计决策。C-033 SP1 推荐方案 A（独立双表），但历史表还需要额外字段——执行摘要（execution_summary）、起始/结束变量快照（variables_start, variables_end）、删除原因（termination_reason）、与 #25 步骤追踪的关联方式——这些在 C-007 中完全没有涉及。

3. **变量存储的粒度是一笔"隐藏工程债"**。C-007 的"变量快照"如果理解为"每 step 一个变量快照"（类似 BPMN `ACT_HI_VARINST`），存储量会是实例级别快照的 10-20 倍。这个粒度选择直接影响 D1 成本和查询性能——但 C-007 未讨论。

4. **R2 归档不是简单的"移文件"操作**。归档后的查询体验（是否需要恢复？查询多慢？）、归档粒度（整实例 vs 按年份分区）、恢复机制（自动重新加载到 D1 还是提供 R2 直接查询接口）都是影响方案可行性的设计决策，C-007 仅用"R2 归档"四个字概括。

5. **审计合规需求被假设但未分析**。C-007 说"审计是明确需求"是正确的，但并未分析审计的具体要求——保留期限、查询响应时间 SLA、审计日志的不可篡改性需求、是否需要数字签名或哈希链来保证记录完整性。

**C-007 的 5-7d 估算在新发现遗漏面前需要上调**。包含历史写入可靠性保障（+1-1.5d）、变量粒度决策与 schema 设计（+0.5-1d）、R2 归档策略与反向查询设计（+1-1.5d）、审计合规确认与分析（+0.5d）后，实际量约在 7-11d。

## 3. 自动化场景需求分析

### 3.1 历史查询的使用者与需求

在"自动审核 + 过程审计"约束下，历史查询的使用者分为四个角色：

| 角色 | 典型查询 | 实时性要求 | 查询频率 | 查询复杂度 |
|------|---------|----------|---------|----------|
| **运维排查人员** | "订单 X 的自动审核为什么被拒绝了？"——通过 businessKey 查执行轨迹，查看每一步的输入变量和判断结果 | 秒级（手动排查，等待 ≤3s 是合理的） | 低（按需） | 中高（关联本实例的步骤日志、变量快照） |
| **审计/合规人员** | "请提供 2025Q3 所有审批类流程的完整执行记录"——按流程类型 + 时间范围筛选，导出完整变量和步骤详情 | 分钟-小时级（批量查询，可异步） | 低（季度/年度审计） | 高（大批量导出，需支持按租户/时间/流程类型筛选） |
| **运维分析/报表** | "过去 30 天各流程的通过率、平均耗时、失败率趋势"——聚合统计查询 | 分钟-小时级（可预计算） | 中等（日报/周报） | 中等（聚合查���，可通过物化视图优化） |
| **业务系统（自动化流程内部）** | "该 businessKey 的历史实例中最后一次成功的执行结果是什么？"——用于幂等性判断或结果缓存 | 近实时（阻塞流程执行路径） | 中等（取决于业务流程逻辑） | 低（精确匹配查询） |

**关键发现**：与 #11 不同，#12 的使用者是"事后追查型"而非"实时监控型"。运维排查和审计合规是主要场景，对查询延迟的容忍度远高于运行时查询。

### 3.2 查询维度与过滤条件优先级

| 优先级 | 查询维度 | 典型过滤条件 | 使用者 |
|--------|---------|-------------|--------|
| **P0（必须）** | 按 instanceId 精确查询历史实例详情（含完整执行轨迹） | `instanceId = ?` | 所有角色 |
| **P0（必须）** | 按 businessKey 查找所有关联的历史实例（含重试/补偿） | `businessKey = ?`, 按 startedAt 排序 | 运维/审计/业务系统 |
| **P0（必须）** | 按流程类型 + 时间范围列出历史实例 | `workflowName = ?`, `startedAt >= ? AND startedAt <= ?`, 分页 | 审计/运维分析 |
| **P1（重要）** | 按完成状态筛选（completed / failed / terminated） | `status = ?` + 分页 | 审计/运维分析 |
| **P1（重要）** | 按租户筛选历史实例 | `tenantId = ?` | 审计合规 |
| **P1（重要）** | 按完成耗时筛选（"耗时超过 X 分钟的失败实例"） | `duration >= ?`, `status = 'failed'` | 运维分析 |
| **P2（增强）** | 按自定义标签筛选 | `tags @> ?` | 审计/运维分析 |
| **P2（增强）** | 历史变量值查询（"所有变量 X 值大于 Y 的历史实例"） | `variables->>'$.amount' > ?` | 高级审计 |
| **P3（按需）** | 聚合统计（按时段/流程类型/状态的计数和均值） | `GROUP BY workflowName, status`, 时间桶 | 报表/运维分析 |
| **P3（按需）** | 补偿链路追踪（"从原始实例找到所有补偿实例"） | `compensation_for = ?` 或 `correlation_id = ?` | 审计/调试 |

### 3.3 与 #11（运行时查询）的边界与共享设计

历史查询与运行时查询不仅是"同一份数据的不同时间窗口视图"——它们在设计上有本质的重叠与分离点：

| 维度 | 共享 | 分离 |
|------|------|------|
| **D1 数据库** | 共享同一 D1 数据库——但表独立（workflow_instances vs workflow_instance_history） | — |
| **基本字段** | instance_id, workflow_name, business_key, status, started_at, tenant_id, tags 共享定义 | 历史表独有：completed_at, duration, termination_reason, execution_summary, variables_start, variables_end。运行时表独有：current_step, updated_at, compensation_status |
| **写入路径** | 运行时写入 → 完成时迁移到历史表（#11 SP5） | 运行时写入由 RuntimeTracker SDK（#11 SP2）处理；历史写入在实例完成时由迁移逻辑（#11 SP5）处理——写入路径在同一代码中但时机不同 |
| **查询 API** | 共享同一 Worker（#14 管理控制台的基础设施），但端点分离 | `GET /api/v1/instances` — 运行时查询（仅查 workflow_instances 表）；`GET /api/v1/history/instances` — 历史查询（查 workflow_instance_history 表 + 关联 #25 step_logs） |
| **索引策略** | 共享索引设计理念 | 运行时索引用 `(workflow_name, status)` 和 `updated_at`（卡住检测）；历史索引用 `(workflow_name, started_at)`（按时间范围查询）和 `business_key`（业务对象关联） |
| **变量存储** | 运行时仅存 variables_summary（摘要），历史存完整快照（variables_start + variables_end） | 运行时不需要完整变量——查询量低、偶尔调试查看；历史需要完整变量——这是审计的核心数据 |
| **步骤记录** | 运行时仅暴露当前步骤（current_step），历史需要完整步骤时间线 | 运行时不需要完整步骤历史（占用空间且无运维用途）；历史必须关联 #25 的 workflow_step_logs |

### 3.4 历史查询的数据量估算

| 指标 | 估算 |
|------|------|
| **日完成实例数（稳态）** | 假设 200-1000 实例/天 |
| **单实例历史记录大小** | 实例记录 ~2KB（含 variables 摘要） + 步骤日志（平均 10 steps × ~500B/step） = ~7KB/实例 |
| **月度 D1 增量** | 1000 实例/天 × 30 天 × 7KB = ~210MB/月 |
| **年度 D1 增量（未归档）** | ~2.5GB/年（1000 实例/天）；日 10000 实例时 ~25GB/年 |
| **D1 存储上限** | CF D1 单数据库限制为 2GB（2024年公开信息）。若日完成超过 ~300 实例，单年历史数据即可超过 2GB，必须配合 R2 归档 |
| **关键推论** | D1 作为历史热数据存储的窗口约为 1-3 个月。超过此窗口的历史数据必须归档到 R2。但归档到 R2 后，需要保证"审计查询可以检索到归档的数据"——要么提供 R2 直接查询（需要恢复数据），要么 D1 保留索引摘要（仅 ID + 时间 + businessKey），R2 存储详情 |
| **R2 存储成本** | R2 存储成本极低（$0.015/GB/月）。年度 2.5GB × 7 年 ≈ 17.5GB，存储成本可忽略。成本焦点在于 R2 检索和恢复的工程设计，而非存储本身 |

## 4. 与 #11 的耦合设计

### 4.1 D1 Schema 联合设计框架

C-033 SP1 推荐的方案 A（独立双表）是正确的基线。在此基础上，历史表（workflow_instance_history）的 schema 设计应与运行时表在工作流命名、基础字段上对齐，但扩展历史独有的字段：

```sql
-- 运行时表（#11 SP1，复述 C-033 §4.2 的设计）

  instance_id TEXT PRIMARY KEY,
```

**字段对齐说明**：
- 共享字段（instance_id, workflow_name, business_key, status, started_at, tenant_id, tags, parent_instance_id, batch_id）与运行时表完全对齐——确保迁移时字段映射无歧义
- 历史独有字段（duration_ms, variables_start/end, execution_summary, termination_reason, correlation_id, compensation_for, attempt_number, archived_at, r2_object_key）是运行时不需要的——运行时不需要完整变量快照、不需要执行摘要、不需要归档标记
- `correlation_id` 作为跨表关联键——连接 #25 的 workflow_step_logs 表，用于"查历史实例时顺带看步骤详情"

### 4.2 迁移逻辑——#11 SP5 中历史表写入的完备性

C-033 SP5 定义的迁移流程（实例完成时）：

```
1. INSERT INTO workflow_instance_history SELECT FROM workflow_instances + computed fields
2. INSERT 追加步骤日志到历史 step_logs（如果 #25 的 step_logs 也需要归档）
3. DELETE FROM workflow_instances WHERE instance_id = ?
```

**本期对迁移逻辑的补全——历史写入的五个"必须"**：

1. **必须在同一 D1 事务中执行 INSERT INTO history + DELETE FROM instances**。如果 INSERT 成功但 DELETE 失败，实例会在两边都存在（但数据一致）；如果 INSERT 失败，实例留在运行时表（completed 状态），由定时任务重试迁移。D1 的 batch SQL 支持事务——可保证"要么全部成功，要么全部回滚"。

2. **必须预计算历史专用字段**（duration_ms, execution_summary等）而非依赖历史查询时计算。原因：实例完成后，运行时的 current_step、updated_at 信息会丢失——计算 duration 等字段的机会窗口仅在一次（迁移时）。

3. **必须处理迁移失败**——C-033 SP5 未详述的失败处理。三种策略：
   - (a) 迁移失败后，实例在运行时表中保留（status=completed），定时任务扫描并重试迁移
   - (b) 迁移失败但实例已从运行时表删除——创建"迁移补偿记录"（在另一张表 workflow_instance_history_pending 中记录待迁移的 instance_id），由定时任务从 wrangler 或 D1 日志中恢复
   - (c) 推荐：(a) 作为主路径，(b) 作为定时任务扫描异常情况的补充路径

4. **必须在迁移时写入 business_key 索引的可查询性**。在运行时表中 business_key 的索引服务于"查找活跃实例"（通常 0-1 条）。在历史表中，同一 business_key 可能有 10+ 条历史记录（重试、补偿多次执行）——索引设计需要支持快速按 business_key + started_at 排序。

5. **必须处理补偿实例的关联**。Saga 补偿产生的新 Workflow 实例，其历史记录需要通过 `compensation_for` 指向原始实例的 instance_id。迁移时必须写入此关联——审计需要追踪"补偿链路"。

### 4.3 R2 归档策略设计

R2 归档不是简单的"到时间就移"——需要精密的三层策略：

| 层次 | 数据 | 保留位置 | 保留期 | 查询能力 |
|------|------|---------|--------|---------|
| **热层（D1）** | 最近 N 天（例如 90 天）的完整历史记录（instance + step_logs + 变量快照） | D1 | 90 天 | 完整 SQL 查询，秒级响应 |
| **温层（R2 摘要索引 + D1 索引）** | 超过 90 天的历史记录：D1 仅保留摘要行（instance_id, workflow_name, business_key, status, started_at, completed_at, r2_object_key）；完整数据在 R2 中 | D1（索引行 ~200B/条）+ R2（完整数据 ~7KB/条） | D1 索引永久，R2 完整数据 7 年 | D1 索引可查"是否存在"和基础信息，完整详情需恢复 R2 数据到 D1 临时表 |
| **冷层（R2 only）** | 超过 7 年的历史数据（按合规策略可删除） | R2 | 按需 | 仅可用于批量恢复 |

**归档执行流程**：

```
定时任务（每日/每周执行）：
1. SELECT instance_id FROM workflow_instance_history
   WHERE completed_at < now() - 90_days AND archived_at IS NULL
   LIMIT 1000
2. FOR EACH batch:
   a. 从 workflow_instance_history 和 workflow_step_logs 读完整数据
   b. 序列化为 JSON 或 Parquet，写入 R2 (key = "history/{workflow_name}/{completion_date}/{instance_id}.json")
   c. UPDATE workflow_instance_history SET archived_at = now(), r2_object_key = ?
   d. DELETE FROM workflow_step_logs WHERE instance_id IN (batch) -- 仅删除已归档的步骤日志（热表瘦身）
3. 可选：从 workflow_instance_history 删除 archived_at IS NOT NULL 且 completed_at < now() - 365_days 的记录
   （仅删除 D1 中的行，R2 中完整数据仍在）
```

**归档后的查询策略**：

- 按 businessKey / instanceId 查历史：先在 D1 查索引行（有则说明在归档期），如 `archived_at IS NOT NULL`，提示用户"该记录已归档，恢复中..."——从 R2 加载 JSON 到临时内存/D1 临时表，返回完整数据
- 按时间范围查列表：若查询时间范围与 D1 热窗口重叠较多（如查"最近 6 个月"），D1 直接查 + 拼接 R2 恢复的冷数据
- 审计批量导出：异步任务——触发 R2 批量恢复脚本，完成后通知用户

## 5. 与 #25（流程追踪）的关系

### 5.1 历史查询对步骤追踪日志的依赖度

历史查询的 Q3（"某历史实例的完整执行轨迹"）和 Q4（"每一步的变量值"）**强依赖** #25 的 workflow_step_logs 表。没有 #25 的步骤级记录，历史查询只能回答"这个实例完成了"但无法回答"每一步发生了什么"。

| 历史查询需求 | 依赖 #25 的数据 | 依赖程度 |
|-------------|----------------|---------|
| 实例基础信息（workflow_name, businessKey, 启动/完成时间） | ❌ 不依赖 | — |
| 实例完整执行轨迹（step 序列，每步的时间和状态） | ✅ 依赖 workflow_step_logs（step_name, status, started_at, completed_at, input_snapshot, output_snapshot） | **强依赖** |
| 每步的变量快照 | ✅ 依赖 workflow_step_logs 的 input_snapshot / output_snapshot 字段 | **强依赖** |
| 执行耗时分解（每个 step 的耗时 vs 总体耗时） | ✅ 依赖 workflow_step_logs 的时间戳 | **中等依赖** |
| 补偿关联 | ✅ 依赖 workflow_step_logs 的 step_type = 'compensation' 标记 | **中等依赖** |

### 5.2 历史表中是否应冗余存储步骤摘要？

有两种设计路径：

| 方案 | 描述 | 优势 | 劣势 |
|------|------|------|------|
| **方案 H1（规范化）** | 历史表仅存 execution_summary（如 `{total_steps: 10, failed_step: "approveOrder", saga_triggered: false}`），完整步骤日志始终查 workflow_step_logs 表（JOIN 或两次查询） | 无数据冗余；历史表保持精简 | 历史查询必须 JOIN 步骤日志；归档后步骤日志也需归档或保留；D1 冷数据膨胀——步骤日志是历史数据中占比最大的部分（~70%） |
| **方案 H2（冗余摘要）** | 历史表的 execution_summary 字段中嵌入步骤摘要数组 `[{step_name, status, duration_ms}, ...]` | 历史查询的"执行轨迹概览"无需 JOIN；归档到 R2 时天然自包含 | 数据冗余（步骤摘要同时在 step_logs 和 history 中）；execution_summary 的 JSON 不是 SQL 可查询的（但步骤日志表可以） |

**推荐 H1 + 步骤日志也归档**。历史查询的"完整执行轨迹"部分总是需要关联步骤日志——冗余嵌入只是把 JOIN 换成了 JSON 解析，查询复杂度不降反增。步骤日志应在实例完成后随历史记录一起进入"D1 热窗口 → R2 归档"的相同生命周期。

### 5.3 历史 → 步骤追踪的数据关联设计

```sql
-- #25 workflow_step_logs（基于 C-033 引用的设计 + 本期扩展）
CREATE TABLE workflow_step_logs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  instance_id TEXT NOT NULL,          -- 关联 workflow_instances（运行时）或 workflow_instance_history（历史）
  step_name TEXT NOT NULL,
  step_order INTEGER NOT NULL,        -- step 在 Workflow 中的顺序（用于排序）
  status TEXT NOT NULL,               -- 'running' | 'completed' | 'failed' | 'compensating' | 'compensated'
  started_at INTEGER NOT NULL,
  completed_at INTEGER,
  input_snapshot TEXT,                -- JSON：step 输入变量快照
  output_snapshot TEXT,               -- JSON：step 输出变量快照
  error_message TEXT,
  step_type TEXT DEFAULT 'normal',    -- 'normal' | 'compensation' | 'wait_event' | 'sleep'
  archived_at INTEGER,               -- NULL = 在 D1，非 NULL = 已归档到 R2
  r2_object_key TEXT,
  FOREIGN KEY (instance_id) REFERENCES workflow_instance_history(instance_id)
);

CREATE INDEX idx_step_logs_instance ON workflow_step_logs(instance_id, step_order);
CREATE INDEX idx_step_logs_archived ON workflow_step_logs(archived_at);
```

**关键决策**：步骤日志不区分"运行时"和"历史"——同一张表，instance_id 在实例迁移到历史表后仍有效（因为历史表的 instance_id 与运行时表相同）。步骤日志的归档策略与历史表对齐：D1 热窗口（90 天）→ R2 归档 → D1 清理。

| **SP4** | **历史查询 API 设计** | 定义 Worker API 的历史查询端点：(a) `GET /api/v1/history/instances`（列表 + 过滤 + 分页 + 排序）；(b) `GET /api/v1/history/instances/:id`（实例详情，含 execution_summary + 步骤概要）；(c) `GET /api/v1/history/instances/:id/steps`（完整步骤时间线，关联 #25 步骤日志）；(d) `GET /api/v1/history/instances/:id/variables`（历史变量快照）；(e) `GET /api/v1/history/instances/stats`（聚合统计）。归档数据查询——如果数据已归档，API 返回 202 Accepted + "归档恢复中"，异步恢复后通知查询 | 与 #11 SP4 共享 API 设计模式，与本 API Worker 部署在同一 Worker（与 #14 共享 Worker）。#14 Dashboard 的历史查询页面直接调用此 API | **中**（~1.5-2d） |
| **SP5** | **变量快照的粒度决策** | 定义历史写入时的变量存储策略：(a) **实例级快照**（variables_start + variables_end）——仅记录启动和完成时的变量值；(b) **步骤级快照**（每步的 input_snapshot + output_snapshot 在 #25 step_logs 中）；(c) **决策**：实例级快照存在历史表（用于"初始条件是什么？最终结果是什么？"）；步骤级快照存在 step_logs（用于"每一步输入输出是什么？"）。历史查询 API 的"实例详情"返回实例级快照，"步骤详情"通过关联 step_logs 返回步骤级快照 | 与 #25 SP1（步骤日志 schema）耦合——步骤级快照的完整存储依赖 #25 的 workflow_step_logs input_snapshot/output_snapshot 字段 | **中低**（~0.5-1d） |
| **SP6** | **审计合规的元数据保留与不可篡改性** | 定义：(a) 不同类型流程的保留期限——关键流程（如审批）7 年，普通流程（如数据同步）2 年，由 `retention_policy` 配置控制；(b) 历史记录的不可篡改性——可选：写入历史表时计算记录哈希（SHA-256），哈希链关联上一条记录（类似区块链的简易版），用于审计时验证记录未被篡改；(c) 合规导出格式——支持导出为 CSV/JSON 或 PDF（带数字签名） | 独立审计合规需求，但应纳入 #12 整体设计而非后期添加。不可篡改的哈希链是可选的（成本低但增加写入复杂度） | **中**（~1-1.5d） |
| **SP7** | **D1 历史表持续增长的性能保障** | 定义当历史表积累数万-百万条记录时的查询性能策略：(a) 归档策略（SP3）天然减少 D1 在线数据量——热窗口仅 90 天；(b) 为高频查询预建覆盖索引——(workflow_name, started_at) 复合索引覆盖 P0 查询；(c) 聚合统计（SP4 的 stats 端点）通过定时任务预计算物化结果（存入单独的小表），避免在百万行级的历史表上实时 GROUP BY | 与 SP3（R2 归档）关联——归档是性能策略，不是仅存储策略。热窗口保留时间的确定基于"90 天内多少条记录"和"D1 单表查询性能的函数" | **中**（~1d） |
| **SP8** | **历史查询与 #11 的接口契约** | 定义 #11 和 #12 之间的接口：(a) 迁移触发器——#11 在 RuntimeTracker.markCompleted() / markFailed() 中调用迁移逻辑；(b) 迁移函数签名——`migrateToHistory(instanceId: string): Promise<MigrationResult>`；(c) 迁移失败处理——返回 `{success: boolean, error?: string, retryable: boolean}`，#11 根据 return code 决定是否立即重试或依赖定时任务；(d) #11 和 #12 共享的 D1 binding——同一 Worker 中的同一 D1 数据库 | 与 #11 SP5（迁移逻辑）和 SP2（RuntimeTracker SDK）耦合——本期定义接口契约的规格，实际实现在 plan-eng-review 和 implementation 中落地 | **中低**（~0.5-1d） |
| **SP9** | **历史查询的权限与访问控制** | 定义：(a) 历史查询 API 的认证——与 #11 查询 API 共享同一认证机制（CF Access / API Token）；(b) 租户级别的数据隔离——每个查询自动附加 tenant_id 过滤（从认证令牌中提取）；(c) 敏感字段的屏蔽——历史变量中可能包含 PII（如用户姓名、身份证号），查询 API 应根据角色过滤敏感字段 | 与 #24（租户隔离）耦合——#24 的权限模型直接应用于 #12 的历史查询 API | **中低**（~0.5-1d） |

### 6.4 与 C-007 Phase 排布的关系

C-007 将 #12（历史查询）放在 Phase 1——与 #11（运行时查询）、#25（流程追踪）、#8（Saga 编排器）、#23（重试/死信）、#24（租户隔离）同属"基础补偿设施"阶段。**本期分析确认此排布合理，且加强了一个建议**：

**#11 和 #12 的 D1 schema 必须联合设计，但 #12 的完整实现可以在 #11 之后再交付**。理由：

1. #11 的 RuntimeTracker SDK 是 #12 历史写入的**触发点**——没有运行时追踪，历史写入无处触发。因此 #11 的实现必须在 #12 之前。

2. 但 #11 和 #12 的 D1 schema（运行时表 + 历史表）**必须在同一设计阶段（plan-eng-review）联合产出**。运行时表的字段决定了迁移到历史表时哪些字段可复制、哪些需计算。若先设计运行时表、后设计历史表，后续的 schema migration 是必然的——新增字段、修改索引、调整迁移逻辑——这是典型的"分阶段设计但需要后续返工"模式。C-033 §4.4 已提出同样的建议，本期从 #12 侧再次确认。

3. #12 的 R2 归档策略可以在 Phase 1 后期实现——最初 90 天内不需要归档。但归档的 schema 设计（archived_at、r2_object_key 字段、归档索引）应在 Phase 1 的 schema 中预留——避免后期 schema change。

**推荐的 #11+#12 交付顺序**：

```
Phase 1（联合设计阶段，约 3-5d）：
├── D1 Schema 联合设计（#11 workflow_instances + #12 workflow_instance_history + #25 workflow_step_logs）
├── RuntimeTracker SDK 设计（写入接口 + 迁移触发点）
├── 运行时查询 API + 历史查询 API 联合端点设计
└── 迁移逻辑设计（#11 → #12 接口契约）

Phase 1a（#11 实现，约 4-6d）：
├── D1 运行时表创建
├── RuntimeTracker SDK 实现（SP2/SP3）
├── 运行时查询 API 实现
└── 迁移逻辑实现（实例完成时触发写入历史表）

Phase 1b（#12 实现，约 4.5-7d，在 #11 就位后）：
├── D1 历史表创建
├── 历史写入可靠性增强（迁移失败重试、定时补偿任务）
├── 历史查询 API 实现
├── R2 归档逻辑（在第 91 天之前就位）
└── 审计合规元数据
```

## 7. 关键假设与未决问题

### 7.1 关键假设

| # | 假设 | 置信度 | 来源/依据 |
|---|------|--------|----------|
| **AH1** | 实例完成时，RuntimeTracker 能可靠地调用 markCompleted/markFailed——即 Workflow 的最后一个 step 始终能执行到状态上报逻辑 | **中高** | 如果最后一个 step 本身失败（如抛出未捕获异常），markCompleted 可能不会执行。需要在 Workflow 级 try/catch 中确保终态上报——即使 step 失败，状态仍能写入历史 |
| **AH2** | D1 事务（batch SQL）能同时覆盖 INSERT INTO history + DELETE FROM instances + INSERT step_logs——即在 D1 的单个 batch 中完成迁移 | **中** | D1 基于 SQLite，支持 batch 执行。但 batch 的事务性在于"同一批次内的 SQL 要么全执行要么全不执行"——需要实际验证 D1 的 batch API 是否提供这一保证。如果不提供，需要自行实现两阶段提交或补偿逻辑 |
| **AH3** | D1 的单表在线存储窗口（90 天）在日完成 1000 实例的场景下足够（即 D1 单表 ~9 万条记录时查询性能可接受） | **中** | 9 万条记录在 D1 SQLite 中查询性能应良好（索引支持下 <100ms）。但如果日完成量上升到 5000-10000 实例，90 天窗口意味着 45-90 万条——需要在 plan-eng-review 中评估是否需要缩短热窗口（如 30 天）或引入时间分表 |
| **AH4** | R2 归档和恢复的延迟（批量索引扫描 + R2 GET + JSON 解析）在 5-10 秒内可达，对审计查询（异步场景）可接受 | **中高** | R2 读取延迟通常 <500ms（同区域）。批量恢复（100 条记录）的主要瓶颈是 R2 对象读取数——不是延迟，是并行读取的 QPS 限制。异步恢复的 5-10 秒目标在大多数场景下可达成 |
| **AH5** | 历史查询不需要实时推送或流式处理——所有查询都是请求-响应模式 | **高** | 审计和运维排查都是按需查询，没有"持续监听历史变更"的场景。这不同于运行时查询的 Dashboard 轮询 |
| **AH6** | 变量快照中不包含大对象（>10KB）——大对象已在运行时存入 R2，仅传递引用 key。历史变量快照中只存引用 key（而非完整对象） | **中高** | 基于 C-007 §28 的已知约束——CF Workflows 的 1MB payload 限制下，大对象本就通过 R2 引用处理。历史变量快照遵循同样的模式——存储引用 key，需要时从 R2 获取 |
| **AH7** | 审计合规的保留期限为 7 年（金融/审批类）、2 年（普通自动化流程）。完整删除规则在 plan-eng-review 中由用户确认 | **中** | 基于一般合规要求。实际规则取决于用户的业务领域和地区法规 |

### 7.2 未决问题

| # | 问题 | 优先级 | 建议处理方式 |
|---|------|--------|-------------|
| **QU1** | D1 的 batch SQL 是否提供事务性保证？——即 batch 内 INSERT INTO history + DELETE FROM instances + INSERT step_logs 三者要么全成功要么全失败？ | **高** | 在 plan-eng-review 启动前通过实际测试确认。如果 D1 batch 不提供事务性，需要设计两阶段提交（标记迁移意图 → 执行迁移 → 确认/回滚）或补偿逻辑 |
| **QU2** | 历史查询是否需要支持全文检索？——如"在历史实例的变量中搜索包含某关键词的所有实例" | **中** | 如果需要——D1 的 SQLite FTS5（全文搜索）扩展可用于在 variables_end JSON 上建立全文索引。但全文搜索通常不是审计查询的核心需求（审计按流程类型+时间范围，而非关键词搜索），优先度较低 |
| **QU3** | 归档到 R2 的历史数据格式——JSON（人类可读、易于恢复）还是 Parquet（存储压缩、批量查询性能好）？ | **中** | JSON 是更自然的归档格式（实例数据是文档型），且恢复时不依赖额外的反序列化库。Parquet 在"定期大批量分析历史数据"场景中有优势——但这不是 #12 的当前需求范围。推荐 JSON 作为第一版归档格式 |
| **QU4** | 被终止（terminated）的实例——是否也需要写入完整的历史记录？还是仅记录"被终止"事件？ | **中** | 被终止的实例的已执行 step 和中间变量仍有审计价值——应写入完整历史（所有已完成 step 的日志），termination_reason 标记为 'terminated_by_user'。如果终止发生在第 3 个 step，则仅记录前 3 个 step 的日志 |
| **QU5** | 历史查询的"恢复已归档数据"是否需要用户可见的进度条？——作为异步操作，用户可能等待 5-30 秒 | **中低** | 第一期不需要复杂的进度跟踪——202 Accepted + "归档数据恢复中，预计 10 秒完成" + 轮询即可。长期可在 Dashboard 中增加"恢复中 X/50 条"的进度指示器 |
| **QU6** | 是否需要历史查询的"变更日志"——如"历史记录 X 被标记为删除/被纠正/被标记为敏感" | **低** | 历史记录应是不可变的（append-only）。如果需要纠正错误记录——通过"更正记录"（新行标记 replaced_instance_id）而非修改原始行实现。这属于高级审计合规需求，可在 Phase 3 中添加 |
| **QU7** | 如果 CF Workflows 未来推出官方"历史查询 API"或延长实例保留期——对 #12 的补偿策略有何影响？ | **低** | 即使 CF 推出官方历史 API，它不太可能涵盖：(a) 自定义业务变量快照，(b) 与 #25 的步骤追踪关联，(c) R2 归档的多层热/温/冷架构，(d) 审计合规的保留策略。自建历史存储是"语义丰富度"的诉求，不是仅"存储"的诉求 |

## 8. 是否需要独立 plan-eng-review 的建议

### 8.1 建议：不独立——与 #11 联合进行 plan-eng-review

**理由**：

1. **#11 和 #12 共享同一 D1 schema 设计阶段**。C-033 和本期分析均已确认——运行时表和历史表必须联合设计（即使实现有先后）。独立的 plan-eng-review 意味着两个分离的设计文档，然后后续需要合并——这是一种组织形式上的额外开销，而不是架构上的清晰分界。

2. **#12 的 9 个子问题中 6 个（SP1, SP2, SP4, SP5, SP7, SP8）与 #11 有强耦合关系**。在同一个 plan-eng-review 文档中处理这些耦合问题，比在两个独立的文档中分别处理然后"对齐"效率更高。

3. **#12 没有独立于 #11 的独特架构挑战**。#8（补偿边界事件）有独立的 Saga 编排器架构挑战（独立的 plan-eng-review 合理）；#12 的挑战主要来自 schema 设计和归档策略——这些在 #11 的 plan-eng-review 中作为"联合 schema 设计"部分自然处理。

4. **联合 plan-eng-review 的产出规模约为单独的 #11 plan-eng-review 的 1.2-1.4 倍**（而非 2 倍——共享 design 部分减少重复工作）。结论：工作量上不会成为瓶颈。

## 10. 本期结论

1. **语义层面**：CF Workflows 无内置历史存储的本质是"引擎不为你保留已完成实例的完整执行记录"。BPMN 中历史数据的写入是引擎自动完成的（`ACT_HI_*` 表）；在 CF Workflows 中，必须在 Workflow 完成时显式将运行时数据迁移到自建历史表。这引入了 BPMN 中不存在的设计挑战：(a) 历史写入的"单次窗口"——实例完成后不能重试写入，写入丢失 = 永久审计链路断裂；(b) 变量快照的粒度——实例级 vs 步骤级；(c) 历史数据的持续增长与 D1 性能退化——需要归档策略。

2. **C-007 判定**：方向正确（D1 历史表 + R2 归档 + Worker API），但存在五个遗漏——(a) 历史写入可靠性未分析（单次窗口风险），(b) 历史表 schema 设计未提出（与运行时表的关系），(c) 变量快照粒度未决策（实例级 vs 步骤级，影响存储量 10-20 倍），(d) R2 归档反向查询设计未展开，(e) 审计合规的具体需求（保留期限、不可篡改性）未分析。本期将这些遗漏识别为 SP1-SP9，构成对 C-007 方案的关键补充。

3. **自动化场景需求**：历史查询有四个使用者——运维排查（按需查业务对象的历史执行轨迹）、审计合规（批量导出指定时间段内的完整执行记录）、运维分析（聚合统计通过率/耗时/失败趋势）、业务系统（查 businessKey 的历史状态用于幂等性判断）。查询维度 P0 必须支持：instanceId 精准查询（含完整步骤时间线）、businessKey 历史实例列表、流程类型 + 时间范围筛选。与 #11 不同，#12 的使用者是"事后追查型"——对延迟的容忍度远高于运行时查询。

4. **交叉依赖**：#12 与 #11（运行时查询）有最强耦合——共享 D1 schema 联合设计。运行时表和历史表必须一次性设计（即使实现分期）。#12 与 #25（步骤追踪）有"数据依赖"——历史查询的"完整执行轨迹"需要对步骤日志的关联查询。与 #8（补偿边界事件）有"语义关联"——补偿执行也产生历史，需要通过 compensation_for 追踪补偿链路。与 #14（管理控制台）有"消费者关系"——历史查询 API 是 Dashboard 的历史查询页面的数据源。

5. **问题拆解**：9 个子问题中，SP1-SP4 是核心交付（4-6d），SP5-SP9 是增强与合规（1.5-4d）。SP1（历史表 schema）与 #11 SP1 联合设计——推荐方案 A（独立双表），公共字段对齐。SP2（历史写入可靠性）是 #12 独有的挑战——实例完成后不能再重试写入，需要同一 D1 事务 + 迁移失败补偿任务。SP3（R2 归档策略）推荐三层架构——90 天热窗口（D1 完整）→ R2 温层（D1 索引摘要 + R2 详情）→ 7 年冷保留（R2 only）。

6. **等级建议**：维持高。理由：历史查询是过程审计的核心基础设施（不可省略）、数据完整性要求高于运行时查询（"单次窗口"不可恢复）、R2 归档架构是 CF 平台特定的工程设计（多层存储需要量身设计）、与 #11 联合 schema 设计的地位（设计质量直接影响 4+ 项 GAP 的数据层）。

7. **是否独立 plan-eng-review**：不需要独立——建议与 #11 联合进行 plan-eng-review。#11 和 #12 共享 D1 schema 设计阶段，6/9 个子问题与 #11 有强耦合。联合 plan-eng-review 的产出规模约为单独 #11 plan-eng-review 的 1.2-1.4 倍。核心交付：#11+#12 D1 schema 联合设计、RuntimeTracker SDK API（含迁移触发）、联合查询 API 设计、R2 归档架构设计、接口契约。
