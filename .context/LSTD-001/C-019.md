## 1. 目标重述

### 1.1 GAP #5 的本质

GAP #5 多实例（Multi-Instance）在 C-007 中被判定为**高 GAP**（维持高等级）。其核心语义来自 BPMN 规范的"多实例活动"（Multi-Instance Loop Characteristics）：对同一活动模板创建 N 个并行或顺序执行的实例，可选指定基数（loop cardinality）和完成条件（completion condition）。

CF Workflows 引擎无此原生能力。C-007 给出的补偿路径是"生产者-消费者"模式（Queue + N 个独立 Workflow + DO 聚合），预估开发量 5-7d。

### 1.2 本期的目标

在自动化场景（无人工审批、自动审核 + 过程审计）约束下，完成 GAP #5 的 goal LENS 分析，产出：

1. 多实例三种核心语义的拆分和 CF Workflows 原语映射
2. 自动化场景下多实例的典型使用模式
3. 与 GAP #1/#2 JoinCoordinator DO 的复用评估
4. 核心冲突分析（无原生循环基数、完成条件需应用层实现）
5. 关键假设梳理（含置信度和验证方式）
6. 未决问题提取（含优先级和依赖）
7. 是否需要独立 plan-eng-review 的初步判断

### 1.3 与 C-011（GAP #1）的关系

C-011 已在 GAP #1 的 plan-eng-review 中产出了 JoinCoordinator DO 的完整设计。方案 B（子 Workflow Fork + 轮询聚合）的接口 `register(instanceId, childIds)` / `reportDone(childId, result)` / `awaitAll()` 被明确标注为"可复用于 GAP #2 和 #5"。本期的复用分析是判断多实例补偿方案是否能以 C-011 基础设施为底座，而非从零设计。

## 2. 核心问题识别

### 2.1 多实例的三种核心语义拆分

BPMN 多实例活动的语义由三类正交配置项组成：

| 语义维度 | 配置项 | 可能取值 | 自动场景下的相关性 |
|---------|--------|---------|-------------------|
| **基数值** | loop cardinality | 固定整数值 / 动态表达式（运行时求值） | **高**。批量处理场景中 N 由数据集大小决定，是运行时变量 |
| **实例执行模型** | isSequential | true（顺序）/ false（并行） | **高**。顺序多实例与并行多实例在 CF Workflows 中的实现路径完全不同 |
| **完成条件** | completion condition | 所有实例完成 / N-of-M 完成 / 表达式求值 | **中高**。自动化场景常见"等待所有完成"，但"N-of-M 满足即继续"也可能出现 |

#### 2.1.1 基数值：固定 vs 动态

- **固定基数**（如 `loopCardinality = 5`）：设计时确定，类似 GAP #1 并行网关的"已知分支数"场景。补偿方式与 GAP #1 的 Fork 模式几乎一致——启动 N 个子 Workflow。
- **动态基数**（如 `loopCardinality = ${items.length}`）：运行时从数据中求值，N 可能是 1 到数百。这是多实例区别于并行网关的关键特征——GAP #1 的分支数在设计时已知，GAP #5 的实例数在运行时才确定。

**冲突**：CF Workflows 的 `workflow.start()` 需要在代码中逐个调用。对于动态基数 N，需要用循环调用 N 次 `workflow.start()`，CF Workflows step 内代码执行有 CPU 时间限制（30s paid / 15min），若 N 极大（如 N > 500），单 step 内循环启动可能存在瓶颈。

#### 2.1.2 实例执行模型：顺序 vs 并行

| 执行模型 | BPMN 语义 | CF Workflows 实现路径 | 复杂度 |
|---------|----------|----------------------|--------|
| **并行多实例** | N 个实例同时执行，各自独立生命周期 | `workflow.start()` × N → N 个子 Workflow 并行运行 → JoinCoordinator 聚合 | 中 |
| **顺序多实例** | 实例 1 完成 → 实例 2 开始 → ... → 实例 N | 主 Workflow 循环内 `workflow.call()` 串行调用子 Workflow（每次等待返回），或单子 Workflow 串行处理 | 低 |

**冲突**：
- 并行多实例的冲突与 GAP #1 相同——CF Workflows 无原生 fork/join。
- 顺序多实例的冲突较小——`workflow.call()` 的串行语义天然匹配顺序多实例，且不存在聚合等待问题。顺序多实例的复杂度主要在"完成条件评估"（如"前 3 个成功即停止后续实例"）。

#### 2.1.3 完成条件

BPMN 多实例的完成条件不是简单的"等待所有完成"，常见形态：

| 完成条件 | 语义 | CF Workflows 实现 | 复杂度 |
|---------|------|-------------------|--------|
| All complete | N 个全部完成（不管成功/失败） | JoinCoordinator.awaitAll() | 低 |
| N-of-M success | M 个中至少 N 个成功 | JoinCoordinator.awaitN(n, childIds) + 提前终止剩余 | 中 |
| Expression-based | 运行时表达式求值决定是否停止 | 每个子 Workflow 完成后重新求值表达式，满足则终止剩余 | 中高 |
| 提前终止 | 某一实例满足条件立即终止所有剩余 | 子 Workflow 间需要共享"终止标志"（DO 存信号），主 Workflow 检测到后终止其余 | 中 |

**冲突**：JoinCoordinator（C-011 方案 B）目前只设计了 `awaitAll()`，未支持 `awaitN()` 或提前终止。多实例的完成条件比并行网关的"全部完成"更复杂。

### 2.2 核心冲突总结

| # | 冲突 | 来源 | 影响 |
|---|------|------|------|
| C1 | CF Workflows 无原生循环基数概念 | 引擎模型差异 | 基数计算需在应用层完成，动态基数下的 N 次 `workflow.start()` 循环可能受 step CPU 时间限制 |
| C2 | 无原生并行实例启动/管理 | 同 GAP #1 引擎限制 | 需 JoinCoordinator DO 补偿，程度与 GAP #1 对等 |
| C3 | 完成条件需应用层实现 | BPMN 的 completionCondition 表达式引擎缺失 | 需在 JoinCoordinator DO 或主 Workflow 中实现完成条件评估逻辑 |
| C4 | 顺序多实例的"实例间数据传递" | 顺序多实例中，实例 N 的输出可能是实例 N+1 的输入 | CF Workflows 无此运行时的数据流原语，需在主 Workflow 循环中显式传递 |
| C5 | 大基数 N 下的启动性能瓶颈 | `workflow.start()` 调用速率限制 + step CPU 时间 | 对 N > 100 的批量场景，可能需要分批启动策略 |
| C6 | 提前终止需要跨子 Workflow 协调 | 无原生 broadcast/kill 原语 | 需 DO 终止标志 + 子 Workflow 主动检查 |

### 2.3 自动化场景下的多实例使用模式

基于"自动化场景为主、人工审核可忽略"的约束，多实例在自动化中的典型使用模式为：

| 模式 | 描述 | 执行模型 | 基数特征 | 完成条件 | 频率预估 |
|------|------|---------|---------|---------|---------|
| 批量审批 | 对 N 个订单并行执行相同自动审核逻辑 | 并行 | 动态（运行时订单列表大小） | All complete | **高频** |
| 批量通知 | 对 N 个渠道发送相同通知 | 并行 | 固定（渠道数 ≤ 5） | All complete | 中频 |
| 批量数据同步 | 将同一变更同步到 N 个下游系统 | 并行 | 固定或动态 | N-of-M (M≥1) 或 All complete | 中频 |
| 顺序重试处理 | 对同一操作按不同参数逐个尝试 | 顺序 | 动态（重试策略列表） | First success 或 expression | 低频 |

**模式分析结论**：
- 并行多实例（批量审批、批量数据同步）是自动化场景的**高频需求**，不可接受 GAP
- 顺序多实例相对低频且补偿简单（`workflow.call()` 串行循环），复杂度可控
- 完成条件以"All complete"为主，N-of-M 和 expression-based 为边缘需求

## 3. 与 GAP #1/#2 JoinCoordinator 的复用分析

### 3.1 C-011 JoinCoordinator 接口回顾

C-011 方案 B 设计的 JoinCoordinator DO 核心接口：

```
register(instanceId: string, childIds: string[]) → void
reportDone(childId: string, result: Result) → void
awaitAll(instanceId: string) → Result[]
```

C-011 §4.3 明确标注："方案 B 的 DO 聚合器可复用于 GAP #2 和 #5"。

### 3.2 多实例场景下的适配评估

#### 3.2.1 可直接复用的能力

| JoinCoordinator 接口 | 多实例语义映射 | 适配程度 |
|----------------------|--------------|---------|
| `register(instanceId, childIds)` | 主 Workflow 注册 N 个子 Workflow ID | **完全匹配**。GAP #1 的 childIds 是设计时已知的分支名列表，GAP #5 的 childIds 是运行时生成的实例 ID 列表（如 `["inst-1", "inst-2", ..., "inst-N"]`）。接口签名无需改变。 |
| `reportDone(childId, result)` | 每个实例完成时上报结果 | **完全匹配**。子 Workflow 模板的标准化出口（接收 parentInstanceId + instanceId + payload，返回统一结构）可直接复用。 |
| `awaitAll()` | 等待所有 N 个实例完成 | **完全匹配**于"All complete"完成条件。轮询逻辑和超时策略可直接复用。 |

#### 3.2.2 需要扩展的能力

| 需求 | 当前 JoinCoordinator 状态 | GAP #5 需要 | 扩展建议 |
|------|--------------------------|-----------|---------|
| `awaitN(n, childIds)` | ❌ 不支持 | N-of-M 完成条件 | 新增方法，DO 内部维护成功/失败计数器，满足条件时返回 |
| 完成条件表达式求值 | ❌ 不支持 | expression-based completion condition | DO 接收 completionExpression 字符串，每次 reportDone 后求值 |
| 提前终止信号 | ❌ 不支持 | 满足条件后终止剩余运行中实例 | DO 存储 `stopFlag`，子 Workflow step 间检查（通过 DO 或 `workflow.waitForEvent`） |
| 基数分批启动 | ❌ 不需要（GAP #1 分支数固定且 ≤ 5） | 大 N 场景需要分批 | 主 Workflow helper 内实现分批循环，逐批启动 |

#### 3.2.3 无法复用的能力（GAP #5 独有）

| 能力 | 说明 | 处理方式 |
|------|------|---------|
| 顺序多实例 | JoinCoordinator 的设计前提是所有子 Workflow 并行运行 | 顺序多实例不使用 JoinCoordinator，用 `workflow.call()` 串行循环即可。属于独立模式，不依赖聚合器。 |
| 实例间数据传递（顺序） | 实例 N 输出 → 实例 N+1 输入 | 主 Workflow 循环内显式传递，无需 DO 协调 |
| 基数计算 | GAP #1 的分支列表在设计时已知，GAP #5 的基数需运行时从数据中计算 | 在主 Workflow 的 fork 前置 step 中完成基数计算 |

### 3.3 复用成本评估

| 项目 | 是否已在 C-011 覆盖 | GAP #5 额外工作量 |
|------|-------------------|-------------------|
| DO JoinCoordinator 核心（register, reportDone, awaitAll） | ✅ 已覆盖 | 0d |
| 子 Workflow 模板（标准化入口+出口） | ✅ 已覆盖 | 0d |
| 超时策略 + 部分失败策略 | ✅ 已覆盖 | 0d |
| 幂等处理 | ✅ 已覆盖 | 0d |
| `awaitN()` 扩展 | ❌ 未覆盖 | 0.5d |
| 完成条件表达式引擎 | ❌ 未覆盖 | 1d |
| 提前终止信号 | ❌ 未覆盖 | 1d |
| 大基数分批启动 helper | ❌ 未覆盖 | 1d |
| 基数计算 helper | ❌ 未覆盖 | 0.5d |
| 单元测试 + 集成测试（增量） | 部分覆盖 | 2d |
| **合计增量** | — | **约 6d** |

**结论**：GAP #5 约 80% 的补偿基础设施可由 C-011 的 JoinCoordinator DO 直接覆盖。C-007 原始预估的 5-7d（独立开发）可降至约 6d（增量开发），且核心风险（DO 状态一致性、超时处理）已在 GAP #1 方案 B 中设计缓解措施。

## 4. 关键假设梳理

| # | 假设 | 置信度 | 依据 | 验证方式 |
|---|------|--------|------|---------|
| A1 | 自动化场景中多实例以"并行多实例"为主，"顺序多实例"为低频需求 | **中高** | GAP 定义为"多实例(并行)"，C-007 §2 描述均为并行模式；顺序多实例在自动化中的使用模式（顺序重试）天然低频 | 需统计原 flowable 流程定义中多实例活动的 `isSequential` 分布 |
| A2 | 完成条件以"All complete"为主，N-of-M 和 expression-based 为边缘需求（< 10%） | **中** | 基于 C-007 的自动化场景特征推断。批量审批、批量同步等典型场景均需等待所有实例完成。但无明显证据支撑。 | 需统计原流程定义中多实例活动的 completionCondition 配置 |
| A3 | 动态基数 N 通常 ≤ 100 | **中** | 基于自动化审批的典型批量大小估计。若实际场景有"对 10000 个订单执行相同流程"的需求，大基数策略需重新设计。 | 需确认原业务中多实例活动的最大基数 |
| A4 | 多实例活动的"活动模板"是单一 step 或无分支的顺序步骤链 | **中高** | 若活动模板内包含复杂的并行/分支结构（如"内嵌并行网关"），CF Workflows 单个子 Workflow 可实现，但复杂度上升。此假设基于多数审批流程的模板为简单顺序逻辑。 | 需抽查原流程定义中多实例活动内部的流程复杂度 |
| A5 | 实例间无需共享可变状态（并行模式） | **高** | 并行多实例的各实例操作不同数据项（如不同订单），无写冲突。若存在同一条数据被多个实例并发写入，需要额外的并发控制。 | 需确认多实例活动是否操作相同数据集 |
| A6 | 单个子 Workflow 实例的执行时间 ≤ 15 分钟 | **中高** | 自动化审批逻辑通常为对单条数据的规则判断 + API 调用，耗时秒级。若单实例涉及长时间的外部服务等待，属于异常情况。 | 需确认原 flowable 执行记录中单实例的平均/最大执行时间 |
| A7 | `workflow.start()` 的调用速率不受限（或限制远高于业务需求，如 ≥ 50/s） | **中** | CF Workflows 的速率限制未在公开文档中明确。若存在严格的 `workflow.start()` QPS 限制（如 10/s），大基数分批启动策略将成为必须。 | 需查阅 CF Workflows 最新文档或在实际环境验证 |
| A8 | GAP #1 的 JoinCoordinator DO 在 GAP #5 开发时已可用 | **中高** | 当前调度进度：GAP #1 处理中（TASK-009），GAP #5 排在第四位。若按 C-007 推荐的 Phase 2 并行推进，JoinCoordinator DO 应在 GAP #5 前完成。但取决于实际开发排期。 | 需 pilot 在调度时确认 GAP #1 与 #5 的开发时序 |
| A9 | 团队可接受 GAP #5 的增量补偿工作量（~6d + 流程适配） | **待验证** | C-011 A7 同类假设，需决策者确认 | 提交决策者确认 |

## 5. 未决问题提取

| # | 问题 | 优先级 | 依赖 | 说明 |
|---|------|--------|------|------|
| Q1 | 原 flowable 流程定义中多实例活动的实际使用模式分布（并行 vs 顺序、基数范围、完成条件类型） | **高** | 无 | 直接决定方案选择。若顺序多实例占比高，补偿工作量可大幅降低。若最大基数 > 1000，需设计分批启动和分批聚合策略。 |
| Q2 | JoinCoordinator DO 的设计是否需要在本期（GAP #1 plan-eng-review）就纳入 GAP #5 的扩展需求（`awaitN`、完成条件表达式、提前终止）？ | **高** | GAP #1 / C-011 | C-011 §4.3 建议"一次投入，三项复用"。若 C-011 的 DO 设计已确定，GAP #5 的扩展需作为后续变更叠加；若 C-011 尚在设计阶段，应尽早将 `awaitN` 和提前终止接口纳入。 |
| Q3 | `workflow.start()` 的实际调用速率限制是多少？ | **中** | 无（需实际环境验证） | 决定大基数策略。若限制宽松（≥ 50/s），单 step 循环启动 100 个实例无压力。若限制严格（如 5/s），需分批 + sleep 策略。 |
| Q4 | 大基数场景（N > 100）是否实际存在？若存在，是否需要单主 Workflow 管理还是引入 Queue 分发？ | **中** | Q1 | C-007 提及 Queue 方案（"主 Workflow 向 Queue 投递 N 条消息，N 个独立 Workflow 实例消费处理"），该方案解耦了基数与启动压力，但引入了 Queue 中间件和额外的运维复杂度。 |
| Q5 | 提前终止的"最小延迟"要求是什么？ | **中低** | 完成条件类型 | 若允许秒级延迟（子 Workflow 定期检查终止标志），DO 信号模式即可。若要求毫秒级立即终止，需评估 `workflow.terminate()` 或事件驱动方案的可行性。 |
| Q6 | 顺序多实例中的"实例间数据传递"是否需要从"实例 N-1 的完整执行上下文"传递到"实例 N"？还是仅需传递一个标量结果？ | **低** | 顺序多实例实际占比（Q1） | 若仅需标量结果（如"上一次尝试是否成功"），`workflow.call()` 返回值即可。若需完整上下文，需设计标准化数据传递契约。 |
| Q7 | CF Workflows 是否有计划支持 step 级并发或批量实例启动原语？ | **低** | 无（需关注 CF 产品路线图） | 与 C-011 Q2 同类——若 CF 即将支持原生能力，补偿投入可能冗余。但不应成为阻塞当前决策的理由。 |

## 6. 是否需要独立 plan-eng-review 的初步判断

### 6.1 判断

**建议：GAP #5 需要独立的 plan-eng-review，但范围可压缩。**

### 6.2 理由

| 因素 | 分析 |
|------|------|
| **与 GAP #1 的重叠度** | 并行多实例的 Fork/Join 核心机制与 GAP #1 高度重叠（~80% 复用 JoinCoordinator DO）。若 C-011 已完整设计 JoinCoordinator DO，GAP #5 的 plan-eng-review 可聚焦于"差异部分"：完成条件扩展、大基数策略、顺序多实例。 |
| **独立决策空间** | GAP #5 有独立于 GAP #1 的决策点：是否需要 Queue 分发模式、完成条件扩展的范围、顺序多实例的模式设计。这些不能简单套用 GAP #1 结论。 |
| **GAP 等级差异** | GAP #5 的动态基数特征使其比 GAP #1 多一个维度（基数管理），需要在 plan-eng-review 中评估大基数场景下的方案差异。 |
| **投入产出** | 若省略 plan-eng-review 直接进入方案设计，可能遗漏完成条件扩展和分批策略的边界条件设计。但若 GAP #1 的 C-011 已充分设计，GAP #5 的 plan-eng-review 可以是一个"轻量版"（1 轮即可收束），重点确认 Delta 需求。 |

### 6.3 推荐的 plan-eng-review 范围

```
GAP #5 plan-eng-review 应涵盖：
├── 确认 JoinCoordinator DO 对 GAP #5 的覆盖度（基于 C-011 最终设计）
├── 设计 GAP #5 增量接口：awaitN()、提前终止信号、完成条件表达式
├── 大基数策略（N > 100）：分批启动 vs Queue 分发 的取舍
├── 顺序多实例的轻量方案（workflow.call() 串行循环）
├── 多实例子 Workflow 模板标准化
├── 工作量复核（基于 Q1 的实际分布数据修正）
└── 接受/不接受判定（含分阶段策略）
```

## 7. goal LENS 视角结论

### 7.1 核心判断

**GAP #5 多实例不是 GAP #1 并行网关的子集或简单变体。** 它有独立的核心冲突（动态基数、完成条件、提前终止）和独特的低复杂度路径（顺序多实例只需 `workflow.call()` 串行循环）。但它在并行执行的补偿路径上与 GAP #1 高度重叠——**约 80% 的补偿基础设施可由 C-011 的 JoinCoordinator DO 直接复用**。

### 7.2 目标定位

GAP #5 的补偿目标应定位为：

1. **以 C-011 JoinCoordinator DO 为底座**，在其上增加完成条件扩展（`awaitN`、提前终止信号、表达式求值），而非重新设计独立的聚合器。
2. **并行多实例为主攻方向**（高频、高复杂度），顺序多实例为辅助路径（低频、低复杂度，不需要聚合器）。
3. **大基数策略需要被评估但不应成为首要设计目标**——先确认 Q1（实际基数分布），再决定是否需要 Queue 分发方案。
4. **完成条件策略分层**：先实现 All complete（覆盖 90% 场景），N-of-M 和表达式作为后续增强。

### 7.3 关键风险

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| JoinCoordinator DO 设计未纳入 GAP #5 需求，导致后续扩展成本高 | 中 | 增加 2-3d 重构工作量 | **即时行动**：在 C-011 plan-eng-review 阶段将 `awaitN` 和终止信号接口预留但暂不实现 |
| 大基数 N > 500 时 `workflow.start()` 循环突破 step CPU 时间限制 | 低中 | 需要架构级方案变更（引入 Queue） | 在 plan-eng-review 中评估分批启动方案的上限 |
| 实际多实例使用模式与假设 A1-A3 严重偏离 | 中 | 方案设计基准错误，需返工 | Q1 在 plan-eng-review 启动前取得答案 |
| 完成条件复杂度被低估（存在大量自定义表达式完成条件） | 低 | 表达式引擎开发量上升至 3-5d | plan-eng-review 中评估是否可简化为少数标准完成条件模板 |

### 7.4 对后续 LENS 序列的建议
