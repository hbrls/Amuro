# C-023 · GAP #6 定时边界事件——目标界定与问题解构

基于 `.agents/lens/goal/LENS.md` 的 goal 分析范式，针对 C-007 §2 GAP #6 的初始判定进行目标界定与问题解构。

---

## 1. 目标重述：GAP #6 的本质

### 1.1 BPMN 定时边界事件的核心语义

定时边界事件（Timer Boundary Event）在 BPMN 中是一种"附加到活动上、基于时间条件触发的边界事件"。其核心语义包含三个维度：

| 维度 | 中断型（Interrupting） | 非中断型（Non-Interrupting） |
|---|---|---|
| **行为** | 超时后终止所附活动，沿边界事件路径继续 | 超时后触发边界事件路径，但**原活动继续执行** |
| **BPMN 记号** | 实线圆圈 + 时钟图标 | 虚线圆圈 + 时钟图标 |
| **典型场景** | "审批超过 3 天自动拒绝" | "订单处理超过 5 分钟时发送提醒，但处理不中断" |
| **活动生命周期** | 被中断取消 | 不受影响，继续到完成 |

时间定义方式：
- **持续时间**（Duration）："附着的活动开始后 N 秒/分/小时"
- **周期**（Cycle）："每 N 秒/分/小时触发一次"（仅非中断型可用）
- **具体时间**（Date）："在某个具体时间点触发"

### 1.2 迁移到 CF Workflows 的定位

CF Workflows 的执行模型是**线性顺序步骤（step）序列**——每个 step 运行到完成才进入下一个 step。不存在 BPMN 的"边界事件附着在活动上、与活动并行监听、在条件满足时打断活动"的并行监听-打断语义。

GAP #6 的本质是：**如何在顺序执行的 Workflow 中模拟"基于时间的并行打断/提醒"行为。**

这与并行网关（#1）的多分支并行执行是不同的问题域——并行网关是"如何同时执行多个分支"，定时边界事件是"如何在执行一个任务的同时等待一个时间条件"。

## 2. 核心问题识别

### 2.1 问题拆解

将定时边界事件拆解为以下可独立处理的子问题：

```
GAP #6 定时边界事件
├── 子问题 A：中断型定时器（超时后跳过/终止当前 step）
│   ├── A1：计时能力——如何在 Workflow 内等待指定时间
│   ├── A2：中断能力——如何在计时到期时"打断"当前 step
│   └── A3：分支能力——超时后如何走替代路径
│
└── 子问题 B：非中断型定时器（超时后触发并行动作，原 step 继续）
    ├── B1：并行时钟——如何在 Workflow 执行的同时运行独立计时器
    ├── B2：状态感知——时钟触发时需要知道原 step 的当前状态
    └── B3：动作触发——时钟到期后如何触发 Webhook / 通知 / 补偿步骤
```

### 2.2 CF Workflows 原语映射

| 子问题 | BPMN 原语 | CF Workflows 可用原语 | 映射缺口 |
|---|---|---|---|
| A1 计时 | 持续时间/周期定时器 | `workflow.sleep(ms)` | sleep 是阻塞等待，不能与 step 并行 |
| A2 中断 | 边界事件中断活动 | 无直接原语 | step 一旦开始执行，无法从外部中断 |
| A3 分支 | 边界事件关联序列流 | `workflow.do` + 条件分支 | 需 sleep 后 + 状态检查 + 条件路由 |
| B1 并行时钟 | 非中断定时器与活动并行 | 无原语 | Workflow 内无法启动独立的并行计时器 |
| B2 状态感知 | 活动状态对边界事件透明 | DO / KV 存储状态 | 需主动写入状态，非自动感知 |
| B3 动作触发 | 边界事件流向目标 | Cron Trigger → Worker → 操作 Workflow | 需外部触发器 + Worker 逻辑串联 |

### 2.3 核心冲突分析

**根本性冲突**：BPMN 的定时边界事件是**声明式、并行、事件驱动**的机制——"当活动执行 + 时间条件满足时 → 触发边界事件路径"。CF Workflows 是**命令式、顺序、步骤驱动**的执行模型。

这导致：
1. **并行性缺失**：CF Workflows 的一个 step 在同一时间只做一件事。无法"一边执行 step 逻辑，一边等待计时器"。这是架构层面的根本差异，无法通过任何语法糖消除。
2. **中断性缺失**：CF Workflows 无原生 step 中断机制。`workflow.do()` 中的逻辑一旦开始执行，必须运行到结束或抛出异常才能离开当前 step。
3. **状态查询依赖**：非中断型定时器必须通过外部存储（DO/KV）查询 step 状态，引入了状态同步的延迟和不一致风险。

**C-007 中判定的合理性再确认**：
- C-007 对 #6 的判定"维持高"是正确的——中断型可通过 sleep + 状态检查模拟，但非中断型必须依赖外部 Cron Trigger + DO 状态存储，构成了架构层面的缺口。
- C-007 的补偿方案（中断型 `~1-2d`、非中断型 `~3-4d`）在"自动化场景"视角下合理，但需注意：非中断型的脆弱性（状态同步问题）在 C-007 中只是简单提及，未充分展开。

## 3. 自动化场景下的使用模式

### 3.1 典型使用场景

| 场景 | 类型 | BPMN 中的典型定义 | 自动化场景中的代码等价 |
|---|---|---|---|
| 外部 API 超时保护 | 中断型 | 调用外部 API，若 10 秒无响应则走降级路径 | `fetch(url, { signal: AbortSignal.timeout(10000) })` —— 实际上**已由 HTTP 客户端层解决** |
| 批量处理单条超时 | 中断型 | 处理订单项，每项超时 5 秒则跳过 | step 内循环 + per-item 超时检查 |
| 流程级超时告警 | 非中断型 | 整个流程执行超 1 小时发告警，但流程继续 | Cron Trigger 定期扫描 D1 中"运行超过 1h"的实例并发通知 |
| 阶段性提醒 | 非中断型 | 订单处理 5 分钟后发"即将超时"通知 | step 间插入 `workflow.sleep(300000)` + 通知 step（但这不是"非中断"语义——这是顺序语义） |

### 3.2 频率预估

**在自动化场景（无人工审批）下的实际需求频率：**

| 子类型 | 需求频率 | 判断依据 |
|---|---|---|
| 中断型定时器 | **中高** | 外部 API 超时保护是自动化场景的常见模式，但大部分超时保护已在 HTTP client / retry wrapper 层面解决，不需要 Workflow 层面的定时边界事件语义 |
| 非中断型定时器 | **低** | "继续执行 + 同时提醒"的模式在自动化中较少——大部分场景下，如果需要在 time T 后执行某动作，直接在 Workflow 中顺序编排为 step 即可（sleep + action）。非中断的"并行提醒"价值在于用户体验（如审批超时提醒），在纯自动化场景中需求弱化 |

**与 C-007 的一致性检查**：
- C-007 未区分中断型和非中断型的频率差异。从自动化场景的实际需求看，非中断型的 BPMN 语义在自动化场景中需求显著低于中断型。这影响工作量估计的优先级——"非中断型约 3-4d"的投入产出比可能低于 C-007 的隐含判断。

### 3.3 可降级性分析

一个值得进一步验证的观点：**中断型定时器在 code-as-workflow 范式中实际上是一种"设计模式"而非"基础设施缺口"**。原因是：

1. HTTP call 超时由 `fetch` 的 `signal`/`AbortSignal.timeout()` 处理（已内建）
2. step 执行超时可借助 `Promise.race` 模式——在 Workers 中以 "sleep step + 状态检查 step" 表达
3. Workflow 总超时（execution timeout）在 CF Workflows 中可通过配置设定，属于平台能力

这意味着**中断型定时器的补偿成本实际上可进一步降低**（从 C-007 的 `~1-2d` 降低到约 `0.5-1d` 模式文档化），而非中断型定时器才构成真正的架构缺口。

## 4. 与已有产出的复用评估

### 4.1 可复用资产分析

| 已有产出 | 与 GAP #6 的关系 | 复用可能性 | 评估 |
|---|---|---|---|
| **C-011 JoinCoordinator DO** | DO 作为结果/状态聚合器 | **部分复用** | DO 可作为"步骤状态持有者"——非中断型定时器的 Cron Trigger 检查 DO 来了解 step 是否还在执行。但 JoinCoordinator 的聚合逻辑（等待所有分支完成）与定时事件的"定时触发"逻辑不同，需扩展而非直接复用 |
| **C-021 提前终止信号** | 多实例中的提前终止机制 | **可参考但不可复用** | 提前终止信号是"外部触发的终止指令"，定时边界事件的"超时终止"是其特例（时间条件触发的终止）。两者的信号机制可统一，但触发条件不同（时间 vs 结果满足） |
| **C-007 中提及的 Cron Trigger** | 外部定时触发器 | **直接可用** | Workers Cron Triggers 是 CF 平台内建能力，零成本可用。非中断型定时器可直接基于此构建 |
| **#11/#12 运行时/历史查询 D1 表** | Workflow 状态索引 | **间接依赖** | 非中断型需要查询"哪些 Workflow 运行超时"，依赖 D1 索引中记录的 `started_at`、`current_step` 等信息 |

### 4.2 建议的统一基础设施方向

如果 #1（并行网关）、#5（多实例）、#6（定时边界事件）都需要"DO 作为状态持有者 + 外部触发检查"的模式，可以提取一个统一的 `WorkflowObserverDO` 基础设施：

```
WorkflowObserverDO
├── 状态追踪：当前 step、开始时间、预期完成时间
├── 超时配置：每个 Workflow 定义各 step 的超时阈值
├── 中断信号：外部 Cron Trigger 可设置 "should_abort" 标志
└── Workflow 端检查：在 step 间调用 observer.getState() 检查是否有中断信号
```

这可以同时服务于：
- 定时边界事件（#6）—— 超时触发中断/提醒
- 事件子流程（#4）—— step 间检查外部事件
- 多实例提前终止（#5 / C-021）—— 提前终止信号传递

---
**结论**：C-011 和 C-021 的产出提供了**可参考的模式**（DO 状态持有 + 信号传递），但不构成直接复用。建议在后续 plan-eng-review 中考虑统一的"Workflow 中断/信号基础设施"以避免重复建设。

## 7. 是否需要独立 plan-eng-review 的初步判断

### 7.1 判断结论

**推荐进行独立 plan-eng-review**，但建议在以下条件满足后进行（避免在不必要分析上浪费工程讨论轮次）：

1. Q1 和 Q3（高频问题）有明确答复——确认定时边界事件在现有流程中的实际使用情况
2. #4 事件子流程的 plan-eng-review 完成后——可以评估"中断/信号基础设施"的统一可行性

### 7.2 推荐范围

| plan-eng-review 应覆盖的内容 | 理由 |
|---|---|
| 中断型定时器的标准化模式设计——step 间 timeout 检查的标准 pattern | 直接决定每个使用定时边界的流程如何改造，是最核心的工程产出 |
| 非中断型定时器的取舍决策——是降级为"用 sleep + action step 替代"还是构建外部 Cron Trigger + DO 检查基础设施 | 取决于 Q3 的结论，如果 Q3 确认无不可替代用例，则非中断型不纳入 plan-eng-review 范围 |
| 与 #4、#5 中断信号的统一设计评估 | 避免三个 GAP 各自独立建设重叠的基础设施 |
| sleep 精度/可靠性边界测试方案 | 验证 CF Workflows sleep 是否足以支撑中断型定时器的需求 |
| 状态同步的最终一致性方案 | 非中断型（如果需要）中最脆弱的一环——Cron Trigger 检查 DO 时的状态可能不是最新的 |

### 7.3 推荐不纳入 plan-eng-review 范围的内容

- Cron Trigger 本身的实现（CF 平台内建能力，无工程设计）
- Webhook 通知的实现（标准能力，与 #7 升级告警共用基础设施）
- 具体流程的逐项改造方案（应落在实际迁移阶段，不属于 GAP 分析层面）

### 7.4 阻塞条件

**plan-eng-review 的启动应阻塞在以下条件上：**
1. Q1（流程中定时边界事件的实际使用统计）已回答——否则无法判断投入是否合理
2. Q3（非中断型是否有不可替代用例）已回答——否则 plan-eng-review 的范围无法确定
3.（建议）C-019 / C-021 的 GAP #5 结论已稳定——作为复用评估的参考基线

## 总结

GAP #6 定时边界事件的核心是**"如何在顺序执行的 CF Workflows 中模拟基于时间的并行打断/提醒行为"**。

从自动化场景视角的再分析：
- **中断型定时器**：实际需求中高，但补偿成本低——大部分超时保护在 HTTP client 层已解决，剩余需求可通过 sleep + 状态检查的标准化模式覆盖（实际工作量预估较 C-007 的 1-2d 更低，约 0.5-1d）
- **非中断型定时器**：自动化场景中需求低，但一旦需要就需要完整的外部基础设施（Cron Trigger + DO 状态检查，约 3-4d）。其价值取决于 Q3 的结论——如果"并行提醒"在自动化场景中可被"顺序 sleep + action step"替代，则非中断型可实质上接受（降级为低），此时 GAP #6 整体从"高"可降级为"中"
- **与 #4, #5 的统一机会**：三个 GAP 都涉及"Workflow 被外部信号中断"，建议在 plan-eng-review 阶段评估统一设计的可行性，避免重复建设

**当前 GAP 等级评估（自动化场景下）**：建议在 Q1/Q3 回答后重新判断——若 Q1 确认低频 + Q3 确认无非中断型硬需求，则 GAP #6 可降级为"中"。
