# C-037 · Goal LENS 视角澄清

> 视角：goal
> 关联：TASK-037

---

## 1. 重述当前目标

**两阶段最小迁移实验**，用实践验证 Cloudflare Workflows 的五项基础能力：

| 实验 | 验证点 |
| --- | --- |
| 实验一：最小 Workflow 部署与运行 | ① 可部署 ② 可启动 ③ 多实例并发启动 ④ 执行日志可观测 |
| 实验二：外部 HTTP 调用 | 在实验一基础上 → 调用 httpbin.org/get，打印请求/响应日志，观察多实例并发下的外部调用行为 |

**目标定位**：这是工程验证实验，不是架构迁移。目标是用最小成本建立对 Cloudflare Workflows 基础能力的直觉和事实依据，为后续运行时状态、历史审计、可靠性、并发、可观测性等更高阶问题的设计提供实践地基。

---

## 2. 识别核心问题

### P0 — 实验范围的边界在哪儿？

当前材料中明确列出了五个验证点（部署、启动、并发、日志、外部 HTTP），但未明确每个验证点的"完成"标准是什么。

- "能部署一个 Workflow"：是指 wrangler deploy 成功即可，还是需要对部署状态做某种断言？
- "能同时启动多个 Workflow 实例"：多少算"多"？2 个？10 个？是否有并发启动时序期望？
- "日志能被开发者观察到"：通过 wrangler tail？Dashboard？还是需要程序化获取日志？
- "外部 HTTP 调用"：只需一次成功调用，还是需要验证重试、超时、错误处理？

**结论**：成功标准需要在实验设计阶段被细化，但不影响启动——实验一和二的最小性本身就允许在过程中逐步明确。

### P1 — 实验一和实验二的耦合关系是什么？

材料中将实验二定义为"在实验一基础上"，但未明确：
- 实验二是实验一的独立追加（即实验一通过后再做实验二），还是实验一保持运行、实验二在其产物之上叠加？
- 如果实验一失败，实验二是阻塞还是可以单独进行？

**结论**：建议将两个实验视为顺序依赖——实验一验证通过后，在同一 Workflow 定义中追加 HTTP 调用能力成为实验二。这符合"从简单开始"的约束。

### P2 — 实验产物的生命周期

实验产生的 Workflow 部署是一次性用完即弃，还是需要保留作为后续实验的基础？
- 如果保留，命名、环境隔离、清理策略需要提前约定。
- 如果用完即弃，每个实验是否需要独立的部署和清理步骤？

**结论**：短期实验可以复用部署产物（同一 Workflow 定义逐步演进），但每次实验结束时应明确验证完成状态并在日志中可追溯。

## 3. 梳理关键假设

| # | 假设 | 风险 | 验证方式 |
| --- | --- | --- | --- |
| A1 | Cloudflare Workflows 的部署流程与 Workers 相同（wrangler deploy 即可） | 低 | 实验一中直接验证 |
| A2 | Workflow 实例的并发启动不受平台配额或限流影响 | 中 | 实验一中 10+ 实例并发启动可部分验证 |
| A3 | Workflow 执行日志可通过 wrangler tail 或 Dashboard 实时/准实时观测 | 中 | 实验一中验证日志可观测性 |
| A4 | Workflow 内部可发起对外部 HTTP 端点的请求（无网络/安全策略阻止） | 低 | 实验二中直接验证 |
| A5 | httpbin.org/get 作为外部端点可访问且返回格式稳定 | 低 | 实验二中直接验证 |
| A6 | 单文件 Workflow 定义足以覆盖实验一和实验二的需求，无需引入 D1/R2/KV 绑定 | 中 | 实验设计阶段确认，执行中验证 |
| A7 | 多实例并发启动时，各实例日志不会混杂到不可区分 | 中 | 实验一和二均需验证 |

### 假设分级说明

- **低风险**：假设很可能成立，即使不成立也有成熟应对方案。
- **中风险**：假设可能不成立，如果不成立会显著影响实验结论或后续设计方向。需要实验中积极验证。

## 4. 标记未决问题

| # | 问题 | 影响 | 建议 |
| --- | --- | --- | --- |
| Q1 | **多实例"并发启动"的具体并发度**未定义 | 实验一验证标准模糊 | 建议起点：10 实例并发启动，后续按需要调整 |
| Q2 | **日志观测的具体方式**未确定 | 影响实验一成功判断 | 优先用 wrangler tail，Dashboard 作为备选 |
| Q3 | **Workflow 是否支持在 wrangler.toml 中配置绑定**（如将来需要的 D1/R2） | 不影响当前实验但影响后续方向 | 实验过程中顺带确认，不做为验证点 |
| Q4 | **Cloudflare Workflows 的配额与定价**对实验的影响未知 | 可能限制并发实例数或执行时长 | 实验前浏览 Cloudflare 文档确认免费层限制 |
| Q5 | **实验二的外部调用是否涉及鉴权** | httpbin.org 不需要，但迁移目标中的真实外部服务需要 | 当前实验不涉及，但需在结论中标记为后续需要验证的点 |
| Q6 | **Workflow 实例的启动方式**（API 触发 vs Dashboard 手动 vs 其他） | 影响实验脚本设计 | 优先使用 wrangler CLI 触发，可脚本化 |

## 5. Goal LENS 视角结论

### 判断：实验目标是清晰的、可执行的，可以进入执行阶段

**理由**：

1. **目标边界已有定义**：五个验证点（部署、启动、并发、日志、外部 HTTP）构成清晰的 MVP 边界，虽是基础能力验证，但恰好是后续所有高阶设计的前提。不验证这些就去设计运行时查询/历史审计是空中楼阁。

2. **风险可控**：七个关键假设中，五个是低风险（A1, A4, A5, A6 可快速验证，A7 有成熟应对方案），两个中风险（A2, A3 配额/限流和日志延迟）但即使不成立，实验规模足够小，不会造成大的资源浪费。

3. **未决问题不构成阻塞**：六个未决问题中，Q1-Q2 可在实验设计时快速确定（建议值已在表中给出），Q3-Q6 要么不影响当前实验，要么可在实验执行中顺带确认。

4. **符合用户约束**：实验一和实验二严格遵循"从简单开始""不一次性实现完整迁移架构""优先验证可部署/可启动/可并发/可日志/可外部 HTTP"的约束。

5. **前序分析已有充分铺垫**：三个 WORKSHOP 和多个澄清卡片已覆盖迁移可行性、高 GAP 项目分析，并从理论上排除了硬阻断项。此时进入实践验证是合理的时序选择。

### 建议

- 在进入 pilot LENS 之前，建议在实验设计文档中补充每个验证点的具体成功标准（参考 Q1/Q2 的建议值）。
- 实验完成后，建议用这次的小规模实验结论更新假设表（A1-A7 哪些确认成立、哪些被推翻），作为下一轮更大规模实验的输入。
