## 1. 语义解构：运行时流程实例查询

### 1.1 BPMN 运行时查询的本质

在 Flowable/BPMN 引擎中，运行时查询是通过引擎内置 API 对运行时数据库表（`ACT_RU_*`）的直接查询。其核心能力包括：

| 查询维度 | BPMN API 示例 | 返回信息 |
|----------|-------------|---------|
| **流程实例列表** | `runtimeService.createProcessInstanceQuery()` | instanceId, processDefinitionKey, businessKey, startTime, startUserId, suspended, tenantId |
| **当前活动节点** | `runtimeService.createExecutionQuery()` | 每个执行路径（execution）的当前 activityId、activityName、isActive |
| **流程变量** | `runtimeService.getVariables(instanceId)` | 当前实例所有变量的 key-value 快照 |
| **过滤与分页** | `.processDefinitionKey("orderProcess").active().listPage(0, 50)` | 按流程定义、状态、业务键、时间范围等过滤 + 分页 |
| **挂起/激活状态** | `.suspended()` / `.active()` | 实例是否处于挂起态 |

这些能力的基础是引擎内部的**运行时数据库**——引擎在每次流程推进时自动写入当前的执行状态、变量、活动信息。查询是对这些自动维护的表进行 SQL 查询。

### 1.2 CF Workflows 的查询能力缺口

CF Workflows 作为 Serverless 工作流引擎，**不暴露内部运行时状态存储**。其原生可用的查询/观测手段：

| 手段 | 能力 | 与运行时查询的差距 |
|------|------|-------------------|
| `wrangler workflows instances describe <id>` | 查看单个 Workflow 实例的当前状态（status, current step, output） | **仅单个实例**，无批量列表，无过滤，非程序化 API |
| `wrangler workflows instances list` | 列出实例（id, status, created_on, version） | **CLI only**，无程序化 API，无可自定义过滤条件，无自定义字段（如 businessKey） |
| CF Dashboard → Workflows | 图形化查看实例列表和状态 | 仅 Dashboard，不可编程查询，不可集成到运维系统 |
| Workers Tail | 实时日志流 | 非结构化查询，不可用于批量实例状态汇总 |

**核心缺口**：CF Workflows 没有暴露一个可供程序化查询的"运行时状态数据库"。`wrangler` CLI 虽然提供了基础功能，但它：
- 不是 REST API（无法集成到 Dashboard、告警系统、自动运维脚本）
- 查询维度固定（无法按 businessKey、流程类型、自定义标签过滤）
- 不包含自定义运行时信息（如当前步骤名称、业务变量值）
- 性能和可用性无 SLA（依赖 CF 内部系统）

### 1.3 运行时查询在 code-as-workflow 范式下的等价需求

在 BPMN 中，运行时查询的数据来源是引擎自动维护的运行时表。在 CF Workflows 的 code-as-workflow 范式中，**没有引擎替你维护状态表**——必须在 Workflow 代码中显式写入状态。

这引出一个关键的范式转换：

| 维度 | BPMN（引擎维护） | CF Workflows（自维护） |
|------|-----------------|----------------------|
| **状态写入** | 引擎在每次事务提交时自动写入 | 每个 Workflow 在关键节点显式调用状态上报 |
| **写入时机** | 隐式（引擎内部） | 显式（需要开发者决定何时上报） |
| **写入可靠性** | 引擎保证（与事务一致） | 取决于自建上报逻辑的正确性和可靠性 |
| **查询接口** | 引擎 REST API（标准 SQL 语义） | 自建 Worker API（需自行设计查询语言和接口） |
| **状态 schema** | 固定（引擎定义的表结构） | 灵活（可自定义字段，但需自行保证 schema 演化兼容） |

**等价需求清单**——在自动化场景下，运行时查询需要回答以下问题：

| # | 问题 | 查询方 | 实时性要求 |
|---|------|--------|----------|
| Q1 | 当前有多少 Workflow 实例在运行？ | Dashboard / 监控 | 秒-分钟级 |
| Q2 | 哪些实例卡住了（长时间未推进）？ | 监控告警 / 运维排查 | 分钟级 |
| Q3 | 某个特定业务对象（如订单 X）关联的 Workflow 实例当前在哪个步骤？ | 运维排查 / 客服查询 | 近实时（秒级） |
| Q4 | 某类流程（如"支付审批"）的当前执行分布（多少在 step A，多少在 step B）？ | Dashboard / 运维分析 | 分钟-小时级 |
| Q5 | 当前有多少实例处于"暂停"或"等待外部事件"状态？ | 运维排查 | 分钟级 |
| Q6 | 实例 X 的当前变量值是什么（用于排查"为什么这个判断走了分支 B 而不是 A"）？ | 运维调试 | 近实时 |
| Q7 | 过去 1 小时内失败/超时的实例列表？ | 告警系统 / 运维 | 分钟级 |
| Q8 | 按流程类型统计当前的并发实例数（用于容量规划） | 运维分析 | 小时级 |

**关键发现**：并不是所有运行时查询需求都需要同等级的实时性和查询能力。Q1-Q3 是日常运维的"刚需"（高频率、高实时性要求），Q4-Q8 是"运维增强"需求（中低频率、可容忍一定延迟）。

### 1.4 "运行时"的时间边界：运行时 vs 历史

运行时查询与历史查询（GAP #12）的边界在于实例是否仍处于"活跃"生命周期：

```
实例生命周期：
CREATED → RUNNING → [WAITING / SLEEPING / PAUSED] → COMPLETED / FAILED / TERMINATED
│                                                      │
└── 运行时查询（#11）的范围 ──────────────────────────────┘
                                                        │
                                                        └── 历史查询（#12）的范围
```

但边界并非绝对——实例完成/失败后，其记录应从"运行时索引"移至"历史存储"。这个边界划分方案影响 #11 和 #12 的耦合设计（见 §4）。

## 2. C-007 判定再评估

### 2.1 C-007 对 #11 的判定回顾

> "即使全自动化，运维仍需知道当前有多少 Workflow 实例在运行、哪些卡住了、哪些已完成。运行时可观测性是运维基线能力，不因'自动化'而消失。补偿方案：自定义 Worker 在 Workflow 关键节点写入 D1 索引表（instance_id, status, current_step, started_at, updated_at）；查询 API 直接查 D1。代价评估：中（每个 Workflow 需嵌入状态上报逻辑，D1 表设计 + Worker 查询 API，开发量约 3-5d）。修正后等级：维持高。"

### 2.2 覆盖度分析

| 语义维度 | C-007 是否覆盖 | 覆盖情况 |
|----------|--------------|---------|
| D1 索引表作为运行时状态存储 | ✅ 已覆盖 | "D1 索引表"是正确的存储选择（可 SQL 查询、Serverless、与 Workers 天然集成） |
| Worker API 作为查询接口 | ✅ 已覆盖 | 方向正确——暴露 REST API 供 Dashboard/监控/告警系统调用 |
| 状态上报的写入时机 | ❌ 未提及 | 在每个 Workflow 的关键节点"是什么？step 开始、step 结束、状态变更？写入粒度过细则 D1 写入量过大且延迟高，过粗则查询精度不足 |
| D1 写入的性能影响 | ❌ 未提及 | 每个 step 执行一次 D1 INSERT/UPDATE 会增加 Workflow 的端到端延迟（D1 写入延迟 p50~5ms，p99~50ms）。对于 step 密集的 Workflow（如 20+ steps），累积延迟不可忽略 |
| 写入失败的处理 | ❌ 未提及 | D1 写入可能失败（限流、网络故障、表锁）。写入失败后——重试？跳过？标记不一致？——直接决定了"运行时查询结果的可靠性" |
| 大规模实例下的 D1 查询性能 | ❌ 未提及 | "查 D1" 假设 D1 的 SQL 查询在大量并发写入 + 读取的场景下仍能满足查询延迟要求。D1 的读取是 SQLite 级别——对简单 SELECT 表现良好，但复杂 JOIN/聚合在万级+记录时可能退化 |
| 与 CF 原生 `wrangler` 状态的同步 | ❌ 未提及 | C-007 假设完全自建状态，未讨论是否可以/应该利用 `wrangler workflows instances describe/list` 的底层数据作为状态源——避免重复存储 |
| 运行时状态与历史状态的边界与迁移 | ❌ 未提及 | 实例完成后，运行时索引记录是删除还是标记为 completed 留在原地？何时迁移到 #12 的历史表？——这决定了索引表的大小增长曲线 |
| 查询 API 的认证与权限 | ❌ 未提及 | Worker API 是面向内部运维系统还是需要多用户/多角色？若涉及多角色，需要与 #24（租户隔离）的权限方案对齐 |

### 2.3 再评估结论

**C-007 的"D1 索引 + Worker API"方案在核心方向上正确，但存在五个结构性遗漏：**

1. **写入策略（何时写、写什么）未定义**。这是影响方案可行性的最关键设计决策。"每个 key step 写入"是一个模糊的指导——需要具体化为"Workflow 启动时 INSERT → step 变更时 UPDATE current_step → 状态变更时 UPDATE status → 完成时标记"，并评估这个写入频率对 D1 的压力。写入策略也与 Workflow 的代码侵入性直接相关——是否需要在每个 step 手动调用 `reportStatus()`，还是通过中间件/包装器透明处理。

2. **写入性能与可靠性的权衡未讨论**。D1 写入是同步阻塞的（在 step 内 await D1 write），对 Workflow 的端到端延迟有直接贡献。如果把 D1 写入做成异步（fire-and-forget），可以消除延迟但引入状态不一致风险（写入失败后状态丢失）。两种模式的选择是一个关键的工程权衡，C-007 未提及。

3. **与实际 `wrangler` 状态的关系未分析**。CF 的 `wrangler workflows instances describe/list` 底层必然维护了一个运行时状态——这个状态是否可以/应该被复用？还是完全自建一个独立的状态层？这个选择影响存储冗余度、一致性问题（两个状态源可能不一致）、和整体架构复杂度。

4. **D1 索引表的 schema 设计未提出**。表的字段、索引、分区策略直接决定了查询能力和性能。一个 naive 的 schema（单表，无合理索引）在数百并发实例下可能工作正常，但在数千+实例下查询延迟可能从 ms 级退化到秒级。

5. **查询接口的能力范围未定义**。查询 API 需要支持哪些查询操作（列出、详情、过滤、分页、排序、聚合）？查询语言是 RESTful query params 还是 GraphQL？——这个设计影响 API 的运维集成能力。

**C-007 的"维持高"判定在本期分析中得到加强**——运行时查询不是"做个 CRUD API"的简单任务，而是一个涉及写入策略、性能权衡、schema 设计和 API 设计的系统性工程决策。C-007 的 3-5d 估算在未计入以上遗漏时是合理的下限，包含上述遗漏后的实际量可能在 5-8d。

## 3. 自动化场景需求分析

### 3.1 运行时查询的具体使用者与需求

在自动化场景"自动审核 + 过程审计"的约束下，运行时查询的使用者分为四个角色：

| 角色 | 典型查询 | 实时性要求 | 查询频率 | 查询复杂度 |
|------|---------|----------|---------|----------|
| **Dashboard（运维面板）** | 实例列表（分流程类型、状态筛选）、运行中/卡住/失败实例计数 | 秒-分钟级（轮询间隔 ~10-30s） | 高（持续轮询） | 中等（聚合查询 + 分页） |
| **监控告警系统** | "卡住超过 N 分钟的实例"、"失败率超过阈值"、"运行中实例总数超过容量上限" | 分钟级 | 中等（定时检查，~1-5min 周期） | 低-中（条件过滤） |
| **运维人员（手动排查）** | 通过 businessKey 或 instanceId 查实例详情、当前 step、变量值、执行时间线 | 近实时（手动操作，期望 <1s 响应） | 低（按需手动查询） | 中高（关联查询 + 变量详情） |
| **自动化流程内部** | 幂等性检查（"同一个 businessKey 是否已有在运行的实例？"）、前置依赖检查（"依赖的实例是否已完成？"） | 近实时（阻塞流程执行路径） | 取决于流程逻辑 | 低（精确匹配查询） |

**关键发现**：自动化流程内部也有运行时查询需求——不只是运维人员使用。流程 A 在启动前可能需要查询"是否存在同一 businessKey 的运行中实例"，或被编排器用于并行分支的状态检查。这意味着运行时查询的调用方不仅是外部运维系统，还有 Workflow 自身。

### 3.2 查询维度与过滤条件优先级

按自动化场景实际需求排序：

| 优先级 | 查询维度 | 典型过滤条件 | 使用者 |
|--------|---------|-------------|--------|
| **P0（必须）** | 按 instanceId 精确查询详情 | `instanceId = ?` | 所有角色 |
| **P0（必须）** | 按 status 列出实例（running / completed / failed / paused） | `status = ?`, 分页 | Dashboard / 告警 / 运维 |
| **P0（必须）** | 按 businessKey 查找关联实例 | `businessKey = ?` | 运维 / 流程内部 |
| **P1（重要）** | 按流程类型（processDefinitionKey）筛选 | `workflowName = ?` + status + 分页 | Dashboard / 运维分析 |
| **P1（重要）** | 按时间范围过滤（started_at, updated_at） | `started_at >= ? AND started_at <= ?` | 告警 / 运维排查 |
| **P1（重要）** | "卡住"检测（updated_at 超过 N 分钟未变化 且 status = running） | `status = 'running' AND updated_at < now() - N min` | 告警 |
| **P2（增强）** | 按 current_step 筛选 | `current_step = ?` + workflowName | Dashboard / 运维分析 |
| **P2（增强）** | 按自定义标签/租户筛选 | `tenant_id = ?` / `tags @> ?` | Dashboard / 流程内部 |
| **P3（按需）** | 聚合统计（各状态计数、按流程类型分组计数） | `GROUP BY status/workflowName` | Dashboard |
| **P3（按需）** | 运行时变量查询 | `variables->>'$.orderId' = ?`（JSON 字段查询） | 运维调试 |

### 3.3 与其他 GAP 的重叠度分析

| 关联 GAP | 重叠维度 | 重叠度 | 分析 |
|----------|---------|--------|------|
| **#12 历史查询** | 运行时→历史的迁移边界；共享 D1 表设计 vs 独立表 | **高（85%）** | #11 和 #12 本质上是同一份数据的两个时间窗口视图。#11 查"活跃实例"，#12 查"已完成/已终止实例"。两者共享的字段（instanceId, workflowName, businessKey, startedAt, variables snapshot）高度重叠。最大的设计决策：是一张表 + status 字段区分（简单但性能退化风险），还是两张表 + 实例完成时迁移（复杂但查询性能隔离） |
| **#25 流程追踪** | correlation_id + 结构化日志的可查询性 | **中高（60%）** | #25 的流程追踪需要通过 correlation_id 查询某次执行的完整步骤记录（包括每个 step 的输入/输出/耗时）。这些追踪数据与 #11 的运行时状态在同一个 D1 数据库中的表设计决定了查询的 JOIN 复杂度。#25 的步骤级追踪表可以复用 #11 的 instanceId 作为外键 |
| **#8 补偿边界事件** | Saga 编排器的补偿状态可观测性 | **中（40%）** | C-031 SP9 明确要求补偿状态通过 #11 的运行时索引暴露——"运行时需可查询：哪些实例正在执行补偿？补偿进行到哪一步？哪些步骤的 compensate 失败了？"。这需要 #11 的 D1 schema 预留补偿相关字段（compensation_status, compensation_progress） |
| **#1 并行网关** | DO 聚合器的状态查询 | **中（35%）** | C-011 的方案 B 中，DO 聚合器（JoinCoordinator）维护分支状态。这些状态是否也需要通过 #11 的查询 API 暴露？——如"某并行网关实例的 3 个分支中 2 个已完成、1 个运行中"。若统一通过 #11 API 查询（而不是直接查 DO），需要将 DO 的状态同步到 D1 |
| **#14 管理控制台** | 运行时查询是管理控制台的底层数据源 | **中高（55%）** | C-007 将 #14 定义为"自建 Admin Worker API + 前端 Dashboard，操作通过 Workflow API 实现"。#11 的运行时查询 API 是 #14 管理控制台的**底层数据基础设施**——Dashboard 的实例列表、状态筛选、详情查看都是调用 #11 的 API。两者的接口设计需要对齐 |
| **#5 多实例** | 批量实例的状态聚合查询 | **中（35%）** | 多实例场景中，一次批量操作产生 N 个 Workflow 实例。运维需要能按"批次 ID"筛选这 N 个实例的状态（多少成功、多少失败、多少仍在运行），并在 Dashboard 上以聚合视图呈现。这需要 #11 的 D1 schema 和查询 API 支持"批次"维度的过滤和聚合 |
| **#4 事件子流程** | 中断等待状态的可见性 | **中低（30%）** | #4 SP2 中，Workflow 进入 `waitForEvent("cancel")` 阻塞等待。从运维视角，这表现为"状态 = waiting_for_event"。#11 的 current_step 需要能区分"正在执行 step X"和"在 step X 处等待事件 Y"——否则运维无法区分"正常运行中"和"无人响应的等待" |
| **#6 定时边界事件** | sleep 等待状态的可见性 | **低（25%）** | #6 的 `workflow.sleep()` 产生"状态 = sleeping"——运维需要知道哪些实例在 sleep、sleep 剩余时间。但 sleep 的时长通常由代码定义（可推导），实时性要求不高 |
| **#24 租户隔离** | 多租户场景下查询需要 tenant_id 过滤 | **中（40%）** | #24 的逻辑隔离方案（所有标识符加 tenant_id 前缀，Worker API 基于 tenant_id 过滤）直接影响 #11 的 D1 schema——每个索引记录都需要 tenant_id 字段，每个查询 API 调用都需要 tenant_id 过滤 |

**核心发现**：#11 运行时查询与 #12（历史查询）和 #14（管理控制台）的交叉依赖性最高——它们是同一个"流程可观测性基础设施"的三个面。#11 是运行时视图，#12 是历史视图，#14 是管理交互视图。三者的 D1 schema 和 API 设计应统一规划，而非各自独立设计。

### 3.4 运行时查询的使用频率与数据量估算

| 指标 | 估算 |
|------|------|
| **并发运行实例数（日常）** | 假设 50-200 实例（取决于业务规模） |
| **并发运行实例数（峰值）** | 假设 500-1000 实例（批量操作 / 定时任务触发） |
| **D1 写入频率** | 每个实例每个 step 变更时 1 次 UPDATE + step 详情 1 次 INSERT（#25）；实例启动 1 次 INSERT；实例完成/失败 1 次 UPDATE。假设平均每实例 10 steps，则每次完整执行约 22 次 D1 操作 |
| **D1 读取频率** | Dashboard 轮询（每 30s，所有运行中实例的 status 查询）约 2-7 QPS；运维手动查询（低频 < 0.1 QPS）；告警检查（每 5min） |
| **运行时索引表大小（稳态）** | 运行中实例数 × 记录大小（~1KB/记录）。若自动清理完成后不过 200-1000 行，但若不清理则持续增长。关键：表大小取决于完成实例的清理策略 |
| **D1 查询延迟目标** | 精确匹配（instanceId / businessKey）：<50ms p95；条件过滤 + 分页（status + workflowName）：<200ms p95；聚合统计：<500ms p95 |

## 4. 问题拆解

### 4.1 子问题清单

| # | 子问题 | 描述 | 与其他 GAP 的关系 | 复杂度 |
|---|--------|------|-----------------|--------|
| **SP1** | **D1 索引表 Schema 设计** | 定义运行时状态表（workflow_instances）的字段、索引、分区策略。核心字段：instance_id, workflow_name, business_key, status, current_step, started_at, updated_at, tenant_id, tags, variables_summary。核心索引：instance_id (PK), business_key (unique constraint), (workflow_name, status) 复合索引, updated_at 索引（用于卡住检测） | 与 #12 共享 schema 基础，与 #24 需要 tenant_id 字段，与 #25 共享 instance_id 作为外键 | **中**（~1-2d） |
| **SP2** | **状态写入策略与 SDK 设计** | 定义何时写入、写什么。包括：(a) Workflow 启动时自动 INSERT（通过标准化 `initRuntimeTracking()` helper）；(b) step 推进时 UPDATE current_step + updated_at；(c) 状态变更（暂停/恢复/失败/完成）时 UPDATE status；(d) 补偿状态变更时 UPDATE compensation 字段。设计为 SDK 中间件而非迫使每个 step 手动调用 | 与 #8 SP9（补偿状态）、#4（waitForEvent 状态）、#6（sleep 状态）相关 | **中高**（~2-3d） |
| **SP3** | **写入可靠性策略** | 定义 D1 写入失败的处置：(a) 同步写入 + 失败重试（保证一致性但有延迟）；(b) 异步写入 + 丢失容忍（低延迟但状态可能缺失）；(c) 混合策略——关键状态变更（启动/完成/失败）同步写入，非关键更新（current_step）异步写入。定义最大重试次数、退避策略、以及持久化失败后的告警 | 与 #23（重试管理）共享重试基础设施 | **中**（~1-1.5d） |
| **SP4** | **查询 API 设计** | 定义 Worker API 的端点、查询参数、响应格式：(a) `GET /instances`（列表 + 过滤 + 分页 + 排序）；(b) `GET /instances/:id`（详情，含当前变量摘要）；(c) `GET /instances/:id/steps`（步骤执行历史，与 #25 关联）；(d) `GET /instances/stats`（聚合统计）。认证方案（API Key / Service Token） | 与 #14 对齐接口契约 | **中**（~1.5-2d） |
| **SP5** | **运行时→历史的迁移策略** | 实例完成后（status = completed / failed / terminated）：(a) 立即从运行时表迁移到历史表；(b) 在运行时表标记为 completed 并保留 N 天（通过定时任务清理）；(c) 运行时表使用 D1 Time Travel 恢复能力，不显式迁移。每种选择的权衡：查询性能隔离 vs 实现复杂度 vs 存储成本 | 与 #12 强耦合——直接影响 #12 的历史表 schema 和归档策略 | **中高**（~1.5-2d） |
| **SP6** | **与 CF wrangler 状态的关系决策** | 是否利用 `wrangler workflows instances describe/list` 的底层数据作为状态源？如果利用：(a) 减少自建状态存储的数据冗余；(b) 但 wrangler 数据是 CF 内部系统，无 API 稳定性保障；(c) 两个数据源可能产生不一致（自建 D1 的 status 与 wrangler 的 status 不同步）。推荐：**不使用 wrangler 数据作为可靠状态源**——wrangler 是运维工具而非 API，其数据模型和稳定性无合同保障 | 独立决策，但影响 D1 schema——若使用 wrangler 数据则字段需对齐 | **低**（~0.5d 调研 + 决策） |
| **SP7** | **大规模实例下的 D1 查询性能保障** | 当并发运行实例数增长到 1000+ 时：(a) D1 单表查询是否需要分页优化（cursor-based pagination vs offset）；(b) 复杂聚合查询（GROUP BY + COUNT）是否在 D1 上性能可接受，或需要建立物化缓存（如定时任务预计算聚合结果写入另一张小表）；(c) D1 的读写并发压力——大量 Workflow 同时写入状态 + Dashboard 轮询读取场景下的性能表现 | 独立性能问题 | **中**（~1d 评估 + 优化） |
| **SP8** | **运行时查询与 Workflow 幂等性/依赖检查的集成** | 定义流程内查询的使用模式：(a) 幂等性检查 helper——`await runtimeQuery.findActiveByBusinessKey(key)`；(b) 前置依赖检查——`await runtimeQuery.waitForInstance(instanceId, 'completed')`。这些内联查询直接阻塞 Workflow 执行，需要可靠的超时和失败处理 | 与 #4（waitForEvent 模式可能替代轮询等待）、#1（并行分支间依赖检查）相关 | **低中**（~0.5-1d） |

│   │   - 写入 QPS：1000 实例 × 平均 0.1 step变更/s = 100 writes/s

│   │

### 4.4 与 C-007 Phase 排布的关系

C-007 将 #11（运行时查询）放在 Phase 1，与 #12（历史查询）、#25（流程追踪）、#8（Saga 编排器）、#23（重试/死信）、#24（租户隔离）同属"基础补偿设施"阶段。**本期分析确认此排布合理**：

1. RuntimeTracker SDK 是 Workflow 代码嵌入的运行时基础设施——越早就位，后续开发的 Workflow 可以直接使用，不需要后期添加状态上报的 retrofitting 成本。

2. #11 的 D1 schema 是 #12（历史查询）、#25（流程追踪）、#14（管理控制台）的数据基础——先确定 schema 后，其他 GAP 可以复用同一数据库和表结构。

3. 但有一个排布建议：**#11 和 #12 应同时设计 schema**（即使 #12 的完整实现在后面）。运行时表和历史表的 schema 如果分开设计（先做 #11 再做 #12），后续可能需要 migration 来对齐字段。应在 Phase 1 同时输出 #11 和 #12 的 D1 schema 设计，但 #12 的历史归档和复杂查询 API 可以延后。

## 6. 是否需要独立 plan-eng-review 的建议

### 6.1 建议：需要独立 plan-eng-review

**理由**：

1. **#11 是 Phase 1 的基础设施组件，不是任何已有 GAP 的附属品**。它有自己的 8 个子问题需要设计决策，与 9 项其他 GAP 有交叉。虽然它的概念（D1 索引 + API）比 Saga 编排器（#8）简单，但其 schema 设计和 SDK 接口定义是多 GAP 复用的基础——草率设计会导致后续 GAP 的返工。

2. **#11 与 #12 的 schema 联合设计是 plan-eng-review 的关键产出**。如 §4.2 分析，运行时表和历史表的 schema 应一次性设计（即使 #12 的完整实现在后面）。plan-eng-review 是完成这个联合设计的正确阶段。

3. **SP2（写入策略）和 SP3（写入可靠性）是影响 Workflow 代码模式的核心决策**。RuntimeTracker SDK 的接口设计直接影响所有 Workflow 的开发体验——每个 step 是否需要手动调用 `tracker.stepStarted()`，还是通过 wrapper 自动跟踪。这个决策在 plan-eng-review 中通过 API 设计来确定。

4. **plan-eng-review 的交付重点**：
   - D1 schema 设计（SP1）——运行时表 + 历史表联合 schema（与 #12 联合输出）
   - RuntimeTracker SDK API 设计（SP2）——写入接口、写入模式（同步/异步/混合）
   - 查询 API 端点设计（SP4）——RESTful endpoint、query params、response format
   - 迁移逻辑设计（SP5）——运行时→历史的迁移时机、事务保证、失败重试
   - 与 #12、#14、#25、#8 的接口契约
   - 性能基准与扩展策略（SP7）

5. **产出规模**：约为 C-011（GAP #1 plan-eng-review）的 0.8-1.0 倍。比 #1 的 7-8d 补偿方案设计更轻量（运行时查询不涉及新的 DO 类或复杂的事件路由），但其跨 GAP 的 schema 设计复杂度（与 #12/#25/#14 的共享表设计）是 #1 中没有的独特挑战。

## 8. 本期结论

1. **语义层面**：CF Workflows 无原生运行时查询 API 的本质是"引擎不为你维护运行时状态表"。在 BPMN 中，查询是对引擎自动维护的数据库的 SQL 查询；在 CF Workflows 中，必须显式在 Workflow 代码中写入状态到 D1，再通过自建 API 查询。这引入了 BPMN 中不存在的设计决策：写入时机、写入粒度、写入可靠性——这些直接影响"运行时可观测性"的完整性和准确性。

2. **C-007 判定**：方向正确（D1 索引 + Worker API），但存在五个遗漏——(a) 写入策略未定义（何时写、写什么），(b) 写入性能与可靠性权衡未讨论（同步 vs 异步），(c) 与 CF wrangler 状态的关系未分析，(d) D1 schema 设计未提出，(e) 查询 API 的能力范围未定义。本期将这些遗漏识别为 SP1-SP5，构成对 C-007 方案的关键补充。

3. **自动化场景需求**：运行时查询有四个使用者角色——Dashboard（高频轮询）、监控告警（定时检查）、运维人员（按需手动查询）、自动化流程内部（幂等性/依赖检查）。查询维度中 P0 必须支持：instanceId 精确查询、status 条件列表、businessKey 精确匹配。流程内部也有查询需求（不再是纯运维工具），这要求 RuntimeTracker 和 RuntimeQueryClient 的设计兼顾 Workflow 内部调用场景。

4. **交叉依赖**：#11 与 #12（历史查询）和 #14（管理控制台）有最高的交叉耦合——它们是同一个"流程可观测性基础设施"的三个面。#11 的 D1 schema 是 #12 历史存储和 #14 Dashboard 的底层数据基础。同时 #11 与 #25（步骤追踪）、#8（补偿状态）、#1（并行分支状态）、#4（等待状态）有数据共享和字段扩展关系。

5. **问题拆解**：8 个子问题中，SP1-SP4 是核心交付（5-8d），SP5-SP8 是增强与关联（1-3d）。SP1（D1 schema）是与 #12 联合设计的——推荐独立运行时表 + 独立历史表（方案 A），实例完成时迁移而非标记留在原地。SP2（写入策略）推荐混合模式——关键操作（init/markCompleted/markFailed）同步写入，普通操作（stepStarted/stepCompleted）异步写入。SP3（写入可靠性）提供重试 + 告警的降级路径。

6. **等级建议**：维持高。理由：运行时可观测性是自动化运维基线（不可省略）、交叉依赖广度 9 项 GAP（仅次于 #8 的 7 项）、D1 schema 的设计基线性（#12/#25/#14 的数据基础）、工程复杂度被 C-007 低估（+1.5-4d 增量）。

7. **是否独立 plan-eng-review**：需要独立 plan-eng-review。产出规模约为 C-011 的 0.8-1.0 倍。核心交付：#11 + #12 D1 schema 联合设计、RuntimeTracker SDK API 设计、查询 API 端点设计、迁移逻辑设计、性能评估。与 #12 的 schema 联合设计是 plan-eng-review 的独特产出。

8. **未决问题**：QU1（instance_id 获取方式）和 QU2（D1 写入并发限制）为高优先级，应在 plan-eng-review 启动前通过实际测试确认。QU3（自定义标签过滤）和 QU4（error_message 详细度）为中等优先级，可在 plan-eng-review 中并行分析。

9. **与 C-007 Phase 排布的对齐**：C-007 将 #11 放在 Phase 1 的排布合理。但建议 #11 和 #12 的 D1 schema 应在 Phase 1 一次性联合设计（即使 #12 的完整实现延后到 Phase 1 后期或 Phase 2），避免后续 schema migration 的返工成本。
