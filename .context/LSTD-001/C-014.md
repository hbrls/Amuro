### 2.2 GAP #2 是否可以直接复用 GAP #1 的结论，还是需要独立进入 plan-eng-review？

**可直接复用。** C-013 §3、§4 和 §8.3 的逐接口分析一致表明：

| 维度 | 结论 |
|------|------|
| 是否需要独立方案 A/B 适配 | 否——方案 A 和方案 B 均可直接复用 |
| DO 聚合器接口改造 | 仅需一个语义增强：空 `childIds` 注册（M=0 场景） |
| 增量工作量 | 方案 A：~0.1d/流程；方案 B：~0.5d（DO）+ 0.1d/流程 |
| 总增量成本 | ~0.5d + 0.1d/流程（对比 GAP #1 的 12-15d） |

GAP #2 是"零新增架构、零新增方案"的邻接 GAP，**不需要独立 plan-eng-review**。其结论归入 C-013 即可，在 GAP #1 的 Phase 2 DO 聚合器实现时一并处理空 `childIds` 场景。

### 2.4 是否需要继续推进下一项 GAP？

**是。** GAP #2 包含网关讨论充分完成，结论可直接复用到 GAP #1 的补偿方案。

按 current-task.md 调度表，下一项待处理的 GAP 为 **GAP #4 事件子流程**。

选择 GAP #4 的理由：

| 因素 | 分析 |
|------|------|
| 调度顺序 | current-task.md 调度表中 #4 紧随 #2 之后 |
| 独立性 | 事件子流程涉及"等待外部中断信号"语义，与并行/包含网关的"分支/汇聚"语义本质不同——无法从 GAP #1/#2 的 DO 聚合器直接复用 |
| 与已有基础设施的关联 | GAP #4 的补偿方案（step 间 `waitForEvent` 检查点）可能复用 `workflow.waitForEvent()` 和 DO 中断标志，需评估与已讨论 GAP 的技术衔接 |
| C-007 初步判定 | 补偿方案为"step 间检查点 + `waitForEvent` / DO 中断标志"，开发量约 2-3d，维持高 |
