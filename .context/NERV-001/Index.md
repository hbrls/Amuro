# Agent 自主工作业界现状研究

> updated_by: Codex - GPT-5
> updated_at: 2026-07-31 15:37:24

## 议题

研究业界如何让 Agent 持续获得工作、推进工作并形成可治理的完成闭环。

关注的不只是人向 Agent 发起一次任务的对话式协作，还包括 Agent 如何在持续运行的工作环境中发现或接收工作、参与任务分配、完成执行并汇报结果。

## 目标

了解 Agent 工作流与运营模型的业界现状，识别已经普遍落地的模式、仍处于探索阶段的模式，以及近期的发展方向。

本议题希望最终形成以下方向性判断：

- 业界如何定义 Agent 的自主工作。
- Agent 的工作通常从哪里产生，又如何进入 Agent 的执行范围。
- Agent 如何被分派工作或自主接单。
- Agent 如何持续推进任务，并在完成、失败或受阻时形成反馈。
- 人工介入、权限控制和组织治理在这些流程中承担什么角色。
- 不同 Agent 工作模式目前各自处于什么成熟阶段，适用于哪些场景。

## 关注范围

- 人工触发的 Copilot 工作模式。
- 由任务系统分派或认领的任务代理模式。
- 由事件、状态变化或周期条件触发的 Agent 工作模式。
- Agent 主动观察环境、发现工作并持续推进的自治模式。
- 单 Agent、监督者调度和多 Agent 协作在工作流程中的常见关系。
- 工作完成后的验证、汇报、审计与后续衔接。

## 边界

本阶段只研究业界现状、流程形态、成熟度和发展方向。

本阶段不包含：

- 为 Glintz 设计具体 Agent 工作方案。
- 定义任务字段、状态机、文件格式或调度器。
- 选择具体技术框架或供应商产品。
- 编写实现代码或改造现有工作流。
- 在本文件中预设具体调研过程、资料来源或任务拆分。

具体调研、证据收集和结论收束由后续 workshop 任务及执行 Agent 完成。

### 调研主体与证据边界

- 确认唯一调研产品的正式名称、官方主页、官方源码仓库和许可证。
- 明确目标版本、分支、Release 与调研日期，避免混用不同证据窗口。
- 聚焦与中心调度和工作机接入有关的模块，记录明确排除的非目标模块。
- 不在 Index 中预设或暗示具体产品名称。

### 开源与服务边界

- 核验开源协议、主干代码可见性，以及是否存在闭源核心模块。
- 区分本地、自托管、云端 SaaS 和混合运行形态，确认各形态的功能完整度。
- 核验账号、授权、同步、配置、调度和执行等能力分别位于本地还是云端。
- 识别云端强绑定依赖、数据离开工作机的边界，以及断网后的功能影响。

### 中心调度核心关注点

#### 调度判定基准

- WorkSpace 或 Project 只是工作容器，不因能够组织文件、记忆、会话或配置而自动构成调度系统。
- 产品存在 Task，或能够在 Task 到达后唤起 Agent，只能证明任务承接与执行能力，不能证明产品拥有调度能力。
- Stateful 调度系统必须持久拥有工作对象、对象关系、任务状态和执行归属，并负责判断任务何时可执行、按何种顺序推进、由谁执行以及失败后如何继续。
- 必须核验调度状态在进程重启、客户端断线或 Agent 退出后是否仍可恢复；只依赖单次会话上下文或临时进程状态的能力按 Stateless 或 Serverless 执行形态记录。
- 若产品不满足上述条件，报告必须明确将其归类为任务执行宿主、自动化运行器或无状态任务消费者，不得因其使用“Agent”“Task”“Plan”“Always-On”或“Router”等名称而判定为调度工具。

#### 工作对象模型

- 分别核验 Workspace、Project、Issue、Plan、Task 是否为真实、持久化的产品对象；不得预设这些对象全部存在。
- 说明各对象的标识、归属、层级、创建来源、状态所有者和相互转换关系；对象不存在时直接记录缺失及影响。
- 区分 Plan 是持久化的编排对象，还是仅供单次 Agent 执行参考的文本产物。
- 区分 Issue 或 Task 是调度中心拥有的工作记录，还是从外部系统读取后交给 Agent 的输入。

#### 任务关系与生命周期

- 核验 Task 之间是否支持父子关系、先后顺序、前置依赖、阻塞关系、并行分支或 DAG，并说明这些关系由谁持久化和解释。
- 核验任务状态机、允许的状态迁移及迁移责任方，重点说明谁把任务从等待推进到可执行、运行、完成、失败或阻塞。
- 核验上游完成、失败、取消或超时后，下游任务如何解锁、阻塞、跳过、重试或终止。
- 核验优先级、计划时间、事件触发、并发限制和资源约束是否参与调度决策。

#### Agent 分派与连续性

- 核验系统是否选择、分派、唤起或重新唤起 Agent，以及 Agent 与 Task 的归属关系是否持久化。
- 区分一次性启动 Agent、已有 Agent 领取任务和调度器主动选择执行者三种形态，不得混为调度。
- 核验 Agent 退出、失败或断线后，Task 是否能够由原 Agent 恢复、转交其他 Agent 或重新排队。
- 核验执行进度、检查点和结果是否属于调度状态，还是仅存在于 Agent 会话内部。

#### 数据库与持久化

- 核验工作对象、依赖关系、任务状态、执行归属、进度和结果分别存放在哪里，以及由哪个组件拥有。
- 强制数据库类型、最低版本和专属扩展依赖。
- 外置数据库、内嵌数据库和内存临时库的实际运行与持久化差异。
- 依赖是否可关闭、替换或剥离，以及相关架构影响。

#### 对外接口

- 调度侧使用的 REST、WebSocket、gRPC、CLI、SDK 或进程间接口。
- 客户端接入、管理界面和第三方扩展接口的职责边界。
- 鉴权方式、接入准入规则与权限模型。

#### 消息通信

- 服务端推送、客户端轮询或其他主交互模式。
- 长连接、短连接、断线恢复与必要的保活机制。
- 进程内通信、跨机器通信和第三方消息中间件的边界。

#### 任务队列

- 持久化队列与内存队列的总体实现形态。
- 单机和分布式场景的最小依赖。
- 任务防重复领取、原子抢占和并发协调的关键机制。
- 任务领取、租约、超时回收、重试和失败转移是否由中心状态驱动，还是仅由单次执行进程处理。

以上关注点用于定义需要回答的问题，不要求无差别扫描全部数据库表、接口、队列或锁实现；源码深度由 RUNBOOK 的问题驱动与停止条件控制。

### Windows 与 macOS 工作机

- PC 在本专项中同时指 Windows 和 macOS，不能把 PC 等同于 Windows。
- 分别核验两个平台的安装方式、运行入口、权限、依赖、网络要求、升级和卸载方式。
- 分别区分完整中心调度服务、客户端程序和辅助组件在两个平台上的支持情况。
- 区分原生二进制、安装包、容器和源码构建等形态，不能用 Linux 容器支持代替工作机原生支持。
- 任一平台缺失或能力不完整，都应作为明确的选型缺陷写入结论，但不得因此停止其余调研。

### 本地、云端与混合运行形态

- Local 优先是产品选型标准，不是调研范围限制。
- 必须确认主体功能实际运行在工作机、云端还是两者之间，并说明桌面客户端是否只是云端服务的壳。
- 只要存在云端组件，就必须调研其职责、核心组件、主要依赖、接口、持久化、通信、部署或托管形态，以及数据、权限和网络边界。
- 即使云端只承担认证、转发、路由或代理，也应说明数据经过方式、鉴权和故障影响。
- 主体能力依赖云端、本地能力不完整或断网后核心流程不可用时，应报告为 Local 优先选型缺陷，同时完整保留云端调研结果。

### 客户端与调度层接入

- 确认官方标准接入载体，如桌面客户端、CLI、SDK 或公开协议。
- 区分客户端创建或管理任务、客户端领取任务、服务端唤起客户端执行三种接入语义，并说明调度状态由服务端还是客户端持有。
- 判断目标工具能否跳过官方客户端直接接入调度中心。
- 不可直接接入时，评估桥接适配层或服务端协议适配的改动范围与架构影响。
- 区分 Windows 与 macOS 上的接入差异。

### 依赖根源与改造边界

- 区分任务锁、事务和状态一致性等架构底层刚需依赖，与向量检索、智能匹配等上层附加能力依赖。
- 对影响核心判断的硬依赖进行定点源码定位，并评估关闭、替换或剥离的影响。
- 识别调度最小核心职责与非调度增值能力的边界。
- 输出改造范围和风险，不在本专项实施代码改造。

### 架构范式与扩展可行性

- 首先判定产品属于 Stateful 调度器、任务执行宿主、自动化运行器还是 Stateless / Serverless 任务消费者，再识别中心化特权调度服务、分布式任务池或其他架构范式。
- 判断调度逻辑是否能够下沉或封装为普通 Agent 任务节点；如果下沉后失去持久任务状态、依赖解析或执行归属，则不得视为等价调度能力。
- 识别任务隔离、多调度节点协调和互斥机制对扩展方式的约束。

### 预期结论

- 形成一份仅针对当前唯一产品、证据可追溯的独立调研报告。
- 明确 Workspace、Project、Issue、Plan、Task 的实际对象模型、缺失项，以及 Task 之间的顺序、依赖和生命周期推进方式。
- 明确产品是否具备 Stateful 调度能力；若仅能承接已有 Task 并启动 Agent，必须归类为执行宿主或 Stateless / Serverless 任务消费者。
- 明确任务状态由谁持有，任务如何进入可执行状态、如何选择执行者，以及失败、断线和重启后如何恢复或转移。
- 明确 Windows 与 macOS 支持情况、Local 优先适配程度、云端依赖、最小部署成本、运维复杂度和私有化改造边界。
- 对平台缺失、云端主体依赖、闭源核心、功能阉割或无法剥离的硬依赖明确标注选型缺陷。
- 报告不得包含其他产品、横向比较、选型矩阵或优劣排名。
